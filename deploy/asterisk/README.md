# Asterisk для LeadDrive — разворачивание рядом с живым 3CX

Цель: убрать 3CX из тракта голоса и получить трубку **внутри CRM**
(3CX блокирует сторонние WebRTC-клиенты, поэтому софтфон в LeadDrive
с ним невозможен в принципе).

Параметры транка: [docs/voip-migration-trunk-dossier.md](../../docs/voip-migration-trunk-dossier.md)

## Прежде чем начинать — одно решение

**Один SIP-аккаунт нельзя зарегистрировать дважды.** Как только Asterisk
зарегистрирует `994995111103`, регистрация 3CX слетит. Параллельно они
работать не будут — начнут перебивать друг друга.

Варианты:

1. **Второй SIP-аккаунт у оператора** (рекомендуется). Asterisk поднимается
   и тестируется рядом с живым 3CX, переключение — одной правкой.
   Требует заявки оператору, закладывать время.
2. **Окно переключения.** Гасим транк в 3CX, поднимаем на Asterisk.
   Откат ручной, телефония на время работ недоступна.

Whitelist у оператора менять **не нужно** — сервер тот же,
IP `185.161.225.131` уже разрешён. Это единственный пункт, который
мы сэкономили за счёт установки на ту же машину.

## Шаг 1. Проверить, что порты свободны

3CX держит 5060/5061 и свой RTP-диапазон. Мы садимся рядом, не поверх.

```bash
ss -lunp | grep -E ':(5070|8089|2000[0-9])' || echo "порты свободны"
```

Если что-то занято — поменять `bind` в `etc/pjsip.conf` и `rtp.conf`,
**не трогая порты 3CX**.

## Шаг 2. Секреты

```bash
cp .env.example .env
```

Заполнить `.env` на сервере, руками:

- `TRUNK_PASSWORD` — пароль SIP-транка. Взять в 3CX:
  Voice & Chat → транк `994995111103` → Authentication password → «показать».
- `WEBRTC_PASSWORD` — придумать новый, для регистрации софтфона CRM.
- `EXTERNAL_IP` — `185.161.225.131`.

`.env` в git не коммитится. Пароли не пересылать в переписке.

## Шаг 3. Сертификат для WSS

Браузер не подключится к софтфону без валидного TLS. Домен уже есть
у 3CX, поэтому берём отдельный поддомен, например `pbx.fanum.az`:

```bash
certbot certonly --standalone -d pbx.fanum.az --http-01-port 8080
mkdir -p certs
cp /etc/letsencrypt/live/pbx.fanum.az/fullchain.pem certs/asterisk.pem
cp /etc/letsencrypt/live/pbx.fanum.az/privkey.pem  certs/asterisk.key
chmod 640 certs/*
```

Самоподписанный сертификат не подойдёт — Chrome отклонит WSS молча.

## Шаг 4. Запуск

```bash
docker compose up -d && docker compose logs -f asterisk
```

## Шаг 5. Проверить регистрацию транка

```bash
docker compose exec asterisk asterisk -rx "pjsip show registrations"
```

Ожидаем `Registered`. Если `Rejected` — сверить пароль и убедиться,
что 3CX не держит ту же регистрацию (см. решение выше).

```bash
docker compose exec asterisk asterisk -rx "pjsip show endpoint trunk"
docker compose exec asterisk asterisk -rx "pjsip show aors"
```

## Шаг 6. Тестовый звонок

```bash
docker compose exec asterisk asterisk -rx \
  "channel originate PJSIP/1001 extension +994512060838@from-internal"
```

В логе должно быть видно нормализацию: `E.164 -> нацформат` и далее
`Набор через транк: 0512060838`. Если в логе улетает `+994...` —
диалплан не сработал, звонок оператор отобьёт.

## Откат

```bash
docker compose down
```

Транк освобождается, 3CX перерегистрируется сам в течение ~180 секунд
(его Re-Register timeout). Проверить в 3CX: Voice & Chat → индикатор
транка должен снова стать зелёным.
