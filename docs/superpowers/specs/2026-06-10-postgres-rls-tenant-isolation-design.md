# Postgres RLS — DB-Enforced Tenant Isolation — Design Spec

- **Date:** 2026-06-10
- **Status:** Draft v2 (architect-reviewed, 4 fixes applied; awaiting user review → writing-plans)
- **Branch:** `feat/rls-tenant-isolation`
- **Driver (user-confirmed):** first live client (zeytunpharm) launches soon; enable DB-level isolation **while the platform has zero live clients** — the regression-risk window is as cheap as it will ever be. Resource pressure is NOT a driver (DB = 57 MB; RAM 1.4/7.6 GB; the user's "27 GB" was disk build-artifacts/logs).

## 1. Goal

Add **Postgres Row-Level Security** as defense-in-depth UNDER the existing app-level isolation: the database itself refuses to return another tenant's rows, even if application code forgets a `where organizationId`. App-level scoping (requireAuth/getOrgId + JWT subdomain binding + per-tenant KEK encryption) stays — RLS is the safety net, not a replacement.

**Non-goals:** DB-per-tenant (rejected — see session analysis 2026-06-10); `mtm_db` (separate small DB, own pass later); global tables (`plan_templates`, etc. — no `organizationId`, no policy); data residency / noisy-neighbor concerns.

## 2. Current state (verified)

- Single DB `leaddrive_v2`, **~300 tenant tables**, every one carries camelCase `"organizationId"` (verified via information_schema earlier; 1254 schema mentions). Connection: single user **`hermes`** (likely table owner → **owner bypasses RLS unless `FORCE`** — load-bearing fact for §3.D1) at `localhost:5432`, direct (no PgBouncer → no transaction-pooling caveats).
- Prisma 6, singleton at `src/lib/prisma.ts:24` — ONE integration point for a client extension.
- Org context today: `requireAuth`/`getOrgId` (478 call sites) resolve the tenant per-request; **no AsyncLocalStorage in the codebase yet**.
- **Cross-tenant (bypass) surfaces that legitimately query without/across orgs:**
  - login/auth flow (`src/lib/auth.ts:179,209,264` — user lookup BEFORE org is known),
  - superadmin API (`/api/v1/admin/{plans,tenants,upload-logo}`) + superadmin server pages (`/admin/*` call prisma directly),
  - **34 cron routes** (`/api/cron/*`),
  - **46 scripts** with their own `new PrismaClient()` (seeds, backfills, migrations),
  - inbound webhooks (WhatsApp/social/email) that resolve the org FROM the payload (query before org context exists),
  - tenant export, purge, provisioning.

## 3. Design decisions

### D1 — Single DB user + `FORCE ROW LEVEL SECURITY` + session-variable bypass (chosen)

Policies apply to the table owner only with `FORCE`. Rather than a second DB role + second Prisma pool (textbook but doubles plumbing), use **one pool** and two session variables:

```sql
ALTER TABLE "deals" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "deals" FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "deals"
  USING (
    "organizationId" = current_setting('app.org_id', true)
    OR current_setting('app.rls_bypass', true) = 'on'
  )
  WITH CHECK (
    "organizationId" = current_setting('app.org_id', true)
    OR current_setting('app.rls_bypass', true) = 'on'
  );
```

`USING` governs read/update/delete **visibility**; **`WITH CHECK` governs writes** (INSERT and the new row on UPDATE) — without it, write-isolation is not enforced the way §7 claims. The generator emits BOTH clauses on every policy (architect fix #1).

- `current_setting(..., true)` returns NULL when unset → **fail-closed**: a query with NO context matches nothing.
- Bypass is grantable ONLY through our helper (`runWithRlsBypass()` / script helper) — enforced by code review + the CI classification test (§6). Single policy shape for all ~300 tables → generated by script, not hand-written.

*Rejected alternative:* two DB roles (`app_tenant` / `app_admin BYPASSRLS`) — stronger separation but two pools, two clients, double env plumbing; revisit if an auditor demands role-level separation.

### D2 — AsyncLocalStorage context + Prisma client extension (zero route edits)

The naive approach edits 478 routes to use a per-tenant client. Instead:

- `src/lib/rls-context.ts`: an `AsyncLocalStorage<{ orgId?: string; bypass?: boolean }>` + `runWithTenant(orgId, fn)` / `runWithRlsBypass(fn)`.
- `requireAuth`/`getOrgId` (and the superadmin/cron guards) **enter** the context once, where the org is already resolved today.
- `src/lib/prisma.ts`: `$extends({ query: { $allOperations } })` — reads ALS; if context exists, wraps the operation in a transaction that first runs `SELECT set_config('app.org_id', $1, true)` (or `app.rls_bypass`), so the setting and the query share one connection. No context → pass through untouched (and the DB fails closed).
- **Interactive `$transaction` callsites (125 in the codebase, e.g. `payment-webhooks/[provider]/route.ts:133`) — explicit sub-decision (architect fix #2):** inner `tx.*` queries do NOT pass through the per-operation wrap, and opening a nested transaction inside an interactive one is a Prisma footgun. The extension therefore hooks **both** levels: per-operation wrap for plain calls, AND a `$transaction` override that injects `set_config(...)` as the FIRST statement inside the user's transaction callback (tx-open wrap). Inner `tx.*` queries then inherit the setting for the life of that connection-pinned transaction. The plan must include a unit test for a nested case.
- **Raw queries:** 44 `$queryRaw/$executeRaw` callsites bypass the extension's model-level hooks but NOT the `$allOperations`/tx-open wrap — they run with whatever context their surrounding request entered; with no context they hit fail-closed. The plan's E2E covers the raw-query-heavy paths (reports, totals).
- **ALS entry mechanism (architect fix #4):** context is entered in the **Node runtime**, NOT Edge middleware (Edge can't host the Prisma client's ALS). `requireAuth`/`getOrgId` *return* mid-handler rather than wrapping it — so entry happens via `AsyncLocalStorage.enterWith()` called inside those guards (binds the rest of the request's async continuation in Node), with `runWithTenant/runWithRlsBypass` wrappers used by webhooks/public pages/instrumentation where a scoped block is clearer. `enterWith` semantics (and its test) are an explicit plan item.
- Result: **route bodies don't change.** The sweep is ~8 files (rls-context, prisma extension incl. tx hook, api-auth, superadmin-guard, cron guard, auth.ts login bypass, instrumentation.ts, script helper) + the webhook/public-page entry list (§5).

### D3 — Scripts (46) get a one-line helper

Pool connections don't share `SET` state. Scripts adopt `scripts/_rls.mjs`: forces `connection_limit=1` on the URL + runs session-level (`is_local=false`) `set_config('app.rls_bypass','on')` once after connect. Each script adds one import+call at the top. (Scripts that are per-tenant, e.g. seeds with `--slug`, may instead set `app.org_id` — decided per script in the plan.)

### D4 — Rollout in table batches; rollback is instant

`ENABLE/FORCE RLS` per table is **independent and instantly reversible** (`DISABLE ROW LEVEL SECURITY` — no migration, no data movement). Phases:
1. Ship plumbing (ALS + extension + helpers) with RLS enabled on **zero** tables — pure no-op in prod, soak.
2. Enable on a 5-table low-risk batch (e.g. `currencies`, `task_types`, `event_types`, `sla_policies`, `taskTemplates`) → smoke on demo tenants.
3. Enable on the rest in 2–3 batches (generator script emits both `enable.sql` and `disable.sql` per batch) → smoke between batches.
4. Watch fail-closed symptoms (empty lists where data exists) for a soak period before zeytunpharm onboards.

### D5 — Fail-closed is the chosen failure mode

A missed context = empty result, never a leak. UI shows "no data" — loud, debuggable, safe. The plan adds a dev-mode warning in the extension (`console.warn` when a tenant-table query runs with no ALS context) so misses surface in logs immediately.

## 4. Policy generator

`scripts/generate-rls-policies.mjs`: reads `information_schema.columns` for `column_name='organizationId'` (same introspection used by the tenant-inventory work), emits idempotent `enable-batch-N.sql` / `disable-batch-N.sql` with the §3.D1 policy per table. Excludes: global tables, `_prisma_migrations`. Checked into `scripts/rls/`.

## 5. Bypass inventory (the load-bearing list)

Every cross-tenant surface is **explicitly classified** (mirror of the module-catalog totality discipline):

| Surface | Classification |
|---|---|
| `src/lib/auth.ts` login lookups (pre-org) | `runWithRlsBypass` around the 3 user lookups |
| `requireSuperAdmin` API + `/admin/*` server pages | bypass entered by the guard after role check |
| 34 × `/api/cron/*` | bypass entered by the shared cron-auth helper (single choke point if one exists — else per-route, enumerated in the plan) |
| 46 × scripts | `scripts/_rls.mjs` helper (D3) |
| Webhooks (WhatsApp/social/email inbound) | bypass for the org-resolution lookup, then `runWithTenant(resolvedOrgId)` for the rest of the handler |
| **`src/instrumentation.ts:57,166` background `setInterval` cron loops** (Finance deadline checker, MTM auto-checkout — each holds its OWN `new PrismaClient`, neither an HTTP cron nor a script; architect fix #3) | own clients also get the extension (import the shared factory) + `runWithRlsBypass` around each tick |
| **7 public RSC pages** that resolve org from a public token/slug with no auth context (`/s/[slug]` surveys, `/f/[slug]` forms, `/(public)/p/[slug]`, `/c/[token]` contracts, `/embed/chat/[key]`, `/s/unsubscribe`, `/(public)/_custom-domain`; architect fix #3) | bypass for the token→org lookup, then `runWithTenant(resolvedOrgId)` for the page render |
| Tenant export / purge / provisioning | bypass (superadmin-gated already) |

## 6. Testing & CI guards

- **Unit:** extension behavior (context → set_config emitted; no context → pass-through + dev warning; bypass var set only via helpers).
- **CI classification test (totality-style):** enumerate `/api/cron/*` routes + admin pages + `scripts/*.{mjs,ts}` with `new PrismaClient` + **every `new PrismaClient` outside `src/lib/prisma.ts` (catches `instrumentation.ts` timers)** + **public RSC pages (route groups `(public)`, `/s/`, `/f/`, `/c/`, `/embed/` that import prisma)** → each must be classified (cron-guard / `_rls.mjs` import / `runWithTenant`-or-`runWithRlsBypass` present / explicit allowlist) — unclassified = CI fail. This is the guarantee the bypass inventory never silently rots (architect fix #3: the classifier's universe must include the timer and public-page categories from day one).
- **Integration (real Postgres):** scratch DB on the server (or docker PG locally) — apply policies to 2 sample tables, prove: tenant A cannot read B (even with a deliberately unscoped raw query); no-context = empty; bypass sees all; owner WITHOUT `FORCE` would leak (regression-proves why FORCE is there).
- **E2E:** demo tenants (mars/afigroup) on the shared box after each rollout batch — login, sidebar, CRUD per module, notifications, exports, one cron manually triggered.

## 7. Risks → closures

| Risk | Closure |
|---|---|
| Missed context → empty screens | Fail-closed by design (no leak) + dev-mode warning + batch rollout on demo tenants + full suite |
| Cron/script silently broken | §5 inventory + §6 CI classification test + manual cron trigger in E2E |
| Bypass var abused by future code | Only settable via 2 helpers; CI classification + code review; revisit two-role split (D1 alternative) if audit requires |
| Interactive-tx overhead per query | Negligible at current traffic (57 MB DB); load smoke in the plan; revisit pooling only if metrics say so |
| Prod surprise | Phase-1 plumbing is a no-op; per-table instant `DISABLE` rollback; batches with smoke between |
| `set_config` + pool affinity | Solved structurally: `is_local=true` inside the wrapping transaction (D2); scripts pin `connection_limit=1` (D3) |

## 9. Confidence (decision-stress-test)

- **Contrarian:** "ALS + extension is magic — explicit per-route clients are clearer." → Rejected: 478 route edits is exactly the migration-surface that produces misses; one choke point + CI guard beats 478 manual edits.
- **First-principles:** isolation belongs at the lowest layer that can express it; the tenant key already exists on every row; policies express it 1:1.
- **Reality:** zero live clients = cheapest window; rollback is per-table and instant; fail mode is closed.
- **Named security boundary (honest framing, architect fix #4):** the session-var bypass is settable by ANY SQL running on the same connection — so this design defends against **application-logic bugs** (the forgotten `where organizationId` class), **NOT against SQL injection** (an injection that executes `set_config('app.rls_bypass','on')` defeats it). That is exactly the "defense-in-depth, not replacement" claim of §1: the app-level layers (parameterized Prisma queries, requireAuth, JWT binding, per-tenant KEK) remain the injection defense. If an auditor requires injection-resistant isolation, the upgrade path is D1's rejected alternative (two DB roles, `BYPASSRLS` granted only to the admin role).
- **Confidence: Medium-High.** The plumbing pattern (ALS + `$extends` + `set_config`) is the documented Prisma RLS approach; the genuinely new surfaces are the bypass inventory (guarded by the CI classification test) and the tx-open wrap for the 125 interactive transactions (unit-tested per D2). Codex second opinion recommended at plan stage on the extension/transaction mechanics (same discipline as module-catalog).
