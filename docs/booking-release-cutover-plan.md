## Два артефакта

| Этап | Поведение | Допустимый откат |
| --- | --- | --- |
| A, compatibility | Вся новая серверная модель и API; прежний редактор ссылок для администратора; новый workspace скрыт | Старый writer — только после остановки процесса и доказательства, что canonical данных ещё нет; иначе A/B |
| B, workspace | Согласованный интерфейс и однократное включение строгого режима | Точный проверенный A, сохраняющий весь новый контракт API, историю и эффекты |

A и B используют одинаковые Prisma schema/migrations и backend. В B меняется
immutable release phase. Переключение не требует второй схемы, переписывания
миграций или нового профиля структуры БД. Production применяет миграции только
из main; после применения их SQL больше не редактируется.

## Что защищает расширение A

- Версия Booking=0 обозначает никогда не канонизированную legacy запись. До B
  такой старый writer остаётся совместимым с расширенной схемой. Все новые
  публичные/служебные команды A сразу создают согласованные положительные
  Booking/event/head версии.
- Положительную версию нельзя вернуть в 0, переписать канонические факты без
  нового события или редактировать принадлежащий ей Task обычным writer.
- Старые редакторы страниц автоматически увеличивают page.version при изменении
  правил. Поздний старый PATCH не обходит проверку свежести. Старый INSERT
  Booking получает известный текущий buffer страницы вместо нулевого default;
  это derived legacy metadata, не восстановленная историческая конфигурация.
- Snapshot старой записи и история не придумываются. Первое новое действие
  атомарно импортирует известное состояние и добавляет настоящий новый event.

## Однократное включение B

Таблица `booking_workspace_release` хранит один глобальный служебный бит,
первый activation artifact SHA и время. Это metadata общей выкладки, не данные
клиента. Web role может читать режим, но не менять его. RLS и ограничения
закрывают INSERT/UPDATE/DELETE/TRUNCATE; обычные mutation права не выдаются.
Migration authority может включить режим один раз; UPDATE назад, DELETE и
TRUNCATE запрещены trigger. Отсутствующий режим не открывает legacy writer.

После подтверждения точного A artifact и применения миграций protected deploy
исполняет `scripts/booking/activate-workspace.sql` через migration identity.
Транзакция дренирует Booking/Task writers блокировками, привязывает активацию к
SHA кандидата и проверяется новым read-only соединением. Повтор — no-op.
Только потом начинается обычная смена процесса. A понимает этот строгий режим:
возврат A сохраняет новые данные и работу API, интерфейс временно возвращается
к прежнему состоянию. Флаг в БД остаётся включённым.

## Admission и автоматический откат

Marker `.booking-backend-contract.json` привязан к artifact SHA и хешу моделей
Booking. Он дополняет реальные CI проверки, а не заменяет их. Включение UI
требует canonical-capable predecessor с тем же storage contract. Доказывается
совместимость backend A с реально включённым B: полный PostgreSQL suite и
production build. Наличие одного JSON marker без этих проверок недостаточно.

Ручной retained recovery проверяется current-main кодом **до SCP**. Helper
сохраняется вне исторического checkout. Pre-A artifact после расширения схемы
не допускается даже при нулевом числе canonical строк: иначе между проверкой
и заменой процесса могла бы появиться новая запись. Операционные процедуры
используют current-main dispatch; старые workflow reruns не являются маршрутом.

Внутренний ранний rollback A допускает legacy только в доказанном pre-canonical
окне. Сначала удаляются процессы/сохраняется пустой PM2 reboot dump; затем
ожидается завершение всех Booking table writers. После этого читается **новый
READ COMMITTED snapshot**. Одного завершения Node PID и одной проверки count
недостаточно: PostgreSQL ещё может завершать COMMIT. Поздний canonical commit
запрещает legacy rollback. Тот же пустой reboot dump сохраняется перед первым
стартом A, чтобы сбой до pm2 save не воскресил старый writer.

Если доказательство получить нельзя, candidate и данные сохраняются, старый
writer не запускается. Возможна временная недоступность до совместимого
восстановления; это явное ограничение первого расширения. База не восстанавливается
из старого dump как обычный откат приложения, события не удаляются, guards не
отключаются. Отдельный recovery-point/commissioning контур проекта не ослаблен.

## Последовательность и доказательства

1. Проверить source A: пять required checks, production build, Node admission/
   recovery tests и настоящий PostgreSQL suite. Локально тяжёлые gates не идут.
2. Обновить inventory через protected Actions, сверить текущие main/deployed SHA.
3. Выпустить A штатным main → immutable artifact → deploy маршрутом; убедиться
   в финальном SUCCESS, ping и точном public build-info. Сохранить SHA и run ID
   неизменяемого A artifact. Не включать B при неуспешной A поставке.
4. Проверить source B с тем же backend/storage contract и активированным B mode.
5. Выпустить B по тому же маршруту. Проверить положительный activation receipt,
   неизменность данных, ping, assets, public booking read и ACL отказ без сессии.
6. Реальные booking/Google/email/push записи не создавать как побочный smoke;
   их атомарность и unknown/retry сценарии проверяются на hosted synthetic DB.

Завершение I-05 требует не только кода, но и фактического проверенного A artifact
перед включением B. Текущие результаты и точка остановки — в append-only
`docs/booking-workspace-session-log.md`. Historical исходный аудит остаётся в
истории; непроведённый production fault injection не обозначается как PASS.
