# Встречи: безопасная последовательность выпуска

Дата: 2026-10-24. Это план выпуска и критерии приёмки; контроллер переключения
ещё не реализован. Документ не делает feature PR #1023 готовым к production.

## Почему одного обычного деплоя недостаточно

Feature source `91dd1edc2a3fbe889e42ecc1477760dcdeb645fa` добавляет deferred
проверку Booking/event/head. Старый writer создаёт Booking с version=0 без
событий, поэтому после этой миграции его запись отвергается. Старый main не
понимает новые состояния completed/no_show. Стандартный server-deploy сначала
применяет миграции и затем меняет процесс; его откат на предыдущий артефакт
сам по себе совместимость не доказывает.

Не допускаются удаление новых событий/записей, снятие guard после активации,
возврат старого writer поверх canonical данных или восстановление старого dump
как обычный откат приложения. Последнее потеряло бы уже принятые записи.

## Отдельный шаг: read-only инвентаризация

PR с inspector не содержит feature-кода, Prisma изменений или новой установки
cron. Его можно проверить и принять отдельно от #1023. Workflow
`booking-release-preflight.yml` допускает доступ к production только через
ручной dispatch из точного current main и существующее protected environment,
серверный SSH pin и ключ Actions. Никаких ключей не переносится на Contabo.

Два SHA имеют разный смысл: `expected_main_sha` фиксирует reviewed inspector,
`expected_artifact_sha` фиксирует уже работающий production. Инструмент читает
маркер артефакта на сервере; SHA берётся из public build-info перед dispatch.
Не требуется выкладывать новую версию приложения только для чтения старой БД.

Запрос выполняется в READ ONLY, с read-only по умолчанию на соединении,
statement_timeout=30s, lock_timeout=3s и внешним timeout. Сохраняются только
allowlisted счётчики и признаки доступности btree_gist. Ошибки транспорта/SQL,
tenant IDs, контакты и строки Booking в артефакт не попадают. Инструмент не
вызывает провайдеров, не устанавливает расширение и не чинит старые данные.

`PASS_INVENTORY_ONLY` означает только отсутствие найденных конфликтов для
проверяемых ограничений. Это не одобрение миграции или доказательство отката.
Отсутствующие legacy Task/Lead фиксируются отдельно: их нельзя создавать заново
без проверки, иначе получится дублирование. Конфликтующие host/page, повторный
Task, неверные интервалы и пересечения confirmed блокируют дальнейший выпуск.
Доступность расширения/CREATE — предварительная проверка; само выполнение DDL
должно быть доказано точной migration identity в проверенном сценарии.

## Два выпуска вместо несовместимого отката

| Этап | Что допускается | Что является откатом |
| --- | --- | --- |
| A: серверная совместимость | Аддитивная схема и canonical backend под закрытой записью; новый раздел, новые действия и статусы пока недоступны | До первого canonical write — старый артефакт при сохранённом запрете записи; после активации — только совместимая версия A |
| B: включение рабочего места | Проверенная версия A уже работает; устанавливаются строгие guards и включается согласованный UI | Точный immutable артефакт A, который понимает новые статусы, version/head, команды и effects |

Этап A — отдельный будущий reviewed PR, а не существующий main. Он должен
содержать весь backend, необходимый для чтения и записи новой схемы, событий,
команд и effect outbox, но не давать раннего доступа к outcome/reassign и новому
UI. Схема и установка guards должны быть разделены до первого production
применения этих миграций. Уже применённые миграции не переписываются.

Сначала закрываются все каналы записи Booking, включая public create/cancel,
служебные команды, фоновые writers и изменение принадлежащих Booking Task.
Закрытие должно переживать рестарт/ошибку deploy и выдавать явный retryable
maintenance ответ, а не ложное подтверждение записи. Затем дренируются старые
запросы и доказанно отсутствуют старые процессы/DB-транзакции. Только потом
выполняются миграции и меняется процесс. Нужен отдельный durable journal
состояния переключения; наличие одного env flag в новом приложении недостаточно,
так как старое приложение его не читает.

На первом запуске A запись остаётся закрытой до успешной проверки артефакта,
readiness и сценариев create/replay/cancel/worker. В случае сбоя до открытия
восстанавливается прежний процесс, запрет записи сохраняется до проверки
совместимости. После открытия canonical записи нельзя автоматически возвращать
pre-A writer. Это ограничение должно исполняться и в автоматическом rollback,
и в workflow recovery_sha, до замены live артефакта.

Перед B точный предыдущий артефакт A проверяется на мигрированной копии данных:
создание, перенос, отмена, completed/no_show, CAS, повтор запроса и эффекты.
Проверяется также его фактический Prisma client. Hash/имя marker без этих тестов
совместимость не доказывает. После B rollback A сохраняет запись и историю;
интерфейс можно временно отключить, canonical backend продолжает работать.

## Обязательные доказательства перед GO

1. Read-only inventory с привязкой source/deployed SHA и фактическими счётчиками.
2. Восстановленная из свежего recovery point изолированная БД и миграция на ней;
   проверены фактическая migration identity, ограничения и сохранение данных.
3. Hosted integration test смешанного окна old → A и A → B: дренирование,
   старые вкладки, повтор после timeout, падение до/после migration commit.
4. Совместимость exact A artifact после B, включая новые статусы и cron эффекты;
   запрет pre-A recovery после canonical write.
5. Проверки durable fence/journal при SIGTERM/ошибке и неуспешной readiness;
   невозможно оставить старый writer открытым с новой строгой схемой.
6. Пять обязательных GitHub checks, production build и согласование краткого
   списка пользовательских изменений перед B по DELIVERY-ARCHITECTURE.md.
7. После каждого разрешённого Actions deploy: ping, exact build-info SHA и
   feature smoke. Реальные email/Google/push не отправлять как побочный тест.
