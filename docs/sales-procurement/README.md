## 2. Правила, которые нельзя нарушать

1. **Закупки — свой модуль `procurement`, по умолчанию выключен.** Пока он
   выключен у организации, в продукте не меняется ничего: ни пункта меню, ни
   вкладки в сделке, ни поля в ответах. Образец выделения модуля — «Встречи»
   (#1519, `BOOKING_MODULE_ID` в `src/lib/modules.ts`), но без бэкфилла: новый
   модуль никому не включается миграцией.
2. **Это закупка под заказ, а не система закупок.** В CRM: поставщики, заявка из
   сделки, предложения и сравнение, PO с согласованием, статусы до «принято»,
   сроки, маржа. **Не в CRM:** тендеры, аукционы, кабинет поставщика, бюджеты,
   сверка счёта с заказом и приёмкой — это LeadProcure. Не копировать код
   LeadProcure: другой стек; брать только правила (§3.6).
3. **Склад и бухгалтерию не трогать.** Справочник контрагентов (карточка ERP 013),
   «Поступление» (015) и проводки по входящим счетам (024) — процесс карточек
   `python3 scripts/erp/next_card.py`. Складская заготовка (`Warehouse`,
   `InventoryItem`, `StockMovement`) будет удалена карточкой 006 — на ней не
   строить. «Принято» в закупках — статус заказа поставщику, без движения товара.
4. **Деньги — `Decimal(18,4)`**, как `Bill`, `Invoice`, `Quote`. Не Float.
5. **Закупочные цены, себестоимость и маржу видят руководство и финансы.**
   Продажи видят статусы, сроки и поставщика без цен (решение по умолчанию §6.5).
6. **Согласование PO не делается ключом API** — как `finance`: scope закупок не
   входит в `MODULES`. Автор не согласует свой PO.
7. **Общие правила CRM**: RLS на каждой новой таблице (`tenant_isolation`,
   `find-context-gaps.py` = 0), маршруты через `withRlsAuth`, файлы клиента
   запечатаны ключом организации, переводы en/ru/az, `logAudit` на каждом
   изменении, тесты поведения на настоящем Postgres гейтом в `static-checks` и в
   деплое. См. `CLAUDE.md`.

## 4. Как это устроено

- **Заказ клиента — это сделка.** Отдельной модели заказа нет. Закупка ссылается
  на сделку и на конкретную строку сделки.
- Поток: строки сделки → «Запросить закупку» → **заявка** (ссылки на сделку и
  строки, нужна к дате, файлы сделки) → **предложения поставщиков** → выбор →
  **PO** → согласование по сумме → отправлен → производство → доставка → принято
  (по позициям).
- **Сделка** показывает вкладку «Закупки»: заявки и PO, статус каждой строки
  заказа, общий статус («готово 2 из 3, ждём баннер до 25.11»), красная метка
  при опоздании.
- **Изменение в сделке** (клиент согласовал новый размер, количество, макет)
  записывается в журнал согласований; связанные заявки и открытые PO получают
  пометку «изменено в сделке — проверь», закупщику — уведомление. Отправленный
  PO сам не меняется.
- **Себестоимость заказа** = сумма согласованных PO по его строкам; **маржа** =
  выручка строк сделки − себестоимость.

### Этап 3. Заявка, предложения, PO
- **3.1 Заявка на закупку** (`PurchaseRequest` + строки, ссылки на сделку и
  `DealLineItem`). Кнопка «Запросить закупку» в сделке: строки берутся из

  *Готово, когда:* заявка из сделки создаётся одним действием и видна закупщику.
- **3.2 Предложения поставщиков** (`SupplierQuote` + строки): цена, срок поставки,
  условия, файл предложения. Таблица сравнения по строкам (лучшая цена и срок
  выделены), выбор победителя по всей заявке или по строке.
  *Готово, когда:* три предложения сравниваются в одной таблице, выбор
  сохраняется с автором.
- **3.3 PO** (`PurchaseOrder` + строки, Decimal) из выбранного предложения или
  вручную; номер по шаблону организации; PDF (az/ru); отправка поставщику по
  e-mail с PDF; правки после отправки — новой редакцией с историей.
  *Готово, когда:* PDF открывается, письмо уходит, правка отправленного PO видна
  в истории.
- **3.4 Согласование по лимитам.** Правила «от X до Y — роли/люди по порядку»
  на экране настроек закупок; движок — чистые функции из
  `src/lib/contract-lifecycle/` (`evaluateRuleConditions`, `routeApproval`);
  свои таблицы ступеней PO. Автор не согласует (`isOwnOrderToApprove`-правило);
  отказ с причиной; делегирование на время отсутствия — через
  `UserApprovalDelegate`, если подходит.
  *Готово, когда:* PO на сумму выше порога требует двух ступеней, автор свою не
  проходит, гонка двух согласующих не даёт двойного перехода (тест на Postgres).
- **3.5 Статусы и история.** черновик → на согласовании → согласован →
  отправлен → в производстве → в пути → принят частично → принят; отменён.
  Таблица переходов (кто, когда, откуда, куда); приёмка по позициям с
  количеством и датой.
  *Готово, когда:* недопустимый переход — 409, история полная.
- **3.6 Сроки и опоздания.** Ожидаемая дата у PO и строки, сдвиг поставщиком с

  `cron-dispatch`, фаза не `*/5`).
  *Готово, когда:* PO с прошедшей датой без приёмки помечен и уведомление ушло
  один раз.
