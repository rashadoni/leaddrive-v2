# Как изменения доезжают до клиентов

## Возврат в GitHub — подготовлен 9 сентября 2026

Владелец решил перенести репозиторий и обычные Linux-проверки в новый публичный
GitHub. Переключение считается завершённым только после проверки всей публичной
истории на секреты, зелёного PR и одной подтверждённой production-выкладки.
До этого Azure и Contabo остаются временным мостом, но один SHA нельзя гонять
одновременно в двух CI-системах. Полная старая история остаётся в приватном
Azure-архиве: публичный GitHub начинается с проверенного чистого snapshot,
поскольку в прежних коммитах обнаружены чувствительные данные.

Платные GitHub-hosted macOS runners запрещены исполняемой политикой
`scripts/ci/check-github-runner-policy.mjs`. Обычные проверки идут на
GitHub-hosted Linux. Реальная нативная macOS/iOS-проверка, если она нужна,
исполняется только на физическом Mac владельца с метками
`[self-hosted, macOS, ARM64, leaddrive-mac-local]`.

После контрольной выкладки выключаются только CI-агенты и очереди Contabo/Azure.
Сайты, базы данных, бэкапы, DNS и другие постоянные сервисы этим решением не
затрагиваются.

### Временный Azure-мост

Репозиторий и PR переходного периода находятся в Azure DevOps: организация
`rashadrahimov`, проект и репозиторий `leaddrive-v2`. Его инструкции описаны в
`ops/azure/README.md` и действуют до подтверждённого переключения.

В Azure действуют две обязательные проверки PR: независимое `leaddrive-agent-review`
и `leaddrive-checks`. Вторая запускает классификацию для каждого PR, но для чистой
документации завершает её без тяжёлых тестов. Поэтому документация не ждёт
несуществующий check. Для применимых изменений сохраняются static/typecheck,
проверки базы и браузерная проверка Social Monitoring.

После merge только `main` запускает `leaddrive-release-build`. Успех этой сборки
запускает отдельный `leaddrive-production`. Он проверяет версию конвейера,
источник архива, SHA и актуальность `main`, затем выполняет прежнюю атомарную
выкладку с резервной копией, проверкой здоровья и откатом. Временный общий
сборочный сервер исполняет по одной тяжёлой работе в изолированном контейнере.
Ключ продакшена находится только в отдельном конвейере Azure на временной машине.

Пока первый полный цикл не завершён, это настройка нового пути, а не доказательство
его работоспособности. Завершение подтверждается успешным production run и
совпадением SHA из `/api/v1/public/build-info`.

Четыре слоя. Каждый ловит то, что пропустил предыдущий. Действует одинаково для
всех сессий: Claude, Codex, любых будущих. Ссылки на этот файл стоят в
`AGENTS.md` и `CLAUDE.md`, и он главнее их обоих в том, что касается порядка
доставки.

Владелец работает один и не читает диффы. Конструкция построена так, чтобы от
него требовалось ровно две вещи: один раз добавить ключ и перед релизом
ответить «давай» на короткий список. Всё остальное делают машина и агенты.

## Зачем это появилось

6 сентября 2026 года в `main` за день влилось восемь PR под именем владельца.
Четыре из них он не открывал: переезд CI, изменение самого деплоя и фича
`personalized welcome experience` на главной, которую никто не заказывал. У
ветки `main` не было никакой защиты. В тот же день сверка показала, что три
задачи из семнадцати, числившихся сделанными, были сделаны целиком, а в моей
собственной работе с зелёными тестами нашлось пять дефектов, включая потерю
отметки о визите в офлайне.

Вывод простой: зелёные тесты означают «то, о чём подумал автор, работает». Они
ничего не говорят о том, о чём автор забыл, и тем более о том, нужна ли эта
работа вообще.

## Слой 1. В `main` только через pull request

Прямой пуш в `main` запрещён правилом репозитория. Любое изменение проходит
через PR. Обязательная проверка ровно одна — `agent-review`, потому что она
запускается всегда, включая PR только с документацией. Тяжёлые проверки
(`static-checks`, `typecheck`) остаются с фильтрами по путям и обязательными не
делаются: иначе PR с одной правкой в тексте висел бы вечно, ожидая проверку,
которая для него не стартует.

Настраивается не руками, а скриптом `scripts/ci/configure-main-protection.sh` —
он же переносит правило на остальные репозитории. Это прямое следствие первого
же разбора по слою 2: агент указал, что контроль, который только описан, не
контроль, и был прав.

Одобрения ревьюера здесь намеренно не требуются. Владелец работает один, и
правило, которое некому выполнить, — это ровно то, из-за чего прод стал
недостижимым.

`enforce_admins` оставлен выключенным осознанно: когда ломается сама проверка,
у владельца должен остаться путь починить прод. Это аварийный выход, а не
рабочая дверь, и каждый его случай стоит называть вслух в отчёте.

Ловит: попадание кода в основную ветку вообще без проверок.

## Слой 2. PR разбирает агент, который его не писал

`.github/workflows/agent-review.yml` на каждом PR даёт диф отдельному агенту.
У него нет заинтересованности в этом коде: он не выбирал решение и не устал его
защищать. Он сверяет изменение с тем, что задача требовала, и ищет дефекты.

Найдено что-то настоящее — проверка красная, смержить нельзя.

Важное правило, чтобы слой не превратился в шум: агент сообщает только то, что
может сломаться у пользователя или в проде. Замечания вида «здесь можно было
короче» в блокирующий вывод не попадают.

Есть два случая, когда разбор не состоится: нет `ANTHROPIC_API_KEY` и сбой
самого API. В обоих проверка проходит, а не падает — иначе один плохой час у
провайдера остановил бы всю доставку, то есть повторил бы ровно ту беду, ради
которой всё это построено.

Но молчания при этом нет. В обоих случаях в PR пишется прямым текстом, что
изменение **никто не разобрал**, и мерж после такого — решение, которое кто-то
принял, а не то, что проскользнуло само. Если этот случай повторяется, значит
слой не работает, и это повод чинить, а не привыкать.

Ловит: дефекты, которые тесты не проверяют, потому что тест написан тем же, кто
ошибся.

## Слой 3. Прод

Уже построено и менять не нужно: выкатка только из `main`, атомарная подмена
версии, проверка здоровья, автоматический откат, гейт по резервным копиям,
привязка SSH-хоста.

Одно исключение, снятое осознанно 6 сентября 2026: требование независимого
человека-ревьюера у окружения `production`. На тарифе GitHub Pro для приватного
репозитория такой настройки не существует — она доступна только в Enterprise, —
поэтому проверка не защищала, а делала выкатку невозможной. Замена ей — слой 2:
разбирает не человек, а агент. Проверка «деплой только из `main`» осталась.

Ловит: сломанную сборку, которая иначе заменила бы работающий сайт.

## Слой 4. Слово владельца

Единственное, чего машина не может. Фича на главной была написана корректно,
тесты бы прошли, ревью бы её пропустило. «Я такого не заказывал» — суждение,
доступное только владельцу.

Поэтому **перед мержем** агент показывает короткий список: что именно поедет
клиентам, по одной строке на изменение, человеческим языком, без имён файлов и
кода. Владелец отвечает «давай» или «это убрать». После «давай» всё дальше
происходит само: мерж, сборка, выкатка, проверка.

Список нужен только для того, что увидит пользователь. Правки тестов,
документации и внутренних скриптов в него не попадают.

Ловит: сделано аккуратно, но не то.

## Что обязан делать любой агент

1. Не пушить в `main`. Только PR.
2. Не мержить красное и не ослаблять проверку, чтобы пройти. Гейт, который
   кажется неправильным, оставить стоять и сказать об этом.
3. Не мержить, пока `agent-review` не зелёный.
4. Перед мержем того, что видит пользователь, показать владельцу список из
   слоя 4 и дождаться «давай».
5. Своё же ревью не считается. Если разбираешь собственный PR, поручай разбор
   отдельному агенту.

## Что делает владелец

Один раз: добавляет `ANTHROPIC_API_KEY` в секреты репозитория.

Дальше: отвечает «давай» на список перед релизом. Всё.
