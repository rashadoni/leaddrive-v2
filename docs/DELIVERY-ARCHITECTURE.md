# Как изменения доезжают до клиентов

## GitHub production route — подтверждён 26 сентября 2026

Единственный действующий репозиторий — `rashadoni/leaddrive-v2`. Изменения
попадают в production только через pull request в `main`, обязательные проверки
GitHub и `.github/workflows/deploy.yml`. Workflow собирает SHA-привязанный
артефакт и атомарно выкладывает его на зарегистрированный Contabo host
`13.140.132.245` в `/opt/leaddrive-v2`. После каждой выкладки `/api/v1/ping`
должен отвечать успешно, а `artifactSha` из `/api/v1/public/build-info` — точно
совпадать с merge SHA в `main`.

Azure, прежний владелец GitHub, старые production-хосты и прямое копирование
worktree не являются резервными маршрутами. Их нельзя использовать даже при
сбое обязательной проверки: сначала исправляется сама проверка в отдельном PR.

Платные GitHub-hosted macOS runners запрещены исполняемой политикой
`scripts/ci/check-github-runner-policy.mjs`. Обычные проверки идут на
GitHub-hosted Linux. Реальная нативная macOS/iOS-проверка, если она нужна,
исполняется только на физическом Mac владельца с метками
`[self-hosted, macOS, ARM64, leaddrive-mac-local]`.

Четыре слоя. Каждый ловит то, что пропустил предыдущий. Действует одинаково для
всех сессий: Claude, Codex, любых будущих. Ссылки на этот файл стоят в
`AGENTS.md` и `CLAUDE.md`, и он главнее их обоих в том, что касается порядка
доставки.

Владелец работает один и не читает диффы. Конструкция построена так, чтобы перед
пользовательским релизом от него требовалось только ответить «давай» на короткий
список. Всё остальное делают машина и агенты.

## Зачем это появилось

6 сентября 2026 года в `main` за день влилось восемь PR под именем владельца.
Четыре из них он не открывал: переезд CI, изменение самого деплоя и фича
`personalized welcome experience` на главной, которую никто не заказывал. У
ветки `main` не было никакой защиты. В тот же день сверка показала, что три
задачи из семнадцати, числившихся сделанными, были сделаны целиком, а в моей
собственной работе с зелёными тестами нашлось пять дефектов, включая потерю
отметки о визите в офлайне.

Вывод простой: зелёные тесты означают «то, о чём подумал автор, работает». Они
ничего не говорят о том, о чём автор забыл, и тем более о том, нужна ли эта
работа вообще.

## Слой 1. В `main` только через pull request

Прямой пуш в `main` запрещён правилом репозитория. Любое изменение проходит
через PR. Обязательных проверок пять, и все их запускает сам GitHub на каждом
PR: `pr-scope`, `static-checks`, `typecheck`, `runner-policy`, `scan`.

Каждая обязана появляться на любом PR, иначе PR вне её путей висел бы вечно,
ожидая проверку, которая для него не стартует. Поэтому `pr-checks.yml` идёт без
фильтров по путям, а тяжёлые `static-checks` и `typecheck` пропускаются через
джобу `pr-scope`, если PR — только документация: пропуск засчитывается как
успех. Сам `pr-scope` тоже обязателен — упавший детектор пропустил бы
зависимые джобы, и пропуск открыл бы `main` для любого кода.

До 2026-09-11 обязательной была одна `agent-review` — именно из-за фильтров по
путям на тяжёлых проверках. См. слой 2.

Настраивается не руками, а скриптом `scripts/ci/configure-main-protection.sh` —
он же переносит правило на остальные репозитории. Это прямое следствие первого
же разбора по слою 2: агент указал, что контроль, который только описан, не
контроль, и был прав.

Скрипт привязывает пять проверок к GitHub Actions app (статус с тем же именем
от кого-то другого их не заменит) и после записи перечитывает правило. Он
завершается ошибкой, если набор контекстов, их app bindings, `enforce_admins`,
PR-only rule, запреты force-push или удаления отличаются от контракта — в том
числе если в обязательных снова оказалась `agent-review`. Запускать его только
из актуального `main`: старые worktree несут версию с `agent-review`.

Одобрения ревьюера здесь намеренно не требуются. Владелец работает один, и
правило, которое некому выполнить, — это ровно то, из-за чего прод стал
недостижимым.

`enforce_admins` включён: администратор не может обойти те же пять проверок.
Сломанная проверка исправляется обычным reviewable PR; обход защиты не является
допустимым аварийным маршрутом.

Ловит: попадание кода в основную ветку вообще без проверок.

## Слой 2. Проверки GitHub (с 2026-09-11)

Каждый PR проходит тесты против базлайна, оба блокирующих гейта тайпчека,
политику раннеров и gitleaks — это обязательные проверки из слоя 1. ИИ-ревьюера
в гейте нет.

**Почему `agent-review` снят.** Он давал диф отдельному агенту через API
Anthropic и был единственной обязательной проверкой. Без `ANTHROPIC_API_KEY`
он по замыслу проходил зелёным, чтобы не останавливать доставку, — и владелец
2026-09-09 решил ключ не заводить. Итог: гейт `main` пропускал всё, а тесты и
тайпчек обязательными не были вовсе. 2026-09-11 владелец снял его: проверку
завели, когда на старом аккаунте искали, как сэкономить, а теперь «гит
проверяет сам».

**Почему он не вернулся 2026-09-26.** В тот день его восстановили в новом виде
(#439/#440): статус `agent-review` для точного SHA публикует агент, который не
писал изменение. Публиковать было некому — он встал на каждом PR всех сессий.
Владелец в тот же день снял его снова: «убери эту проверку с ИИ… удали её, чтоб
для других сессий также не выскакивала». Не возвращать ни в каком виде: ни
платного ИИ-ревьюера в CI, ни статуса, который должна публиковать другая сессия.

Чего это не ловит — и не ловило раньше: дефекты, которые тест не видит, потому
что тест написан тем же, кто ошибся. 2026-09-09 в #14 зелёными были все
проверки, включая свой же тест: он проверял форму запроса, а не поведение.
Защита от этого — тест на поведение на реальных данных, а не на форму вызова.

## Слой 3. Прод

Уже построено и менять не нужно: выкатка только из `main`, атомарная подмена
версии, проверка здоровья, автоматический откат, гейт по резервным копиям,
привязка SSH-хоста.

Одно исключение, снятое осознанно 6 сентября 2026: требование независимого
человека-ревьюера у окружения `production`. В solo-owner репозитории нет второй
независимой человеческой identity, способной одобрить deploy при запрещённом
self-review, поэтому правило не защищало, а делало выкатку невозможной.
Environment по-прежнему допускает deploy только из `main`.

Ловит: сломанную сборку, которая иначе заменила бы работающий сайт.

## Слой 4. Слово владельца

Единственное, чего машина не может. Фича на главной была написана корректно,
тесты бы прошли, ревью бы её пропустило. «Я такого не заказывал» — суждение,
доступное только владельцу.

Поэтому **перед мержем** агент показывает короткий список: что именно поедет
клиентам, по одной строке на изменение, человеческим языком, без имён файлов и
кода. Владелец отвечает «давай» или «это убрать». После «давай» всё дальше
происходит само: мерж, сборка, выкатка, проверка.

Список нужен только для того, что увидит пользователь. Правки тестов,
документации и внутренних скриптов в него не попадают.

Ловит: сделано аккуратно, но не то.

## Что обязан делать любой агент

1. Не пушить в `main`. Только PR.
2. Не мержить красное и не ослаблять проверку, чтобы пройти. Гейт, который
   кажется неправильным, оставить стоять и сказать об этом.
3. Не мержить, пока пять обязательных проверок не зелёные.
4. Перед мержем того, что видит пользователь, показать владельцу список из
   слоя 4 и дождаться «давай».
5. Добавляешь обязательную проверку — сделай так, чтобы она появлялась на
   каждом PR (без фильтра по путям), иначе PR вне её путей повиснет навсегда.

## Что делает владелец

Отвечает «давай» на список перед релизом. Всё.
