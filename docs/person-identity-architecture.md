# Единая учётная запись и независимые приложения

Дата: 24 октября 2026. Статус: архитектура → аудит → самокритика → итоговое решение → проверенный неактивный foundation (этапы0–1). Текущая авторизация и регистрация ещё не переключены.

Основание: владелец принял «один человек — одна учётная запись и номер; Time и Route & Field включаются отдельно». Попросил сначала спроектировать, проверить, критически пересмотреть, показать итог и затем начать работу. Область уникальности — одна компания, не все клиенты SaaS. Номер не является доказательством юридической личности.

## 1. Исходная архитектура, вариант A

Использовать существующую учётную запись User как идентификатор человека внутри компании. Не создавать глобальный каталог физических лиц. У неё отдельные разрешения CRM, Time, Route & Field. Номер для входа и учётные данные принадлежат этой записи. Рабочие карточки используют её идентификатор; не содержат независимые копии данных для входа.

Начальная гипотеза: достаточно унифицировать номер и добавить два переключателя приложений, оставив существующие роли и рабочие дни. Аудит ниже проверяет эту гипотезу, а не выдаёт её за готовый проект.

## 3. Самокритика варианта A

1. **Два переключателя поверх прежней роли недостаточны.** Роль определяет и полевой доступ, и исключение из табеля. Исправление: отдельные права приложений и кадровое членство, без вывода из роли CRM/агента.
2. **User не должен означать доступ к CRM.** Создание User агенту может открыть CRM или изменить тарификацию. Исправление: запись личности отдельно от разрешения CRM; мобильная учётка по умолчанию не может войти в CRM. Существующую оплату не менять скрытно: до миграции сверить расчёт мест, сохранять текущие начисления, изменение тарифа — отдельная задача.
3. **Копирование phone между таблицами не создаёт единственный источник.** Появятся гонки, импорты и обходные формы. Исправление: каноническое назначение номера, все входы и записи проходят один сервис; legacy-поля лишь переходные проекции, не fallback владельца после переключения.
4. **Склеивать по телефону/email опасно.** Один номер мог быть общим, ошибочным или перевыпущенным. Исправление: существующая явная связь userId — кандидат для проверки; совпадение контакта только конфликт, никогда автоматическое объединение.
5. **Одна учётка не означает один рабочий день двух приложений.** Полевой сеанс может закрыть табель. Исправление: отдельный полевой сеанс и кадровая отметка, связанные с человеком, с явно определённой сервером областью событий.
6. **Смена номера — операция входа, а не косметика.** Исправление: подтверждение нового номера, атомарное переключение, версия владельца, аннулирование старых OTP/setup/сессий. Нельзя отдать новому владельцу очередь старого сотрудника.
7. **Миграция всех сразу слишком рискованна.** Исправление: сначала инвентаризация без изменений, затем добавочная схема и сравнение чтения; один тестовый tenant; реальная компания только после проверок и выпуска. Конфликты не исправлять эвристикой.
8. **Откат к прежней авторизации после отзыва недопустим.** После переключения авторитетного хранилища откат UI не должен оживлять старый пароль или номер. Поддерживаем предыдущий интерфейс через новый сервис либо блокируем переход; нет возврата к stale legacy phone/password.
9. **Обещать мгновенный отзыв офлайн неправильно.** Телефон без сети не узнает отзыв немедленно. Нужен ограниченный подписанный офлайн-допуск; сервер проверяет актуальные права при синхронизации, спорные события остаются отдельными, не теряются и не принимаются под другим человеком.

## 4. Итоговая архитектура, вариант B

### 4.1. Личность и рабочие данные

**Одна User-запись человека на компанию**, включая людей без доступа к CRM. Стабильный ключ organizationId+userId, глобальное isActive означает запрет всей учётки. Отдельного глобального Person и повторной миграции всех исторических FK не вводим. Агент без User получает User только через контролируемую миграцию, без CRM grant; существующие ID агента/визитов/табеля сохраняются.

Концептуальные сущности (имена ещё не объявляют готовую Prisma-миграцию):

- **LoginIdentity** — текущий номер для входа, нормализованный E.164, владелец User, состояние подтверждения, версия; история назначения append-only. Уникальный активный claim (organizationId, normalizedPhone) и не более одного активного номера на User. Незавершённые операции имеют короткую reservation с уникальностью, сроком и освобождением, но не дают вход.
- **AccountCredential** — один авторитетный пароль/эпоха учётки и существующая MFA-политика. Мобильный OTP не сбрасывает CRM MFA и не выдаёт CRM сессию. Отличающиеся legacy passwords не выбираются автоматически: нужен контролируемый reset, сохраняющий MFA.
- **ApplicationGrant** — CRM / TIME / ROUTE_FIELD, ACTIVE / REVOKED, область роли и version. Проверяется сервером при входе и каждом запросе. Допуск приложения не поднимает роль CRM и не расширяет tenant entitlement.
- **TimeEnrollment** — явное кадровое включение, отдел, руководитель, даты и участие в табеле. Не возникает от создания пользователя или выдачи полевых прав. Роль HR-ревьюера отдельна от учёта собственного времени.
- **FieldMembership** — полевая роль и территория/команда. Отключение Time не выключает маршруты, отключение маршрутов не увольняет человека.
- **Legacy actor mapping** — сохранённый MtmAgent.id привязан к User, служит совместимостью истории. Не является вторым владельцем номера/пароля. Множественные/межтенантные связи блокируют миграцию до ручного решения.
- **DeviceEnrollment** — допуск установки для User+приложение. Замена номера не выдаёт новый допуск автоматически. Устройство и номер — разные понятия; аппаратная защита и запрет совместного использования устройств потребуют отдельной реализации и приёмки.

Список CRM Users показывает людей с CRM grant. «Сотрудники» — TimeEnrollment, включая исторически уволенных по фильтру. «Агенты» — FieldMembership. Один человек с обоими членствами показан в обоих рабочих списках, но связан с одной учёткой. В каждом списке — своя роль/статус, а не две независимые личности.

### 4.2. Вход и права

Клиент выбирает компанию и своё приложение. Сервер разрешает вход только при действующей учётке, entitlement компании и grant этого приложения. Выдаёт токен с tenant, user, audience, credentialVersion, grantVersion и совместимым actor mapping. Передача имени приложения/заголовка сама по себе прав не даёт. Для CRM сохраняется собственная MFA и web session; мобильный токен не принимается вместо CRM-cookie.

Пользователь с одним разрешением открывает только своё приложение. С двумя — оба, с отдельными сессиями/кэшами и серверными audience-ограничениями. Кадровик не получает маршруты от HR роли; менеджер маршрутов не получает кадровую историю от полевой роли. API keys/импорты используют отдельные права, не обходят claim/tenant-проверки. В public login не раскрывается, кому принадлежит номер.

### 4.3. Создание и подключение существующего человека

1. Администратор выбирает «Добавить нового» либо «Подключить существующего». Второе действие ищет только разрешённых ему людей внутри компании.
2. Новый номер свободен: создаётся одна личность без пароля, нужное членство и только нужный app grant. Подтверждение WhatsApp и установка собственного пароля завершают активацию; кадровик пароль не знает.
3. Номер найден: уполномоченному администратору показывается карточка владельца с маскированным номером и действием «Подключить к Time»/«Подключить к Route & Field». Это явное действие над найденной учёткой, а не merge введённых ФИО и не автоматическая выдача прав.
4. Если это другой человек, используется его номер. Два человека в одной компании не получают вход одним номером. Общий рабочий аппарат при необходимости — отдельный терминальный сценарий, вне этой задачи.
5. Просмотр конфликта и выдача гранта имеют разные права. Кадровик без права управления доступами может отправить запрос администратору; не расширяем нынешние права HR автоматически.

### 4.4. Смена/освобождение номера

Обычная смена требует повторной авторизации владельца или уполномоченного администратора и подтверждения нового номера. Утрата старого номера не требует код на недоступный телефон: отдельное восстановление с проверкой администратором, аудитом и подтверждением нового номера. Контактный номер при необходимости явно помечен как контактный и не участвует в логине.

После проверки в одной транзакции: повторно проверяются actor/права/версии, резервируется новый claim, старый переводится в завершённое состояние, повышаются identity/credential epochs, аннулируются старые OTP/setup/reservations, фиксируется аудит. Старый номер освобождён только после commit; новый владелец проходит собственное подтверждение. Challenge связан с userId+claimVersion+purpose, не только со строкой номера. Две конкурентные операции на один номер завершаются одним успехом и понятным конфликтом. Порядок блокировок фиксирован: tenant guard → claims по сортированному номеру → account rows по ID; повтор с requestId идемпотентен.

### 4.5. Рабочие дни и офлайн

Time сохраняет юридически значимую историю табеля и immutable events. Route & Field получает отдельный FieldSession для маршрутов/GPS; он не начинает и не закрывает Time автоматически. Старые полевые дни доступны как legacy history, их существующие события и ID не переписываются. Новые полевые сессии не помещаются в старый общий unique org+agent+date.

Офлайн-операция хранит company+user+application+originalActor+grantEpoch+operationId. Исходная очередь сохраняется при обновлении и смене номера. Повторная авторизация того же человека позволяет проверить и отправить его очередь; вход другого человека не открывает и не отправляет её. Нельзя заменять owner на нового владельца номера. При отозванном праве сервер не принимает новые операции; старые неподтверждённые сохраняются для явного разбора, время клиента не доказывает, что действие было до отзыва. Already accepted idempotent receipts не превращаются в новые события. Истечение офлайн-допуска не стирает локальную очередь.

### 4.6. Перенос существующих данных

Не менять историю, пароли, телефоны или активные grants массово без отчёта. Сначала отчёт: linked/unlinked actors; разные User/Agent phones; неоднозначные форматы; дубликаты активных номеров; несколько actors на User; orphan/cross-tenant links; технические автоматические карточки; наличие двух источников паролей. Отчёт без credentials и открытых номеров.

Существующие связи и audit enrollment используются как доказательства, роль/совпавший номер сами по себе недостаточны. Вводятся новые таблицы/RLS/unique/FK и централизованный сервис, сначала shadow-read без выдачи новых прав. Для каждого tenant сверяется expected grants и список людей. Автоматический provision-trigger перестаёт выдавать членство, но заменяется сохранением необходимых integrity guards; его нельзя просто удалить вместе с защитой истории.

Legacy-совместимость имеет явный период и нижнюю границу версии. Два приложения для одной личности не активируются, пока сервер и обе сборки не умеют разделять audience и session streams. Старым клиентам показывается необходимость обновления, но их очереди сохраняются; приёмка проверяет реальное обновление без очистки. После authoritative cutover старые поля больше не используются для поиска владельца.

## 6. Матрица приёмки

- CRM-only не появляется в HR и не получает доступ к мобильным приложениям.
- Time-only не видит клиентов/маршрутов/чужой кадровой истории и не входит в CRM.
- Field-only не попадает в табель; менеджер видит только разрешённую команду.
- Оба приложения: одна личность/номер, независимые grants, отдельные рабочие сессии; отзыв одного доступа не выключает второй.
- Один и тот же номер в другой компании не смешивает учётки/OTP; без выбранной компании нет неоднозначного поиска.
- Все пути смены номера/импорта используют единый сервис; конкурирующие назначения не создают два active claims.
- Неверный/истёкший/повторный OTP и токен предыдущего владельца/версии отвергаются; CRM MFA не сбрасывается мобильным восстановлением.
- Безопасное подключение existing account: чужая компания, неподходящая роль администратора, повтор/replay, изменённые grants и неоднозначная связь отвергаются.
- Смена номера освобождает старый после commit, но не переносит старые сессии, approvals или очередь следующему владельцу.
- Coldstart/upgrade/offline>24h: исходные операции сохраняются; accepted replay не удваивает события; новый пользователь не видит очередь прежнего.
- Legacy client в период перехода не получает новые права и не создаёт второй смешанный день; обязательное обновление не уничтожает очередь.
- Увольнение/архив/отзыв: история сохраняется; обычное отключение одного приложения не превращается в глобальную блокировку.

### 8.1. Одноразовые коды и отправка: проверенные точки повторного использования

`OtpCode` и `src/lib/mtm/mobile-login-code.ts` уже хранят bcrypt-код с purpose/tenant, TTL и попытками; нынешний `codeHolder` выбирает legacy MtmAgent, а setup token связан с его fingerprint. Эта схема не является proof для нового claim/reservation: в ней нет связи с reservation ID, ожидаемыми версиями личности и назначением нового номера. Purpose `mtm_app_login` и старый setup JWT не допускаются как подтверждение identity phone change. Смена номера/версии отзывает старый proof, даже если его цифровой код ещё не истёк; повторное подтверждение сериализуется с выдачей/отзывом и не создаёт второго claim.

Провайдер `src/lib/mtm/whatsapp-login-code.ts` уже использует заданный сервером канал LeadDrive и authentication template; он намеренно не пишет телефон/код в общую переписку. Можно повторно использовать этот транспорт после проверки нового контракта, сохраняя отсутствие OTP в журнале. Его нынешний legacy caller выдаёт код, затем отдельно отправляет и отзывает при ошибке; это не атомарная запись нового claim+delivery. Для новой регистрации нужна отдельная транзакционная запись proof+аудита+задания отправки с зашифрованным секретным содержимым и ограниченным сроком жизни. Повтор/timeout отправки не продлевает бронь и не подтверждает владение автоматически. Обычный route-notification outbox содержит пользовательский текст, а event/effect outbox имеют собственные контракты; ни в один из них нельзя просто положить открытый OTP или изменить общий drain без явного нового типа/ограничений.

Публичный ответ на запрос кода остаётся неразличимым для неизвестного/чужого номера; приватный поиск конфликтующего владельца доступен только уполномоченному администратору компании. Ни совпадение телефона, ни факт выдачи/успеха отправки кода не подключает приложение: отдельно проверяются proof possession, нужный app grant/лицензия и членство. Восстановление общего пароля не выключает и не сбрасывает CRM MFA. В этой задаче реальные коды не отправлялись; provider/schema source audit не является проверкой доставки Meta.
