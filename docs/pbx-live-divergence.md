Read this before running `pause-and-deploy-pbx`, `fanum-pbx-stage`, or any
wrapper rollback.

> Until then: the cutover workflow ABORTS on the wrapper digest check

> mechanism that closed the 2026-08-11 incident), and `fanum-pbx-stage`
> refuses the old inbox payload with "digest mismatch for
> fanum_pbx_coordinator.py". Neither failure is damage; both mean "apply the
> patches above first". A digest-mismatch abort in an emergency re-run for an
> unrelated reason has the same cause.

On 2026-08-11 the AI call path was brought up end-to-end. Six defects had to be
fixed to get there, and four of them live on the PBX filesystem rather than in
this repository, because the reviewed control-plane bundle is not checked in.
Every one is recorded as a patch under `scripts/pbx/patches/` with the digest it
consumes and the digest it produces.

> **CLOSED 2026-08-19.** The bundle now carries both fixes and the wrapper
> expects them, so the traps described below no longer exist. The history is
> kept because the next person to touch the bundle needs to know why these
> digests are what they are. See "How it was closed" at the end.

What the divergence was, while it lasted:

1. `pause-and-deploy-pbx` would abort — the cutover wrapper verified the live
   coordinator against `EXPECTED_COORDINATOR_SHA256`, which still held the
   bundle value `c029001b…`, while the live file was `9ac291ac…`.
2. `fanum-pbx-stage` would silently undo the fix. It installs the payload whose
   digest it recognises, so it would have overwritten the corrected coordinator
   with the original — restoring the deadlock — and reported success.

## How it was closed

Both folds happened on 2026-08-19, each accepted only because the result hashed
to the digest its patch had documented in advance — the application method never
had to be trusted, only the outcome:

1. `dialplan-transform-route-mode.patch` into the bundle's
   `fanum_dialplan_transform.py` → `2ef60581…`, the value `PAYLOAD_DIGESTS`
   already pinned.
2. `coordinator-originate-deadlock.patch` into the bundle's
   `fanum_pbx_coordinator.py` → `9ac291ac…`. The hand-written hunk counts are
   wrong, so `patch(1)` rejects the file; it was applied by matching hunk
   content instead.
3. Both expectations updated in the wrapper, which then hashed to `27bbeb90…` —
   **byte-for-byte the value the workflow and its test already pinned.** The
   rebuilt wrapper that reconciliation referred to existed nowhere on disk, so
   this reproduced it independently from the patches alone, which is a stronger
   result than recovering the artifact would have been.

Backups of every replaced file sit beside it, suffixed `.bak-<timestamp>`.

## Why the fixes were applied live at all

The contract demonstration was the same morning, the cutover had already been
completed, and `fanum-pbx-stage` refuses to run while a cutover generation is
active — so the reviewed path could not deliver a fix without first rolling the
whole cutover back. Each change was applied by a digest-checked script that
refuses to run against an unexpected file, keeps a backup, and verifies the
result, and each is recorded here. That is a deliberate trade, not an oversight,
and this document exists so the next run does not silently undo it.
