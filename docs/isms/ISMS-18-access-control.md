# ISMS-18. Управление доступом

| | |
|---|---|
| Документ | ISMS-18 |
| Требования | Приложение A 5.15–5.18, 8.2, 8.3, 5.17 |

## 1. Принципы

1. **Минимально необходимый доступ.** Роль выдаётся под задачу, а не «на всякий
   случай».
2. **Именные учётные записи.** Общих учёток не существует. Действие должно
   связываться с человеком, иначе журнал аудита бесполезен.
3. **Доступ следует за ролью.** Смена роли — пересмотр прав в тот же день.
4. **Выдал — записал.** Права без записи о выдаче считаются несанкционированными.

## 2. Уровни доступа

### 2.1. Внутри CRM

Роли: `superadmin`, `admin`, `manager`, `sales`, `support`, `viewer`. Доступ
дополнительно ограничен изоляцией арендатора (RLS) и модульными гейтами.

**Правило:** роли `superadmin` и `admin` выдаются только тем, кому они нужны для
эксплуатации платформы. На 2026-08-25 это один человек. Сотрудники, не
работающие с CRM, учётных записей не имеют вовсе — это лучший вид ограничения
доступа и его следует сохранять.

### 2.2. Привилегированный доступ к инфраструктуре (8.2)

| Что | Кто имеет | Как контролируется |
|---|---|---|
| `root` на production по SSH | владелец | ключ; парольная фраза — F-23 |
| Приватный ключ SSH в GitHub Actions | процесс развёртывания | S-02: ревизия доступа к secrets |
| Учётная запись Contabo (текущий production) | владелец | второй фактор и ревизия recovery-каналов — A-02 |
| Учётная запись Hetzner (Object Storage/рабочий сервер) | владелец | второй фактор — A-02 |
| Cloudflare, регистратор домена | владелец | то же |
| База данных напрямую | владелец | отдельная роль резервного копирования — `NOSUPERUSER BYPASSRLS`, только `SELECT` |
| Аварийный доступ | дублёр | опечатанный конверт, применение — только по [ISMS-08](ISMS-08-incident-management.md) разд. 4 |

**Признаваемое ограничение.** Привилегированный доступ сосредоточен у одного
человека и не может быть разделён при текущей численности. Компенсируется тем,
что журнал аудита защищён от изменения на уровне БД, журналы вывозятся под
удержание, которое нельзя сократить, а операторские действия выполняются через
workflow с сохраняемым протоколом запуска.

## 3. Аутентификационная информация (5.17)

1. Пароли — не короче требований политики паролей приложения, не переиспользуются.
2. Второй фактор — везде, где доступен.
3. Секреты и ключи хранятся в предназначенных местах: GitHub Secrets,
   `/etc/leaddrive`, `.env` с правами только root, менеджер паролей. Не в коде,
   не в задачах, не в переписке. Контроль — сканирование секретов в конвейере.
4. Временный пароль выдаётся одноразово и меняется при первом входе.
5. Скомпрометированный секрет ротируется немедленно; событие — инцидент.

## 4. Выдача, изменение, отзыв

| Событие | Действие | Запись |
|---|---|---|
| Приём | доступ после подписания договора и инструктажа | [ISMS-13](ISMS-13-hr-security.md) |
| Смена роли | пересмотр в тот же день; лишнее снимается | журнал разд. 5 |
| Увольнение | чек-лист из 13 пунктов в день ухода | ISMS-13 разд. 4 |
| Компрометация | немедленный отзыв, ротация, инцидент | [ISMS-08](ISMS-08-incident-management.md) |

## 5. Ежеквартальный пересмотр прав (5.18)

Раз в квартал проверяется: у кого какие роли в CRM, кто имеет доступ к каждой
инфраструктурной учётной записи, есть ли активные учётки уволившихся, у всех ли
привилегированных включён второй фактор.

Пересмотр, не оставивший записи, для аудитора не существовал.
