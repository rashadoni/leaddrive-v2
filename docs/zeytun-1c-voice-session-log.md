## 2026-10-22 — предварительная архитектура для обсуждения

Это предложения, а не согласованная спецификация или описание уже работающей интеграции.

1. 1С остаётся источником истины для номенклатуры, договоров, персональных цен, доступного остатка, резервов и статусов заказа.
2. Отдельный адаптер синхронизирует компактный tenant-scoped каталог постранично и, при наличии возможностей API, по изменениям. Первичный импорт не находится на пути разговора. Нужны обработка удалений/деактиваций, версия каталога, отметка свежести и периодическая сверка.
3. Поиск использует название, подтверждённые варианты произношения/написания на языках клиентов, точные коды, дозировку, единицы, форму, фасовку и производителя. PostgreSQL с индексами — исходный вариант для проверки на таком объёме; необходимость отдельного поискового сервиса должна следовать из измерений.
4. Модель получает несколько найденных кандидатов, например 3–5, и нужные поля, а не весь каталог. Нечёткое совпадение помогает найти кандидатов; не подтверждает медицинскую взаимозаменяемость или точность выбранной позиции.
5. Поиск должен учитывать неоднозначность по полному ассортименту, включая отсутствующие товары. Единственный товар в наличии не становится автоматически правильным; нельзя скрыть опасного созвучного кандидата усечением выдачи.
6. Результат сопоставления — проверенный ID позиции 1С и обязательные характеристики. Уверенность нельзя сводить к самопроизвольной оценке LLM или одной метрике сходства. Пороговые правила калибруются на телефонных записях Зейтун и размеченных заказах.
7. Диалог собирает изменяемый черновик. Однозначная полная позиция добавляется с коротким проговариванием. При пропущенном существенном признаке задаётся один конкретный вопрос. Созвучные опасные пары, противоречия и повторная неудача требуют явного уточнения или оператора. Молчание не считается согласием.
8. История покупок повышает релевантность поиска только после проверки контрагента/филиала; не разрешает угадывать дозировку, производителя, форму, количество или заменять товар.
9. Котировка и проверка условий идут для выбранных позиций и идентифицированного контрагента. Перед оформлением проверяются актуальные цены, свободные остатки, единицы/кратность, кредитные ограничения, доставка и допустимость товара по согласованным правилам Зейтун.
10. Клиент подтверждает конкретную актуальную версию итогового заказа. Для длинного B2B-заказа предлагается проверяемый список в согласованном канале/кабинете; голосовой режим должен перечислять достаточно деталей и допускать исправления. После существенного изменения заказа/цены требуется новое подтверждение.
11. Создание заказа/резерва выполняет серверный валидатор через ограниченный API, с устойчивым внешним номером запроса и защитой от дублей. При таймауте сначала проверяется результат по этому номеру; если API не позволяет проверить, исход считается неизвестным и передаётся оператору, без слепого повтора.
12. Корректный lifecycle: черновик → проверка/котировка → подтверждение → отправка → принят 1С либо ожидание/ошибка. Наличие по снимку не равно резерву. Готовый заказ/резерв объявляется только после подтверждённого ответа 1С.
13. Голосовая обработка и синхронизация отделены от веб-запросов CRM. Нужны лимиты одновременных звонков и обращений к 1С по tenant, ограничения очередей, таймауты, замедление повторов и ручной fallback. Отдельный процесс на том же сервере не гарантирует изоляции ресурсов; при росте нагрузок нужен отдельный worker с ресурсными лимитами.
14. Внешняя обработка речи/модель — кандидат для уменьшения нагрузки на собственные серверы, с предварительной оценкой качества, стоимости и требований к данным. Конкретный провайдер и пропускная способность не выбраны.

## 2026-10-22 — B2B-риски и проверка гипотез

- Идентификация юрлица, филиала и полномочий сотрудника; номер телефона сам по себе недостаточен для доступа к условиям договора.
- Единицы: коробка, упаковка, блистер, штука; кратность заказа; похожие числа и единицы дозировки; смешанная русская/азербайджанская речь.
- Персональные прайсы, НДС, скидки, бонусные товары, валюта, задолженность и кредитные лимиты; изменение цены требует согласования новой версии.
- Партии, остаточный срок годности, карантин/отзыв, холодовая цепь, лицензируемые/ограниченные позиции — правила согласуются с Зейтун и применимыми требованиями; это не утверждение конкретных юридических норм.
- Одновременные заказы на последние остатки, частичная поставка, замены, отмена/изменение после принятия, недоступность 1С, неизвестный результат после таймаута.
- Разделение данных tenant и контрагентов, секреты API вне промпта, проверяемые права операций, минимальный доступ, защита от инструкций в речи и текстах товаров, ограничения хранения записей/транскриптов.
- Для исходящих звонков — согласованный список, допустимое время/частота, отказ от обзвона и проверка получателя до раскрытия условий. Правила записи и внешней обработки данных предстоит согласовать.
- Пилот: исторические/тестовые разговоры и черновики с проверкой оператором; затем ограниченные заказы постоянных контрагентов. Метрики: точность полной строки (ID + форма + дозировка + фасовка + количество/единица), ошибочный автоматический выбор, пропуски товаров, число уточнений, p95 задержки, стоимость успешного заказа и ошибки API. Нулевое число обнаруженных ошибок в конечном тесте не доказывает нулевой риск.
- Для расчёта мощности нужны одновременно активные звонки, длительность, число строк заказа, скорость и лимиты 1С; 10 000 названий само по себе не определяет мощность голосовой системы.
