# Прод: хост придерживает ядра (замер 2026-11-13)

Коротко: остаток «подвисаний» CRM в начале минуты — не наш код и не наше
расписание. Виртуальным ядрам сервера хост Contabo регулярно не даёт
работать. Изнутри сервера это видно только пробой ниже.

## Что видит человек

Полная загрузка раздела — 2,5–2,7 с в спокойную секунду и 5–6,5 с, если она
пришлась на начало минуты, кратной пяти. Журнал nginx за 13 ноября, 12:40–18:00,
только веб-процесс, без потоков:

| Когда | Запросов | Медиана | 90 % быстрее | Дольше 1 с |
|---|---|---|---|---|
| Первые 20 с пятиминутки | 477 | 0,40 с | 1,7–2,0 с | 21–26 % |
| Остальное время | ~4000 | 0,16 с | 0,5 с | 3 % |

## Что показала проба

Шесть процессов, по одному на ядро, спят по 4 мс и записывают, на сколько
позже их разбудили. 13 минут, 18:28–18:41 по часам прода:

- каждое ядро стояло **12,6 %** времени;
- первые 10 с минуты, кратной пяти, — **54 %**; первые 10 с прочих минут —
  23–42 %; середина минуты — 2–6 %;
- самая длинная остановка — **1457 мс**;
- очередь планировщика самого сервера (`run_delay` из `/proc/self/schedstat`)
  объясняет **18 %** потерянного времени. Остальное сервер считает простоем.

Процесс, который не спит вовсе, за 25 секунд вокруг начала минуты потерял
7–8 % времени кусками до 166 мс. То есть ядро отбирают и у работающего
процесса, а не только поздно будят уснувший.

Счётчик `steal` в `/proc/stat` при этом ноль с загрузки: Contabo его гостю не
отдаёт, поэтому `top`, `sar` и `iostat` показывают свободный сервер.

Dev-бокс — другой VPS Contabo — в 18:41:01–05 стоял 80 % каждой секунды,
самая длинная остановка 1115 мс. Это свойство общих ядер, а не одной машины.

## Чем это не является

- Не расписание задач: на секундах 0–8 минут, кратных пяти, в crontab нет
  ничего, а собственные задачи на секундах 38–48 всплеска не дают.
- Не контрольные точки Postgres: они идут на 4-й и 9-й минуте и пишут по
  сотне буферов.
- Не запросы: в 18:15:02 веб-процесс занял 139 % ядра при трёх служебных
  вебхуках, простейший `SELECT` из `channel_configs` шёл 1,3 с.
- Не нехватка памяти: подкачки нет, 9 ГиБ свободно.

## Что с этим делать

Настройкой внутри сервера это не убрать. Варианты — решение владельца:

1. Обращение в Contabo с этими цифрами: попросить перевести VPS на менее
   загруженную машину. Бесплатно, результат не гарантирован.
2. Сервер с выделенными ядрами (у Contabo это линейка Cloud VDS).

После любого из них — прогнать пробу снова.

## После переноса на другой хост (2026-11-14)

Contabo по обращению (тикет 16240564320) перенёс сервер на менее загруженный
хост «на ходу»: без перезагрузки, uptime и процессы те же, скачков часов нет.
Письмо о завершении — 14 ноября; проба через 10 минут после него, суббота
15:49–15:56 по часам прода:

| | 13.11, пятница, до | 14.11 утром, до | 14.11 после |
|---|---|---|---|
| Ядро стоит, в среднем | 12,6 % | 6,6 % | **2,5 %** |
| Первые 10 с минуты, кратной пяти | 54 % | 21 % | 17,5 % |
| Середина минуты | 2–6 % | 3–8 % | **0,2–1,7 %** |
| Самая длинная остановка | 1457 мс | 188 мс | 445 мс |

Общий фон ушёл почти целиком; всплеск в первые секунды пятиминутки остался, но
короче (в 15:50 — одна плохая секунда, в 15:55 — 16 %). Сравнение с пятницей
нечестно (выходной), поэтому окончательно — повторить в будний день в 18:30.
Если всплеск вернётся к прежним 50 % — снова тикет или выделенные ядра.

## Проба

Только чтение, около 1 % процессора. Запуск: `python3 probe.py 780 prod`,
затем сложить столбец «потеряно» по секундам.

```python
# Per second and per vCPU: ms lost to late wake-ups (>5 ms late), how much of
# that the guest run queue explains, and the longest single stop.
import os, sys, time, multiprocessing as mp

def run_delay():
    with open("/proc/self/schedstat") as f:
        return int(f.read().split()[1])

def worker(cpu, until, path):
    os.sched_setaffinity(0, {cpu})
    last = time.monotonic(); last_rd = run_delay(); cur = int(time.time())
    lost = rq = worst = 0.0
    with open(path, "w") as out:
        while time.time() < until:
            time.sleep(0.004)
            now = time.monotonic(); rd = run_delay(); gap = now - last - 0.004
            if gap > 0.005:
                lost += gap; rq += (rd - last_rd) / 1e9; worst = max(worst, gap)
            last = now; last_rd = rd
            sec = int(time.time())
            if sec != cur:
                out.write("%d %d %.0f %.0f %.0f\n" % (cur, cpu, lost * 1000, rq * 1000, worst * 1000))
                out.flush(); cur = sec; lost = rq = worst = 0.0

if __name__ == "__main__":
    seconds, tag = int(sys.argv[1]), sys.argv[2]
    until = time.time() + seconds
    workers = [mp.Process(target=worker, args=(c, until, "/tmp/jit3-%s-%d.txt" % (tag, c)))
               for c in range(os.cpu_count())]
    for w in workers: w.start()
    for w in workers: w.join()
```

Строка файла: секунда (unix), ядро, потеряно мс, из них в очереди сервера мс,
самая длинная остановка мс.
