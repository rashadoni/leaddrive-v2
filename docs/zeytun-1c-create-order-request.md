# Зейтун: метод 1С для приёма телефонного заказа

Задание для программиста 1С Зейтуна. Дата: 2026-10-27.

## Зачем

Аптека звонит на линию Зейтуна, ИИ принимает заказ, менеджер Зейтуна
проверяет его в LeadDrive CRM и нажимает «Подтвердить». Сейчас после этого
менеджер набирает тот же заказ в 1С вручную. Нужно, чтобы по кнопке
«Подтвердить» заказ сам появлялся в 1С.

В опубликованном веб-сервисе `ZTNMOBILE` девять операций: `ListClients`,
`CustomerDebts`, `Data`, `Debet`, `GetInvoice`, `History`, `NewGoods`,
`SaleHistory`, `SettlementClients`. Все они только читают данные (WSDL
проверен 2026-10-27). Создать документ ими нельзя, поэтому нужен новый метод.

## Что CRM уже знает о заказе

Всё это CRM берёт из ваших же методов, ничего нового заводить не нужно:

- **аптеку** — `GUID` контрагента из `ListClients`;
- **товар** — `Номенклатура.Guid` из `AvailableBalances`;
- **склад и признак METRO** — те же значения, с которыми CRM запрашивает
  `AvailableBalances` (`Warehouse`, `METRO`);
- **количество** — в `БазоваяЕдиницаИзмерения` товара, как в
  `AvailableBalances`. Строку в другой единице (например, штуки вместо
  упаковок) менеджер исправляет до подтверждения, в 1С она не уходит;
- **цену**, которую видел менеджер, — `Цена` из `AvailableBalances`. Она
  только для сверки: цену в документе ставит 1С по своим правилам.

## Метод 1: создать заказ

Предлагаем добавить его в тот же HTTP-сервис, где работает
`AvailableBalances`: тот же вход (Basic), тот же JSON. Название, например,
`CreateOrder`, `POST`.

Запрос:

```json
{
  "ВнешнийИД": "cmh9x2k0q0001abcd",
  "ВнешнийНомер": "TS-1005",
  "GUID": "guid-аптеки-из-ListClients",
  "METRO": false,
  "Warehouse": "guid-склада",
  "Дата": "20261027153000",
  "Комментарий": "Телефонный заказ TS-1005. Подтвердил: Менеджер Имя",
  "Товары": [
    { "Номенклатура": "guid-товара", "Количество": 10, "Цена": 12.5 },
    { "Номенклатура": "guid-товара-2", "Количество": 3, "Цена": 4.2 }
  ]
}
```

- `ВнешнийИД` — постоянный идентификатор заказа в CRM, до 64 символов.
  **По нему 1С узнаёт повтор**: если документ с таким `ВнешнийИД` уже есть,
  метод не создаёт второй, а возвращает существующий (`"Создан": false`).
  Без этого обрыв связи после записи документа давал бы дубль заказа.
- `ВнешнийНомер` — номер, который видят менеджер и аптека; удобно показать
  его в документе, чтобы находить заказ поиском.
- `Дата` — время звонка, формат как в ваших методах (`ГГГГММДДччммсс`, время Баку).

Ответ при успехе:

```json
{
  "code": 0,
  "data": {
    "Создан": true,
    "Документ": { "Guid": "guid-документа", "Номер": "ЗК-000123", "Дата": "20261027153112", "Сумма": 137.6 },
    "Товары": [
      { "Номенклатура": "guid-товара", "Количество": 10, "Цена": 12.5, "Сумма": 125.0 },
      { "Номенклатура": "guid-товара-2", "Количество": 3, "Цена": 4.2, "Сумма": 12.6 }
    ]
  }
}
```

`Товары` в ответе — то, что фактически записано в документ, с ценами 1С.
CRM покажет менеджеру, если цена или количество отличаются от отправленных.

Ответ при отказе, документ **не** создан:

```json
{
  "code": 1,
  "Ошибки": [
    { "Код": "товар_не_найден", "Номенклатура": "guid-товара-2", "Текст": "..." },
    { "Код": "нет_остатка", "Номенклатура": "guid-товара", "Текст": "..." }
  ]
}
```

Коды, которые CRM будет понимать: `аптека_не_найдена`, `товар_не_найден`,
`нет_остатка`, `неверное_количество`, `нет_договора`, `склад_не_найден`,
`прочее`. Если заказ нельзя записать целиком, лучше не записывать ничего и
перечислить все проблемные строки сразу: менеджер исправит их за один раз.

## Метод 2: узнать, записан ли заказ

Нужен на случай, когда CRM отправила заказ, а ответа не дождалась (таймаут,
обрыв связи). Повторять запрос вслепую CRM не будет, она сначала спросит.

`OrderStatus`, `POST`:

```json
{ "ВнешнийИД": "cmh9x2k0q0001abcd" }
```

Ответ: `{"code": 0, "data": {"Найден": true, "Документ": {…}, "Товары": […]}}`
в том же виде, что у метода 1, или `{"code": 0, "data": {"Найден": false}}`.

## Что нужно решить Зейтуну

1. **Какой документ создаётся**: «Заказ клиента» или другой, который у вас
   используется для заказов аптек.
2. **В каком состоянии**: только записан, и дальше его ведёт оператор 1С,
   или сразу проведён. Мы предлагаем «записан, не проведён»: так оператор 1С
   видит заказ и может его остановить.
3. **Договор или соглашение аптеки**: 1С подставляет основной сама, или CRM
   должна передавать его (`agreement`, как в `SettlementClients`).
4. **Адрес и защита**: сейчас сервис открыт по HTTP. Метод, который
   создаёт документы, просим открыть по HTTPS и под отдельным пользователем
   1С, которому разрешено только это.

## Что сделает CRM, когда метод появится

- По «Подтвердить» отправит заказ в 1С и запишет в карточку номер документа
  1С. Подтверждение аптеке в WhatsApp уйдёт после ответа 1С.
- Если 1С отказала, заказ останется у менеджера с перечнем строк и причин.
- Если ответа нет, CRM спросит `OrderStatus` и не создаст дубль.
- Сначала проверим на тестовой базе 1С, если она есть, или на одном
  заказе с вашим сотрудником.

## Ответы Зейтуна (2026-10-28, Самир, 1С)

1. Документ — **«Заказ покупателя»**.
2. Документ **сразу проводится**, оператор 1С его не останавливает. Значит,
   «Подтвердить» в CRM — окончательное решение менеджера: CRM отправляет в 1С
   только заказ, где у каждой строки есть товар из 1С и количество в его
   базовой единице, а повторную отправку того же заказа 1С узнаёт по
   `ВнешнийИД` и второй документ не создаёт.
3. **Договор 1С подбирает сам**, CRM его не передаёт.
4. HTTPS — «в скором времени». Метод, который создаёт документы, CRM начнёт
   вызывать только по HTTPS.

Осталось от Зейтуна: сами методы `CreateOrder` и `OrderStatus` (адрес, пример
ответа) и, если есть, тестовая база.

## Сделано в CRM (2026-10-30)

Сторона CRM готова и ждёт только методов (код —
`src/lib/pharmacy-orders/erp-order.ts`). Включается файлом
`zeytun-1c-orders.json` в приватной папке разрешения линии на сервере CRM:

```json
{ "organizationId": "<организация Зейтуна в CRM>",
  "createEndpoint": "https://…/CreateOrder", "statusEndpoint": "https://…/OrderStatus",
  "username": "<пользователь 1С только для заказов>", "password": "<…>" }
```

Права 0600, владелец — тот же пользователь, что у остальных файлов папки.
Без файла кнопка «Подтвердить» работает как раньше. Сначала — адреса
тестовой базы, проверка на одном заказе, потом адреса рабочей.
