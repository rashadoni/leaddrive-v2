## R-01 · P2 · Фильтр «Мои встречи» проверяет количество без владельца

Место: `scripts/booking/role-browser-evidence.mjs:273–276`.
После выбора собственного userId тест ждёт одну строку и повторяет count=1.
Затем проверяется canManage другой встречи, но не identity отфильтрованной строки.
Если регрессия вернёт единственную назначенную встречу вместо собственной,
проверка всё равно пройдёт: обе записи уже разрешены координатору и исходная
проверка scope не отличает такое последующее ошибочное сужение фильтра.

Подтверждение: точный callback waitRows извлечён из исходника и исполнен в
изолированном Node vm с одной строкой Sandbox assigned meeting. И callback,
и следующий count assertion принимают этот неверный owner. Это маленький
контрпример predicate, не браузерное воспроизведение дефекта приложения.
[Квитанция](evidence/review-filter-counterexample.json).

Исправление: после выбора фильтра проверить точное собственное имя/ID и отсутствие
assigned-встречи; полезно также запросить list API с host=coordinatorId и сравнить
точный singleton ID. Тест должен падать на контрпримере с одной чужой разрешённой
строкой, а не только на изменении количества.

## R-02 · P2 · Draft-флаг события может пропустить свежий candidate

Место: `.github/workflows/booking-role-sandbox.yml:29`.
Job разрешён только если github.event.pull_request.draft=false. Это snapshot
события, не текущее состояние PR. При близких push/ready synchronize для свежего
SHA может сохранить draft=true, а ready event относиться к предыдущему SHA.
Fresh job будет SKIPPED, тогда как другой event может проверить старый исходник.
Cancellation не создаёт отсутствующий тест свежего candidate.

Репозиторий уже документирует тот же инцидент #639 в AGENTS.md:216 и
`.github/workflows/pr-checks.yml:57–71`; основной pr-scope поэтому использует
`scripts/ci/pr-draft-state.sh` и живое чтение PR. Новый workflow повторяет старую
ошибку. Точный expression проверен малой truth-table диагностикой: свежий
snapshot=true даёт false даже когда PR уже ready; старый ready snapshot=false
даёт true. Новый GitHub race/run намеренно не создавался.
[Квитанция](evidence/review-draft-counterexample.json).

Исправление: использовать тот же живой draft gate в лёгком preflight job и
разрешать тяжёлый job по его результату; подтвердить успех именно на текущем
head/merge. Не делать gate обязательным с существующим paths filter и не
выдавать SKIPPED за PASS. Нужный для чтения PR token не должен передаваться
непроверенному application runtime.

## R-03 · P2 · Отказ административных настроек подтверждён только через UI

Место: `scripts/booking/role-browser-evidence.mjs:184–187`.
Тест утверждает canConfigure=false, отсутствие кнопок и Forbidden при tab=pages/team.
Он ни разу не вызывает GET /api/v1/booking-pages или GET
/api/v1/bookings/coordinators. Если UI останется правильным, а HTTP handler
начнёт отдавать страницы или grants обычному сотруднику, текущий stand останется
зелёным. Дополнительные действия записи не требуются для этого отрицательного
read-контроля: достаточно настоящих HTTP GET с ожидаемым403.

В текущих handlers (`src/app/api/v1/booking-pages/route.ts:17` и
`src/app/api/v1/bookings/coordinators/route.ts:10`) проверка administrator есть.
В её поломке приложение не обвиняется; отсутствует автоматическое покрытие
важной серверной границы. Прямое отсутствие обоих paths подтверждено просмотром
всего harness и диагностической квитанцией R-01.

Исправление: для employee, restricted coordinator и manager без grant явно
получить403 с обоих API и проверить отсутствие data. Не мокировать ответы,
не ослаблять RLS и не добавлять права записи. Existing unit/PG проверки
сохраняются как отдельный слой и не называются этим новым browser proof.
