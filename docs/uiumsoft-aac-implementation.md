# AAC — реализация клиентского API-коннектора

Дата: 14 октября 2026. Основание: API flow AZ/EN v1.1 и поручение пользователя начать автономную реализацию. Клиент подтверждён: **AAC**.

## Граница текущего результата

Добавлено проверяемое серверное ядро в `src/lib/integrations/customer-receiver/`. Оно пока **не подключено к маршрутам CRM или расписанию задач**. Ни одна операция в работающей CRM не начинает внешнюю отправку от этих изменений. Настоящий приёмный API, организация AAC, Azure/VPN и сертификаты ещё не подключены.

Название AAC — бизнес-идентичность, не подтверждённый `organizationId`. В `clients/registry.json` отдельной AAC-инсталляции нет; это не доказывает отсутствие такой организации в БД. Не использовать ID одноимённой клиентской карточки вместо ID tenant. Шаблон `ops/customer-receiver/aac.test.example.json` намеренно содержит `organizationId: null`, отключённую интеграцию и `exportRule.mode: disabled`. Приложение его не загружает.

## Что реализовано

| Компонент | Поведение |
| --- | --- |
| `contract.ts` | Проверяет предлагаемый JSON v1.0 для клиентов и сделок, возвращает отдельную копию только разрешённых полей. Проверяет UUID, версии, UTC и календарные даты. Контакты/заказы требуют отдельного согласованного профиля и пока не поддержаны |
| `eligibility.ts` | Явные режимы disabled / all_deals / pipeline_stages. Совпадения названия этапа в другой воронке недостаточно. Проверяет организацию и наличие CRM-клиента. Правило AAC ещё не выбрано |
| `delivery.ts` | Стабильный ключ события с tenant/integration/environment; изменение тела не создаёт новый ключ. Проверка точного event/external ID/version в receipt. HTTP 200/201/202 без receipt остаётся неопределённым исходом. Принятые API события не пересылаются из-за отсутствия ERP-статуса |
| `outbox.ts` | Адаптер к существующему `EffectOutbox` через переданную транзакцию. Replay/shadow запрещены. Ошибка записи передаётся вызывающей транзакции. Это ещё не доказательство атомарности всей CRM: подключение команд остаётся следующим этапом |
| `transport.ts` | Один PUT по HTTPS 443 с обязательными CA/mTLS/Bearer. Точный RFC1918 IPv4 привязан к сокету; имя проверяется TLS/SNI. Нет DNS-переходов и HTTP redirects. Ограничения соединения 5 с, всей попытки 30 с, ответа 16 KiB. Существующая защита обычных webhook не изменена |
| `security-events.ts` | Нормализация по разрешённым полям без произвольных сообщений/тел/секретов. UTF-8 JSONL, схема JSON Schema, manifest со счётчиками и SHA-256. Проверка организации и TEST/PROD, явные пробелы покрытия, отсутствие заявления о полноте/подлинности только на основании hash |

Повторы разрешаются только после проверки receipt и подтверждённой долговременной дедупликации у получателя. Чистый планировщик учитывает 1/5/15/60 минут, положительный jitter, `Retry-After` и окно 24 часа. Он не является запущенным worker и не обходит принятую платформой очередь reconciliation.

Денежные значения не проходят через JavaScript Number. CRM хранит `Decimal(18,4)`, предложенный профиль — два знака. Преобразование допускает только нулевые дополнительные знаки; `1500.1234` отклоняется вместо неявного округления. Иная точность должна быть согласована в версии контракта.

Текущий профиль уже проектного максимума: до 256 KiB отправляемого JSON, только HTTPS 443 и точный частный IPv4. IPv6, другой внутренний порт, дополнительные поля/типы клиентов и аутентификация без mTLS требуют отдельной проверенной доработки. Это ограничения первой реализации, а не утверждения о возможностях API заказчика.

## Следующие этапы и критерии готовности

1. **Идентичность AAC и бизнес-правило.** Подтвердить фактический tenant ID будущей инсталляции и правило all_deals либо конкретную воронку/этапы. Утвердить поля, валюты, точность и обязательные реквизиты. Ни одна пустая настройка не означает «передавать всё».
2. **Транзакционное подключение CRM.** Добавить durable версии сущностей и связи зависимостей. Сохранение клиента/сделки, снимка разрешённых полей и Outbox должно происходить в одной tenant-транзакции. Покрыть API, импорт, конвертацию лида и прочие фактические пути изменения; не ограничиваться REST POST. Проверить rollback и конкурентные версии на PostgreSQL.
3. **Worker и reconciliation.** Применить существующие lease/attempt/state-machine guards `EffectOutbox`; не писать статусы произвольно. Отдельно хранить accepted_by_api и опциональные ERP-результаты. Сделка ждёт durable receipt нужной версии клиента. Ограничить поток 5 запросами/с и 2 соединениями на интеграцию; восстанавливать неопределённые исходы через согласованный receipt API. Подключить планировщик, backpressure и метрики.
4. **Секреты и клиентское подключение.** Получить тестовый receiving API-контракт, CA/mTLS и OAuth-параметры. Реализовать выдачу/кэш/ротацию токенов и интеграцию с Key Vault. Настроить Azure/VPN и подтвердить фактический source IP. Не вводить примерные адреса в рабочую конфигурацию.
5. **Security logging.** Подключить реальные источники к устойчивому хранилищу, добавить tenant-authorized HTTPS export с аудитом самой выгрузки, ограничениями объёма/доступа и retention/incident hold. Сам JSONL builder не обеспечивает долговременную запись, неизменяемость архива или полноту источников.
6. **Приёмка.** Проверить потерянное подтверждение, перезапуск worker, конкуренцию, отказ БД/VPN/API, ротацию, чужой tenant, реальные TLS-сертификаты и читаемость пакета клиентом. Только затем ограниченный пилот AAC. Внутреннее сохранение в ERP подтверждает заказчик.

## Предварительные трудозатраты

Это оценка всего объёма нашей стороны, а не обещание календарного срока и не автоматически измеренное время работы агента.

| Этап | Инженерные часы |
| --- | --- |
| Контракт, проверяемое ядро, базовые негативные тесты | 4–6 |
| Транзакционный Outbox, версии, охват путей изменения CRM | 12–18 |
| Worker, подтверждения, recovery/reconciliation, мониторинг | 8–12 |
| Реальные security logs, хранение и защищённая выдача | 6–10 |
| Наша сторона Azure/VPN/секретов и подключение | 6–10 |
| Совместная приёмка, исправления, эксплуатационная передача | 4–8 |
| **Всего** | **40–64** |

Ожидание AAC, дополнительная разработка их приёмника/ERP-адаптера, закупка/создание подписки и изменение согласованного API сюда не входят. После подтверждения источников логов и инфраструктуры оценку необходимо пересмотреть: незнакомый SIEM или отсутствующие аудиты могут расширить объём.

## Проверка и выпуск

Модульные тесты находятся в `src/__tests__/lib-customer-receiver-*.test.ts`; сетевые сценарии используют подменённый транспорт и синтетические данные. Это не проверка реального TLS/VPN/ERP. Выполняется узкий TypeScript check этих файлов и `git diff --check`.

Полный typecheck/build/E2E и PostgreSQL-проверки — отдельные обязательные gates перед выпуском; на Contabo тяжёлые проверки не запускаются. Никаких изменений БД, push, merge, production deploy или изменений работающей сети в этом этапе не выполняется.
