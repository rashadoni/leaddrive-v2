# AAC — реализация клиентского API-коннектора

Дата: 14 октября 2026. Основание: API flow AZ/EN v1.1 и поручение пользователя начать автономную реализацию. Клиент подтверждён: **AAC**.

## Граница текущего результата

Добавлено серверное ядро и конструктор в `src/lib/integrations/customer-receiver/`. В новой странице `/settings/integrations/customer-receiver` и API `/api/v1/integrations/customer-receiver` реализованы сохранение настроек и синтетическая проверка пакетов. **Захват изменений CRM и автоматическая очередь передачи ещё не подключены.** Ни одна операция в работающей CRM не начинает внешнюю отправку от этих изменений. Настоящий приёмный API, организация AAC, Azure/VPN и сертификаты ещё не подключены.

Название AAC — бизнес-идентичность, не подтверждённый `organizationId`. В `clients/registry.json` отдельной AAC-инсталляции нет; это не доказывает отсутствие такой организации в БД. Не использовать ID одноимённой клиентской карточки вместо ID tenant. Шаблон `ops/customer-receiver/aac.test.example.json` намеренно содержит `organizationId: null`, отключённую интеграцию и `exportRule.mode: disabled`. Приложение его не загружает.

## Что реализовано

| Компонент | Поведение |
| --- | --- |
| `contract.ts` | Проверяет предлагаемый JSON v1.0 для клиентов и сделок, возвращает отдельную копию только разрешённых полей. Проверяет UUID, версии, UTC и календарные даты. Контакты/заказы требуют отдельного согласованного профиля и пока не поддержаны |
| `eligibility.ts` | Явные режимы disabled / all_deals / pipeline_stages. Совпадения названия этапа в другой воронке недостаточно. Проверяет организацию и наличие CRM-клиента. Правило AAC ещё не выбрано |
| `delivery.ts` | Стабильный ключ события с tenant/integration/environment; изменение тела не создаёт новый ключ. Проверка точного event/external ID/version в receipt. HTTP 200/201/202 без receipt остаётся неопределённым исходом. Принятые API события не пересылаются из-за отсутствия ERP-статуса |
| `outbox.ts` | Адаптер к существующему `EffectOutbox` через переданную транзакцию. Replay/shadow запрещены. Ошибка записи передаётся вызывающей транзакции. Это ещё не доказательство атомарности всей CRM: подключение команд остаётся следующим этапом |
| `transport.ts` | Один PUT по HTTPS 443 с обязательными CA/mTLS/Bearer. Точный RFC1918 IPv4 привязан к сокету; имя проверяется TLS/SNI. Нет DNS-переходов и HTTP redirects. Ограничения соединения 5 с, всей попытки 30 с, ответа 16 KiB. Существующая защита обычных webhook не изменена |
| `security-events.ts` | Нормализация по разрешённым полям без произвольных сообщений/тел/секретов. UTF-8 JSONL, схема JSON Schema, manifest со счётчиками и SHA-256. Проверка организации и TEST/PROD, явные пробелы покрытия, отсутствие заявления о полноте/подлинности только на основании hash |

Повторы разрешаются только после проверки receipt и подтверждённой долговременной дедупликации у получателя. Чистый планировщик учитывает 1/5/15/60 минут, положительный jitter, `Retry-After` и окно 24 часа. Он не является запущенным worker и не обходит принятую платформой очередь reconciliation.

Денежные значения не проходят через JavaScript Number. CRM хранит `Decimal(18,4)`, предложенный профиль — два знака. Преобразование допускает только нулевые дополнительные знаки; `1500.1234` отклоняется вместо неявного округления. Иная точность должна быть согласована в версии контракта.

Первый фиксированный sender сохраняет предел 256 KiB. Добавлен внутренний sender для подготовленных конструктором пакетов: POST/PUT, проверенный относительный путь, контроль checksum/tenant/environment/selection и пределы из профиля до 1 MiB. Сеть остаётся HTTPS 443 с точным частным IPv4, mTLS и Bearer. IPv6, другой порт и иная аутентификация требуют отдельной доработки. Builder API sender не вызывает.

## Конструктор: подготовленные возможности

- Клиенты, контакты и сделки; разрешённые штатные поля и зарегистрированные в этой организации активные пользовательские поля поддерживаемых простых типов.
- Переименование полей и вложенные JSON-объекты; значения из CRM, системного контекста события или явные константы. Защищённые системные идентификаторы и версия сохраняются; пароли, токены, внутренние заметки и произвольная metadata не входят в каталог.
- До восьми последовательных преобразований: trim, регистр, десятичная строка с точностью 0–4 и явным правилом округления, UTC date/timestamp, префикс/суффикс и таблица соответствия кодов. Неизвестные коды можно отклонять. Дублирующиеся исходные коды не принимаются.
- Правила manual/all/filtered, группы all/any, равенство, списки, заполненность и точное сравнение числовых значений. Числовые налоговые идентификаторы сохраняются строками. Пустая группа filtered не означает «все записи».
- POST/PUT и пути с `{resource}`/`{externalId}`, структура полей receipt, планы manual/on_change/interval, размеры, скорость, concurrency, тайм-ауты и окно повторов. Эти настройки пока описывают будущий runtime; сохранение draft не запускает расписание.
- Создание нескольких профилей TEST/PROD, optimistic concurrency, история до 20 предыдущих версий, восстановление старых настроек с новым номером версии. Общий размер хранимого профиля и истории ограничен 512 KiB; для крупных конфигураций сохраняется меньше предыдущих версий.
- Импорт/экспорт JSON-конфигурации, полный JSON-редактор и точный preview с hash/размером/пропущенными полями. Проверки используют только синтетические данные, включая отсутствующие поля и precision-loss cases.

Страница и API доступны session admin/superadmin своей организации. `organizationId`, секреты, endpoint и активация не принимаются из файла профиля. Tenant-привязка определяется авторизованной session; отдельный ID AAC не требуется для редактирования профиля после регистрации и входа в его инсталляцию. Runtime connection и Azure-реквизиты создаются владельцами инфраструктуры отдельно.

Сохранение профиля и audit фиксируются в одной транзакции. Сравнение версии находится в предикате самого UPDATE. Повреждённые/чужие/активные записи не возвращаются как draft. Тип `customer-receiver-draft` зарегистрирован как dedicated: общий API каналов не может создать, изменить, удалить или активировать эти профили.

Для реальных данных подготовлены `constructor/source.ts` и `prisma-source.ts`: выбор только разрешённых столбцов, проверка org/id каждой записи и связанного клиента, чтение зарегистрированных custom values, lossless Decimal и UTC snapshots. Они пока не вызываются из публичного preview API. `receipts.ts` проверяет aliases ответа и точное совпадение event/external ID/version; HTTP-успех сам по себе не становится ERP-подтверждением.

## Журнал самого конструктора

Метаданные чтения, создания/изменения профиля, preview и выгрузки записываются в AuditLog. Ошибка обязательной записи audit не выдаётся за успешную операцию. В лог не копируются пакеты, значения полей, константы или секреты.

`GET /api/v1/integrations/customer-receiver/logs` выдаёт авторизованному администратору JSONL, JSON Schema и manifest с counts/SHA-256 за UTC-период до 31 дня, до 5000 событий. Превышение требует уменьшить период, а не даёт незаметное усечение. В интерфейсе доступны три файла одного сформированного пакета. Повторный экспорт сохраняет event IDs и содержимое старых событий; recorded/observed timestamp берётся из исходного AuditLog, ingested_at остаётся неизвестным.

**Scope этой выгрузки — только constructor configuration/read/preview/export.** Разделение TEST/PROD здесь относится к целевой среде профиля, а не доказывает среду/регион физической CRM-инсталляции. Это не аттестация всего security logging. Azure/VPN/WAF, остальные CRM auth/access events, ERP и клиентский приёмник явно исключены из manifest. Срок хранения в профиле является проектной настройкой; он не изменяет существующую DB-retention или WORM-политику.

## Следующие этапы и критерии готовности

1. **Идентичность AAC и бизнес-правило.** Подтвердить фактический tenant ID будущей инсталляции и правило all_deals либо конкретную воронку/этапы. Утвердить поля, валюты, точность и обязательные реквизиты. Ни одна пустая настройка не означает «передавать всё».
2. **Транзакционное подключение CRM.** Добавить durable версии сущностей и связи зависимостей. Сохранение клиента/сделки, снимка разрешённых полей и Outbox должно происходить в одной tenant-транзакции. Покрыть API, импорт, конвертацию лида и прочие фактические пути изменения; не ограничиваться REST POST. Проверить rollback и конкурентные версии на PostgreSQL.
3. **Worker и reconciliation.** Применить существующие lease/attempt/state-machine guards `EffectOutbox`; не писать статусы произвольно. Отдельно хранить accepted_by_api и опциональные ERP-результаты. Сделка ждёт durable receipt нужной версии клиента. Ограничить поток 5 запросами/с и 2 соединениями на интеграцию; восстанавливать неопределённые исходы через согласованный receipt API. Подключить планировщик, backpressure и метрики.
4. **Секреты и клиентское подключение.** Получить тестовый receiving API-контракт, CA/mTLS и OAuth-параметры. Реализовать выдачу/кэш/ротацию токенов и интеграцию с Key Vault. Настроить Azure/VPN и подтвердить фактический source IP. Не вводить примерные адреса в рабочую конфигурацию.
5. **Security logging.** Подключить реальные источники к устойчивому хранилищу, добавить tenant-authorized HTTPS export с аудитом самой выгрузки, ограничениями объёма/доступа и retention/incident hold. Сам JSONL builder не обеспечивает долговременную запись, неизменяемость архива или полноту источников.
6. **Приёмка.** Проверить потерянное подтверждение, перезапуск worker, конкуренцию, отказ БД/VPN/API, ротацию, чужой tenant, реальные TLS-сертификаты и читаемость пакета клиентом. Только затем ограниченный пилот AAC. Внутреннее сохранение в ERP подтверждает заказчик.

## Проверка и выпуск

Модульные тесты находятся в `src/__tests__/lib-customer-receiver-*.test.ts`; сетевые сценарии используют подменённый транспорт и синтетические данные. Это не проверка реального TLS/VPN/ERP. Выполняется узкий TypeScript check этих файлов и `git diff --check`.

На текущем checkpoint: 194 tests PASS в 9 файлах (kernel, constructor, API ownership/revision/audit, source, receipts, transport и регрессия event-platform). Scoped strict TypeScript для kernel/constructor без Prisma-adapter и для UI PASS. Prisma validate/generate выполнены для существующей неизменённой схемы с синтетическим URL без подключения к БД.

Реальный UI-компонент проверен в браузере со standalone локальным синтетическим API: RU/EN/AZ, 1440x1050/390x900, save/preview, keyboard tabs, precision choice, conflict/reload, history restore, audit files, export/import. Ни одного внешнего запроса и page error. Доказательства — `docs/evidence/customer-receiver-builder-2026-10-14/result.json` и screenshots. Это не полная Next-page/production/DB проверка.

NOT RUN / CI REQUIRED: полный application typecheck, lint/build, PostgreSQL/RLS/rollback/CAS и фактический Prisma-adapter. Даже scoped check, включивший большую generated Prisma-схему, достиг 2 GiB heap limit; heap на Contabo не увеличивался. Адаптер отделён от чистого engine, чтобы обязательную широкую проверку выполнить в CI/выделенном worker. NOT RUN: live OAuth/mTLS/VPN/customer API/ERP/SIEM — реквизиты и среды не предоставлены.

Schema, рабочая сеть и production не изменены. Следующий самостоятельный этап — durable capture/worker и его PostgreSQL-проверки; он ещё не завершён. Перед настоящей передачей необходимы также receiving API-контракт, тестовый endpoint, сертификация/авторизация, Azure/VPN и приёмка. Наличие конструктора не означает готовность всего обмена.
