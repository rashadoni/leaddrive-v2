## 2. Что берём из образца

Сквозное правило ролика: **ИИ предлагает — человек решает одним нажатием —
решение записано с именем.** У каждого предложения: причина одной фразой,
выигрыш цифрой, «сейчас против предлагаю», кнопки «Отклонить / Подробнее /
Одобрить». Всё, что предложил ИИ, нарисовано пунктиром (на карте и на шкале
времени); принятое становится сплошным.

| Экран ролика | У нас |
|---|---|
| Главная: 6 чисел, проблемный рейс с машиной, «Operations brief» (причины с весом, 3 предложения, одна кнопка), мини-карта, шкала дня по водителям | §5 Главная диспетчера |
| Dispatch: очередь грузов · карта (красный — пробка, фиолетовый пунктир — объезд) · «Dispatch Agent» с пронумерованными предложениями и блоком «сделано само» | §5 Диспетчерская |
| «Approve route change?»: две карточки «Сейчас / Предлагаю», строки последствий, «записано в журнал», штамп APPROVED | §5 Окно решения |
| Карточка рейса: машина с выносками, путь с объездом, отчёт агента «Что случилось / Почему / Рекомендация» + 3 цифры + «Одобрил X в 11:58», лента событий, схема загрузки, нагрузка по осям, документы | §5 Карточка рейса |
| «Share live tracking»: ссылка, кому, что видно (3 переключателя), срок ссылки, «Отправить» | §5 Ссылка клиенту |
| Live tracking: список машин · карта с легендой · панель машины (скорость, температура, топливо, часы за рулём, прогресс к окну, итог агента) | §5 Живое отслеживание |

**Правило визуала (владелец):** каждая часть картинки несёт живые данные.
Нет источника данных — нет элемента, а не выдуманное число.

## 3. Что уже есть в коде (разведка 2026-11-01)

  в `src/lib/tenant-capabilities.ts`: `route-field`, `workforce-hrm`,
  `personnel`. «Учёт рабочего дня» (`personnel`) с 2026-10-14 продаётся без

  (`application` VarChar(16), значения сейчас `TIME` и `ROUTE_FIELD`;
  проверки — `src/lib/identity/application-actor.ts`,
  `application-enrollment.ts`, `activation.ts`).

  `src/lib/mtm/road-distance.ts`, `map-matching.ts`.
- **Порядок объезда** — `src/lib/mtm/route-order.ts` (#1230): один агент, до 25
  точек, визит 30 мин, опоздание = приезд позже слота + 10 мин; без
  вместимости и без окон «с–до».
- **Уведомления о маршруте** — `MtmRouteNotificationOutbox` → колокольчик + пуш

## 4. Архитектура

### 4.1 Модуль — четвёртая возможность `logistics`

`logistics` добавляется в `FIELD_TENANT_CAPABILITY_IDS` по образцу
`personnel`: своя подписка, своё меню «Логистика», продаётся без Route & Field
и вместе с ним. Обёртки: `withLogisticsRlsAuth` (веб + телефон),
`withLogisticsWebRlsAuth`; мобильная возможность `logistics` в
`MobileEndpointCapability`.

### 4.2 Ядро — общее, фармацевтика — нет

Таблицы ядра не переименовываются и не выносятся: префикс `Mtm` в коде остаётся,
клиент его не видит. Меняется только то, **кого пускают**:

| Часть | Кому |
|---|---|
| Карточка сотрудника, вход в приложение, смена и перерывы, приём GPS, живая карта, история движения, километры по дорогам, пуш, задачи, сообщения, тревоги | `route-field` **или** `logistics` — новая обёртка `withFieldCoreRlsAuth` |
| Визиты, клиенты MTM, врачи, KPI, покрытие, акции, презентации, оценки визитов | только `route-field`, как сейчас |
| Учёт рабочего дня | `personnel`, как сейчас |
| Машины, рейсы, доставка, решения, ссылка клиенту | только `logistics` |

### 4.3 Человек: роль — это права, вид работы — это допуск

- Водитель — та же карточка `MtmAgent`. Новой роли в `MtmAgentRole` **нет**.
- Вид работы — допуск приложения: `IdentityApplicationGrant.application =
  "LOGISTICS"` (роль `DRIVER` / `DISPATCHER` / `LOADER` внутри допуска).
  Мерчендайзер, который иногда возит, получает два допуска при одной карточке.
- Приложение — своё (§4.7), вход тот же: допуск `LOGISTICS` пускает в него.

### 4.4 Свои таблицы модуля

Все — с `organizationId`, `FORCE ROW LEVEL SECURITY`, политикой
`tenant_isolation`; персональные поля (имя и телефон получателя) — шифруются
ключом организации и проходят `lint:pii-columns`.

| Таблица | Что хранит |
|---|---|
| `LogisticsVehicle` | номер, класс (`TRAILER_TRUCK` фура, `TRUCK` 5–10 т, `VAN` фургон 3,5 т, `SMALL_VAN` Dokker/каблук), кузов (`REEFER`, `TENT`, `BOX`, `ISOTHERM`), вместимость кг / м³ / паллеты, размеры кузова, диапазон температуры, состояние. Класс подставляет типовые значения, их можно поправить |
| `LogisticsTrip` | машина, водитель (`MtmAgent`), дата, состояние `PLANNED → LOADING → LOADED → IN_TRANSIT → COMPLETED / CANCELLED`, `version` / `publishedVersion`, план погрузки (JSON клеток), время старта и конца |
| `LogisticsStop` | рейс, порядок, вид (`PICKUP` / `DROP`), получатель: клиент MTM (`customerId`, необязателен) **или** свой адрес + координаты + имя/телефон; окно «с–до», минуты выгрузки, плановое и живое время приезда, состояние `PENDING / ARRIVED / DONE / FAILED / SKIPPED`, причина отказа |
| `LogisticsCargo` | рейс, точка выгрузки, источник (`sourceType`: `BUYER_ORDER` / `PHARMACY_PHONE_ORDER` / `ERP_DOCUMENT` / `MANUAL` + `sourceId`), **снимок** содержимого (описание, места, вес, объём, паллеты), место в кузове |
| `LogisticsProofOfDelivery` | точка, кто принял, подпись и фото (файлы — запечатаны ключом организации), координаты и время, ключ идемпотентности телефона |
| `LogisticsDecision` | журнал решений: вид (`REORDER` / `REROUTE` / `REASSIGN` / `NOTIFY`), предложение «сейчас / предлагаю» с цифрами, причина фразой, кто предложил (ИИ / человек), `PROPOSED → APPROVED / REJECTED / EXPIRED`, кто и когда решил, чем кончилось. Строки не правятся, только дописываются |
| `LogisticsTrackingLink` | ссылка клиенту на точку рейса: хеш токена, кому отправлена, что видно (карта и время / температура / водитель), срок, отзыв |

Почему не `MtmRoute` + `MtmVisit`: визит кормит KPI, покрытие, оценки и
акции; доставка, записанная визитом, их исказит. Почему не `MtmCustomer` для
всех получателей: у транспортной компании получатели разовые, база клиентов
MTM с закреплёнными агентами для них не подходит.

`LogisticsCargo` держит снимок, а не только ссылку: источник живёт в другом
модуле, без внешнего ключа, и удаление заказа не должно ломать историю рейса
(урок `PaymentRegistryEntry` из CLAUDE.md — у ссылки без FK нет уборщика).

### 4.5 Расчёты

- **Время приезда** — тот же `road-router.ts` (OSRM `table` / `route`).
- **Порядок объезда одной машины** — `route-order.ts` расширяется окнами
  «с–до» и минутами выгрузки по объёму; правило «показывать, только если
  выигрыш ≥ 3 мин и ≥ 5 % или больше точек в окне» остаётся.
- **Живое время в пути** — пересчёт каждые N минут по активным рейсам в
  фоновом процессе `leaddrive-v2-jobs` (не в веб-процессе: CLAUDE.md, «Фоновые
  задачи идут в свой процесс»). Риск = живое время приезда позже конца окна.
- **Распределение по машинам** (вместимость + окна + несколько машин) — не свой
  алгоритм, а VROOM (открытый, работает поверх нашего OSRM) отдельным
  контейнером рядом с OSRM. Этап 6.
- **Грузовик** — второй граф OSRM с грузовым профилем, собирается в CI как
  первый. Этап 6. До него класс `TRAILER_TRUCK` получает время приезда с
  пометкой «по легковым дорогам».

### 4.6 Связи с другими модулями

- Заказы и склад модуль **читает**. Склад не меняет (правило карточек ERP).
- Доставка обновляет `OrderShipment.status` (`in_transit` / `delivered`) через
  его же машину состояний `src/lib/oms/shipment-state-machine.ts` — у отгрузки
  не появляется второй статус.
- Вес и объём: дистрибьютору — из 1С (нужно попросить программиста 1С отдавать
  «Вес» и «Объём» номенклатуры); транспортной компании — из накладной клиента
  (ввод диспетчера, Excel, API).

### 4.7 Приложение водителя

**Отдельное приложение из того же кода — по образцу LeadDrive Time.** Учёт
рабочего дня уже выпускается отдельным APK `com.leaddrive.attendance` из
репозитория `rashadoni/leaddrive-mtm` (свой канал `time-stable`, свои теги
`time-v…`, манифест `src/lib/mtm/time-app-release-manifest.json`). Так же:
«LeadDrive Логистика» — своё имя, значок, пакет и канал выпуска, но общий код
входа, синхронизации, GPS, офлайн-очереди и фото с Route Field. Почему не
экраны внутри Route Field: водителю не нужны визиты и презентации; модуль
продаётся отдельно; Google Play требует обоснование фоновой геолокации для
каждого приложения, и «отслеживание доставки» — чистое обоснование. Человек с
двумя допусками ставит оба приложения — это редкий случай. Кладовщик —
в том же приложении, экраны по его роли в допуске.

- Начало смены — выбор машины.
- Список точек с окнами и временем приезда; «Открыть в навигаторе» (Google
  Maps / Waze). Своей карты в кабине нет, пока не выбран поставщик (§7.3).
- «Приехал → Выгрузил (подпись + фото) / Не доставлено (причина)» работают без
  сети: очередь на телефоне с ключом идемпотентности, сервер принимает повтор
  как тот же шаг.
- Кладовщик: «Погружено» по плану погрузки.

### 4.8 Приватность

- Телефон водителя подчиняется правилу перерыва без исключений.
- Положение **машины** (не человека) в перерыв — только от трекера в машине и
  только после решения владельца (§7.2).
- Ссылка клиенту показывает машину, только когда его точка — следующая; до
  этого — только время приезда. Имя и телефон водителя по умолчанию выключены.
  Чужие точки рейса не видны никак.

### 4.9 Визуал — «живая машина» и схема кузова

- **Изображения машин** — своя серия рендеров, 4 класса × кузов, один угол
  (3/4 спереди), один свет, белый фон, без марок и логотипов. Каждый рендер —
  слои: основа, маска кузова (под заливку загрузки), свечение состояния.
  Статика — по правилу «новое имя + md5» (CLAUDE.md, статика на проде).
- **Выноски привязаны к узлам машины** (координаты узлов — JSON на класс):
  кабина — водитель, телефон, до перерыва; кузов — места, вес, заполнение %;
  холодильник — температура против нормы; двери — последнее открытие;
  колёса — скорость и «−N % от плана»; бак — топливо или «по норме».
  У каждой выноски один источник; нет источника — нет выноски.
- **Цвет состояния** — вовремя / под риском / опаздывает; ИИ — один акцентный
  цвет на все предложения. Правила MTM действуют и здесь: без бледных
  заливок (`mtm-calm-colours`), таблица в `overflow-x-auto`, текст не мельче
  12 px — оформление ролика переносится в этих рамках.
- **Схема кузова сверху** строится из размеров кузова и груза рейса: клетка —
  паллета или место, цвет — получатель. Это **план погрузки**: последняя точка
  — в глубину, первая — у дверей. Выгруженное исчезает. Если порядок точек
  меняют после «Погружено», окно решения предупреждает: «груз для точки N в
  глубине кузова».
- **Парк в масштабе** — машины рядом, в одном масштабе, кузов залит по
  загрузке, свободное место цифрой.

## 6. Этапы и задачи

Первый клиент (§7.1) определяет порядок: для дистрибьютора со своими фургонами
этап 6 не нужен вовсе; для транспортной компании с фурами он идёт сразу после 3.

### Этап 0 — каркас модуля

- **L0.1 Возможность `logistics`.** Определение в `tenant-capabilities.ts`,
  включение в админке организации, обёртки `withLogisticsRlsAuth` /
  `withLogisticsWebRlsAuth`, мобильная возможность.
  *Готово, когда* организация без `logistics` получает 403 на любом маршруте
  модуля, с ней — 200; тест гоняет все маршруты модуля, как
  `finance-api-authorization.test.ts`.
- **L0.2 Ядро пускает обе подписки.** `withFieldCoreRlsAuth` на GPS, смене,
  живой карте, истории, задачах, сообщениях, пуше.
  *Готово, когда* тест-матрица на настоящем Postgres: организация только с
  `logistics` пишет GPS и открывает смену, но получает 403 на визитах, клиентах
  MTM, KPI, акциях; организация только с `route-field` — ничего не потеряла;
  правило перерыва действует для обеих.
- **L0.3 Допуск `LOGISTICS`.** Значение в `IdentityApplicationGrant`, проверки
  в `application-actor.ts` / `application-enrollment.ts` / `activation.ts`;
  в карточке сотрудника — «Вид работы»: агент / мерчендайзер / водитель /
  диспетчер / кладовщик.
  *Готово, когда* водитель входит в приложение и видит только экраны водителя;
  агент — как раньше.
- **L0.4 Меню «Логистика».** Раздел в навигации, пустые экраны с понятным «что
  здесь будет», скрытие фармацевтических разделов у организации без
  `route-field`.
- **L0.5 Демо в LeadDrive Inc.** Машины, водители, рейсы; машины едут по
  рейсам тем же демо-пульсом (`demo-pulse*.ts`), что и демо-агенты.
- **L0.6 Механизмы ядра для логистики** (§3.1, строки «механизм»): строки
  «что может водитель» в `agent-permissions.ts`, тревоги логистики в общем
  потоке тревог, зоны «склад / рампа», отчёты и Excel — каждый подключается в
  своей задаче ниже, а не пишется заново.

### Этап 1 — машины и рейсы (макет обязателен)

- **L1.1 Таблицы** `LogisticsVehicle`, `LogisticsTrip`, `LogisticsStop`,
  `LogisticsCargo` + миграция с RLS + шифрование полей получателя.
  *Готово, когда* `find-context-gaps.py` — 0, тест на Postgres доказывает
  изоляцию организаций.
- **L1.2 Экран «Машины»**: список, добавление, класс подставляет вместимость.
- **L1.3 Создание рейса из заказов**: дистрибьютору — телефонные заказы и
  `BuyerOrder` на дату, получатели — его клиенты; окна «с–до»; часы приёма
  получателя с подсказкой «приём закрывается в 14:30»; приоритет; груз —
  снимком; адрес → координаты через `geocode.ts`.
- **L1.4 Путь и время** — расширение #1230, не новый расчёт: путь по дорогам,
  время приезда у каждой точки, «опоздает», «есть порядок лучше» с окнами и
  минутами выгрузки; в таблицу сравнения добавить топливо по норме машины и
  CO₂; возврат на склад; метки «поднят на N», «было опоздание — исправлено»;
  перетаскивание с пересчётом «рано / поздно» (макет Reorder этапа 1).
  *Готово, когда* на настоящем OSRM прода (вымышленные точки) окно
  учитывается: перестановка, сажающая точку вне окна, не предлагается.
- **L1.5 Публикация водителю**: пуш на его языке через тот же outbox, что у
  маршрутов (#1231); квитанция телефона (`mobile-route-command-receipt.ts`) —
  диспетчер видит «водитель получил».

### Этап 3 — контроль окна и решения (макет обязателен)

- **L3.3** Предложения: перестановка точек; передача точки другой машине

- **L3.4** Окно решения «Сейчас / Предлагаю», штамп, «Одобрил X в ЧЧ:ММ» на

  · ждут решения M» (механизм `panel-attention.ts`). Сводка «что не так и
  почему» с уверенностью цифрой и страница «что сделал ИИ» (журнал решений).
- **L3.6** Новый рейс, заполненный ИИ: из PDF, письма или заказа — поля,
  заполненные ИИ, подсвечены, «N полей, M проверить», «ничего не уйдёт, пока
  не создадите». Ставка рейса — только по своим прошлым рейсам этого
  направления; рыночной цены у нас нет, не показывать.
- **L3.7** Автоназначение «Распределить N рейсов?»: рейс → водитель и машина,
  «почему эта пара», % совпадения, снять галочку, «ждёт слота на рампе»,
  запись в журнал. Сначала простое правило (свободна, ближе, хватает места и
  часов смены), VROOM — этап 6. % вовремя водителя — по журналу доставок.
  *Готово, когда* опоздание, заданное вручную на стенде, через один цикл
  пересчёта даёт предложение; «Одобрить» меняет рейс, водитель получает пуш,
  в журнале — имя, причина, цифры.
