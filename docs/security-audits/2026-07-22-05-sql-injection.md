# Security audit #5 — SQL-инъекции

Дата: 2026-07-22  
Режим: read-only static audit, без запросов на изменение production-данных

## Итог

Подтверждённой SQL-инъекции в проверенных production API-поверхностях не найдено.
Пользовательские значения в raw SQL передаются параметрами (`$1`, `$2`, …) или
через `Prisma.sql`/`Prisma.join`, а не конкатенируются в SQL-текст.

## Что проверено

- Все вхождения `$queryRaw`, `$executeRaw`, `Prisma.sql` и unsafe-вариантов в
  `src/`, `prisma/` и runtime-скриптах.
- Векторный поиск KB и контрактов, reindex и cron backfill embeddings.
- Динамическое удаление tenant-контента.
- Blind-index backfill с динамическими именами таблиц/колонок.
- Аналитические SQL-фильтры inbox и SQL-операции блокировок/агрегаций.

## Проверенные поверхности

### `src/lib/ai/embeddings.ts`

`$queryRawUnsafe`/`$executeRawUnsafe` используют плейсхолдеры для
`vectorStr`, `orgId`, `limit`, текста и ID. SQL-текст статичен; прямой ввод в
него не попадает. `limit` дополнительно ограничен на API-поверхности semantic
search диапазоном 1–50 через Zod.

### Contract semantic search и reindex

Raw-запросы параметризованы. `contractId` перед записью проверяется через
`findFirst({ id, organizationId })`; поиск ограничен `organizationId` на обеих
сторонах JOIN. Подстановки vector/text/IDs выполняются параметрами.

### `src/lib/crypto/blind-index-backfill.ts`

Имена таблиц и колонок берутся только из закрытых allow-list констант
(`TABLES`, `WIRED_COLUMNS`). Значения и лимит передаются параметрами. Это
допустимое исключение для `$queryRawUnsafe`, но оно требует сохранения
allow-list при добавлении новых сущностей.

### `src/lib/tenant-provisioning.ts`

Имя таблицы берётся из `information_schema`, проходит строгую проверку
`^[a-z_][a-z0-9_]*$` и исключается из preserve-list; `orgId` параметризован.
Инъекция через имя таблицы не подтверждается.

## Findings

### SEC-05-1 — Использование `$queryRawUnsafe` как поддерживаемый residual risk

Severity: P2 (hardening, exploit не подтверждён)

Несколько runtime-модулей используют unsafe API даже при полностью
параметризованных запросах. Это не является текущей SQL-инъекцией, но повышает
риск будущей ошибки: добавление `${userInput}` в SQL-текст может обойти обычный
review.

Рекомендации:

1. Для статических запросов перейти на tagged `$queryRaw`/`$executeRaw` там, где
   не нужны динамические идентификаторы.
2. Для динамических идентификаторов оставить только allow-list и добавить
   unit-тест, который отвергает неизвестное имя.
3. Добавить CI-проверку, блокирующую unsafe raw API в `src/app/api`, кроме
   явно разрешённого списка с комментариями.
4. Не использовать строковую конкатенацию SQL даже для «внутренних» cron-
   маршрутов.

## Вердикт

Статический аудит закрывает SQL-инъекцию как подтверждённую уязвимость: **нет
подтверждённых находок**. Остался отдельный hardening-пункт SEC-05-1. Его
исправление не выполнялось до отдельного разрешения.
