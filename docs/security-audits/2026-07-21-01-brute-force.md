# Отчёт безопасности №1: brute force и защита входа

- Проект: LeadDrive v2
- Проверенный код: `origin/main` на commit `29d6a479c`
- Дата: 2026-07-21
- Метод: анализ кода, конфигурации и локальных тестов
- Production: активные запросы не выполнялись
- Решение: `УЯЗВИМО`
- Приоритет категории: `P1 / высокий`

## Краткий вывод

В проекте есть базовая защита основного CRM-входа и усиленная защита мобильного
MTM-входа, но всю категорию нельзя считать защищённой по двум подтверждённым
причинам:

1. клиент может снять признак незавершённой 2FA-проверки через обновление
   сессии без проверки серверного nonce;
2. парольный вход клиентского портала фактически не проходит через rate limit.

Дополнительно основной CRM-вход ограничивается только по IP в памяти одного
процесса. Это замедляет простой перебор с одного адреса, но не защищает целевой
аккаунт от распределённого перебора и сбрасывается при перезапуске процесса.

Исправления в рамках диагностического этапа не вносились.

## Инвентаризация поверхностей

| Поверхность | Механизм | Текущая защита | Результат |
|---|---|---|---|
| CRM web | NextAuth Credentials | 10 POST/мин на IP в middleware | Частично защищено |
| CRM OAuth | Google / Microsoft Entra ID | Защита провайдера; app-level 2FA не подтверждается | Не подтверждено |
| MTM mobile | Email + пароль → JWT | 10 POST/мин на IP в middleware и 5/мин на IP+email+tenant в route | Частично защищено |
| Client portal | Email + пароль → portal JWT | Достижимого rate limit нет | Уязвимо |
| TOTP 2FA | 6 цифр / backup code | 10 POST/мин на IP, но завершение 2FA обходится | Уязвимо |
| SMS 2FA | OTP | 5 проверок на OTP; send: 3/телефон и 10/IP за 10 мин | Частично защищено |
| Восстановление CRM-пароля | Email token | Токен 256 бит, срок 1 час; middleware-маршрутизация некорректна | Функционально заблокировано |
| Portal registration/set-password | Email token | 256-битный token, 24 часа; общий public limit недостижим | Частично защищено |

## Подтверждённые находки

### BF-01 — 2FA можно завершить без проверки второго фактора

- Статус: `УЯЗВИМО`
- Приоритет: `P1 / высокий`
- Поверхность: CRM TOTP и SMS 2FA, включая пользователей с `require2fa`

Серверные endpoints проверки TOTP/SMS создают случайный `twoFactorNonce` и
сохраняют его пользователю. Клиент передаёт nonce в `session.update(...)`.
Однако JWT callback не сравнивает переданный nonce со значением в базе:

- `src/app/api/v1/auth/verify-2fa/route.ts:62-74` — выдача nonce после TOTP;
- `src/app/api/v1/auth/verify-sms-2fa/route.ts:45-57` — выдача nonce после SMS;
- `src/app/(auth)/login/verify-2fa/page.tsx:65` — передача nonce клиентом;
- `src/lib/auth.ts:303-310` — очистка `needs2fa`/`needsSetup2fa` только по
  значениям из клиентского update, без чтения или сравнения nonce.

Установленная версия Auth.js передаёт тело клиентского обновления в JWT
callback как `session` с `trigger: "update"`:
`node_modules/@auth/core/src/lib/actions/session.ts:42-54`.

Следствие: после успешного ввода только пароля пользователь уже получает JWT с
`needs2fa`. Обладатель этого JWT может запросить обновление сессии со значением
`needs2fa: false`; знание TOTP/SMS-кода или `twoFactorNonce` сервером не
проверяется. После перевыпуска JWT проверки middleware и `requireAuth` видят
2FA как завершённую.

Это снижает 2FA до UI-барьера и делает её неспособной остановить захват
аккаунта после подбора или утечки пароля.

### BF-02 — вход в client portal не ограничен по частоте

- Статус: `УЯЗВИМО`
- Приоритет: `P1 / высокий`
- Поверхность: `POST /api/v1/public/portal-auth`

`RATE_LIMITED_PATHS` не включает portal login. Общий limiter для
`/api/v1/public/*` присутствует ниже в middleware, но до него выполнение не
доходит:

- `src/middleware.ts:36` — `/api/v1/public` входит в `publicPaths`;
- `src/middleware.ts:249-263` — auth limiter не совпадает с portal login;
- `src/middleware.ts:296-307` — public path немедленно возвращает
  `NextResponse.next()`;
- `src/middleware.ts:321-348` — общий public POST limiter расположен после
  раннего return и недостижим;
- `src/app/api/v1/public/portal-auth/route.ts:7-121` — route-level limiter
  отсутствует.

Безопасный локальный диагностический тест принудительно заставлял
`checkRateLimit` возвращать `false`. Portal login всё равно прошёл middleware со
статусом 200, а limiter не был вызван. Временный тест после проверки удалён.

Следствие: атакующий может выполнять неограниченное число сравнений пароля для
контакта портала, ограничиваясь только производительностью приложения и
внешней инфраструктурой.

### BF-03 — основной CRM limiter не защищает целевой аккаунт

- Статус: `ЧАСТИЧНО ЗАЩИЩЕНО`
- Приоритет: `P2 / средний`

Основной вход ограничен 10 POST-запросами в минуту на IP:

- `src/middleware.ts:77` — перечень auth-маршрутов;
- `src/middleware.ts:249-263` — ключ `auth:<ip>`;
- `src/lib/rate-limit.ts:6-18` — порог `public = 10/мин`;
- `nginx/leaddrive.conf:54-64` — canonical Nginx перезаписывает `X-Real-IP`;
- `ecosystem.config.cjs:7-12` — текущая заявленная топология: один PM2 fork.

Ограничение не имеет отдельного ключа по нормализованному аккаунту/tenant.
Смена исходных IP создаёт новые buckets для одного и того же пользователя.
Хранилище является process-local `Map`, очищается при рестарте и не разделяется
между процессами (`src/lib/rate-limit.ts:35-40`).

Таким образом, защита эффективна против простого скрипта с одного адреса, но не
против распределённого перебора. Проверять это активными запросами к production
не требовалось и не разрешалось; найденный в репозитории
`scripts/test_rate_limit.py` не запускался.

### BF-04 — MFA не является обязательным или единообразным барьером

- Статус: `ЧАСТИЧНО ЗАЩИЩЕНО`
- Приоритет: `P2 / средний`

- Для CRM-пользователя `require2fa` по умолчанию равен `false`
  (`prisma/schema.prisma:507`). Администратор может включить требование вручную.
- У client portal и MTM mobile нет второго фактора в парольном login flow.
- OAuth JWT callback не устанавливает `needs2fa`/`needsSetup2fa` из записи
  пользователя. Эти признаки переносятся только из результата Credentials
  provider (`src/lib/auth.ts:298-301`). Защита может обеспечиваться внешним
  провайдером, но требование/assurance level со стороны LeadDrive не проверяется.
- Даже там, где CRM 2FA включена, действует BF-01.

### BF-05 — ответы и аудит неудачных входов неоднородны

- Статус: `ЧАСТИЧНО ЗАЩИЩЕНО`
- Приоритет: `P2 / средний`

Положительные свойства:

- CRM UI показывает одинаковое сообщение о неверных credentials;
- forgot-password route возвращает одинаковый текст для существующего и
  несуществующего email;
- MTM записывает `MOBILE_LOGIN_FAILED` и отдельный `RATE_LIMITED` event.

Недостатки:

- portal login отличает несуществующий контакт, отключённый portal access,
  отсутствие пароля и неверный пароль кодами/сообщениями
  (`src/app/api/v1/public/portal-auth/route.ts:50-73`);
- MTM различает `Organization not found`, `Agent not found` и
  `Invalid password` (`src/app/api/v1/mtm/mobile/auth/route.ts:99-100,161-162,225-238`);
- CRM пишет причины отказа только в server console и не создаёт долговечного
  security event по аккаунту; оповещение или автоматическая реакция на
  распределённые неудачи не обнаружены;
- при отсутствующем CRM-кандидате bcrypt не выполняется, а при существующем
  выполняется, поэтому одинаковый UI-ответ не гарантирует одинаковую стоимость
  обработки (`src/lib/auth.ts:101-110`,
  `src/lib/auth-credentials.ts:85-93`).

### BF-06 — recovery API не согласован с public middleware

- Статус: `ЧАСТИЧНО ЗАЩИЩЕНО` (availability/response defect)
- Приоритет: `P2 / средний`

Страницы `/forgot-password` и `/reset-password` публичны, но вызываемые ими API
`/api/v1/auth/forgot-password` и `/api/v1/auth/reset-password` не входят в
`publicPaths`. Reset route попадает в rate limit, после чего unauthenticated
request перенаправляется на login; forgot route не попадает и в auth limiter.
Route unit tests вызывают handlers напрямую и не проверяют связку middleware +
handler.

Это не даёт атакующему обхода авторизации, но мешает легитимному восстановлению
после атаки и оставляет защиту recovery flow непроверенной end-to-end.

## Подтверждённые защитные свойства

- Canonical Nginx-конфигурация перезаписывает `X-Real-IP` значением
  `$remote_addr`, поэтому произвольный клиентский `X-Real-IP` не должен
  приниматься приложением при соответствии production-конфигурации репозиторию.
- Основной CRM credentials flow использует bcrypt и минимум 8 символов.
- MTM mobile имеет дополнительный route-level bucket 5/мин по хешированному
  сочетанию IP+email+tenant и записывает события неудачи/лимита.
- SMS OTP одноразовый, хранится в виде bcrypt hash, действует 10 минут и
  блокируется после 5 ошибочных проверок одного кода.
- Отправка SMS OTP ограничена по телефону и IP.
- Password reset token CRM создаётся через `crypto.randomBytes(32)`, действует
  один час и очищается после использования.
- Успешная смена/reset CRM-пароля обновляет `passwordChangedAt`, что используется
  для отзыва старых CRM-сессий.

## План устранения

Исправления предлагается выполнять как один security-slice категории №1, но с
отдельными checkpoint-коммитами и проверкой после каждого блока.

1. Закрыть BF-01 первым:
   - JWT callback очищает `needs2fa`/`needsSetup2fa` только при совпадении
     одноразового server-side nonce с пользователем из `token.sub`;
   - nonce потребляется атомарно и имеет короткий срок жизни;
   - произвольное `session.update({ needs2fa: false })` не меняет JWT;
   - добавить отрицательные тесты для отсутствующего, неверного, просроченного и
     повторно использованного nonce.
2. Закрыть BF-02 и недостижимый public limiter:
   - переместить public rate limiting перед ранним public return;
   - добавить portal-login reinforcement по IP и по хешированному
     `tenant+normalizedEmail`;
   - добавить тесты 429 непосредственно для portal handler и middleware.
3. Усилить CRM/MTM/recovery:
   - ввести общий распределённый limiter (Redis уже присутствует в
     dependencies) с отдельными buckets по IP и principal;
   - не использовать жёсткую долгую блокировку аккаунта, которую можно
     превратить в DoS; применять progressive delay/короткий cooldown;
   - сделать recovery API явно публичными и дать им собственные IP+account
     limits;
   - добавить интеграционный тест страница → middleware → handler.
4. Привести MFA к политике:
   - обязательно требовать MFA для `admin` и `superadmin`;
   - определить второй фактор для portal и MTM либо явно принять остаточный
     риск;
   - для OAuth проверять допустимый assurance level внешнего IdP или проводить
     app-level challenge.
5. Снизить enumeration и улучшить обнаружение:
   - унифицировать внешние ответы login flows;
   - выполнять dummy bcrypt work при отсутствии principal;
   - писать нормализованные security events успеха, отказа и лимита без паролей,
     OTP и полных персональных данных;
   - оповещать о серии неудач по одному principal из разных IP.
6. После реализации выполнить targeted tests, полный auth/security test sweep,
   `npx tsc --noEmit`, `npm run build` (изменяется auth boundary), а затем —
   только при отдельном разрешении — staging smoke тестовыми аккаунтами.

## План отката

- Каждый блок выполняется отдельным commit.
- При ошибке MFA сначала откатывается только nonce-validation commit; нельзя
  временно разрешать клиенту самостоятельно снимать 2FA.
- При проблеме distributed limiter допускается переключение на старый IP limiter
  только через явный аварийный флаг с коротким сроком и журналированием.
- Изменения recovery/public routing откатываются отдельно от MFA.

## Решение владельца

- Требуется: `ИСПРАВИТЬ`, `ОТЛОЖИТЬ`, `ПРИНЯТЬ РИСК` или `НУЖНЫ ДАННЫЕ`.
- До решения код приложения не изменяется.
- Переход к категории №2 (credential stuffing) не разрешён автоматически.
