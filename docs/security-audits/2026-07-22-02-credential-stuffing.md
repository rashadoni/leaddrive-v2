# Отчёт безопасности: №2 Credential stuffing

- Проект / commit: LeadDrive v2 / `f51720e4e`
- Дата / исполнитель: 2026-07-22 / Codex
- Разрешённое окружение: чтение репозитория и локальные тестовые фикстуры; production не атаковали
- Решение: **ЧАСТИЧНО ЗАЩИЩЕНО**
- Приоритет: **P1**
- Изменение 2FA: не выполнялось

## Что проверено

- CRM Credentials login через NextAuth;
- portal login и MTM mobile login как альтернативные password surfaces;
- password reset, self-service password change и admin password set;
- IP/principal rate limiting, MFA flags, session invalidation и login telemetry;
- существующие unit/route tests.

Реальный credential stuffing и проверка паролей по внешним утечкам не выполнялись. Конкретные пользовательские пароли третьим сторонам не передавались.

## Подтверждённые защитные свойства

- CRM login имеет отдельные buckets по IP и по нормализованному principal (organization/email).
- Portal login имеет coarse IP limit и дополнительный principal limit.
- MFA уже применяется к аккаунтам, где она включена; для admin/superadmin действует обязательная политика. В рамках этой проверки настройки не изменялись.
- Ответы login не раскрывают существование пользователя.
- Смена/сброс пароля выставляет `passwordChangedAt`; старые JWT отзываются на следующем запросе. Есть отдельный `revoke-sessions` endpoint.
- Recovery token — случайный 32-байтный токен с TTL один час; forgot-password возвращает одинаковый успешный ответ.

## Находки

### CS-01 — Нет проверки скомпрометированных паролей (P1)

Создание пользователя, admin password set, self-service change и reset-password проверяют только длину (минимум 8 символов). Нет локального denylist/поддержки k-anonymity для известных скомпрометированных паролей и нет принудительной смены уже скомпрометированного пароля. Поэтому валидная утёкшая пара логин/пароль может пройти до rate limit/MFA.

### CS-02 — Rate limit не является распределённым (P1)

IP и principal buckets хранятся в process-local `Map`. Перезапуск worker очищает состояние; несколько инстансов не делят счётчик. Это снижает эффективность защиты от массового credential stuffing в масштабировании и при ротации источников.

### CS-03 — Нет обнаружения аномалий и уведомления о новом входе (P2)

Успешный login обновляет только `lastLogin` и `loginCount`. Не фиксируются устойчивые признаки входа (IP, user-agent, география), нет уведомления пользователю о новом/подозрительном входе и нет автоматического риска/step-up для необычного устройства.

### CS-04 — Успешный вход не отзывает другие активные сессии (P2)

Сессия живёт до 8 часов. Отзыв происходит после смены пароля или явного `revoke-sessions`, но факт нового входа сам по себе не сокращает срок ранее выданных сессий.

### CS-05 — Неудачные входы не являются durable security events (P2)

CRM путь пишет причины отказа в console log, но не создаёт унифицированную durable запись для агрегации по пользователю, IP, tenant и времени. Это ограничивает оперативное обнаружение credential stuffing.

## Ограничения

- Динамический перебор не выполнялся.
- Реальные учётные записи, пароли и внешние breach databases не использовались.
- Проверка выполнена по коду и локальным тестовым фикстурам.

## Рекомендуемый план устранения после разрешения

1. Добавить локальную проверку скомпрометированных паролей без передачи полного пароля наружу; применить к create/change/reset/admin-set путям.
2. Вынести auth rate-limit state в Redis/shared store с отдельными IP, principal и tenant dimensions.
3. Добавить унифицированное событие `login_success/login_failed` с маскированными признаками и пороговым risk scoring.
4. Добавить уведомление о новом устройстве/подозрительном входе и UI для просмотра/отзыва сессий.
5. После реализации добавить отрицательные тесты для каждого password surface и distributed limiter contract.
