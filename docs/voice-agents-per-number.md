# Голосовые агенты по номерам: у каждого клиента свой SIP-номер и свой сценарий

Владелец, 2026-10-26: «для каждого клиента будет свой номер сип и для каждого
клиента будет свой сценарий — кто-то как техподдержка, кто-то продавать, кто-то
делать записи на встречи». Одна АТС на всех; отдельный сервер — только для
клиента, которому нужна изоляция.

## Что есть сейчас (прочитано в коде 2026-10-26)

- Все внутренние ручки голоса (`runtime-config`, `call-continuation`,
  `call-lifecycle`, `call-source`, `call-result`, очередь, `pharmacy-inbound`)
  берут организацию из одной переменной `VOICE_AGENT_ORGANIZATION_ID`.
  Номер, на который позвонили, нигде не участвует.
- На АТС в `[from-fanum-provider]` заведён один номер
  (`/etc/fanum-inbound-browser.did`). В CRM уходит не он: `toNumber` в
  `call_logs` — постоянная метка `fanum-inbound-browser` (ARG1 в AGI).
- У Asterisk-канала в настройках нет номера (`phoneNumber` пишется только
  для Twilio); связи «номер → канал» нет.
- Сценарий — один на организацию: `voiceAgentPrompt`, `voiceAgentKnowledge`,
  приветствие и правила входящих в `channel_configs.settings`.
- Инструменты у агента в разговоре есть только у Зейтуна (каталог, сумма,
  заказ, аптека по номеру) — отдельный код и отдельное разрешение.
- Лимитов голоса на клиента нет (минуты, одновременные звонки).

## Этапы

### 1. Номер → клиент
- Таблица `voice_line_numbers` (номер E.164 уникален на всю установку,
  `organizationId`, `channelConfigId`), читается до того, как клиент известен
  (обход RLS только на поиск по номеру); экран «Номера» в настройках VoIP.
- АТС передаёт CRM номер, на который позвонили (`${EXTEN}`/`agi_dnid` вместо
  метки) и маршрутизирует все номера провайдера, а не один. Правка диалплана и
  AGI, одна установка с sudo владельца.
- `call-lifecycle` создаёт звонок в организации номера; остальные ручки
  находят организацию по `providerCallId` звонка. `VOICE_AGENT_ORGANIZATION_ID`
  остаётся только запасным для номеров без привязки (LeadDrive/AAC).
- Зейтун переезжает на это: его номер привязан к его организации, разрешение
  `zeytun_line` больше не нужно.

### 2. Сценарий в настройках канала (макет `voice-agent-settings-mock.png`)
- Тип сценария: Техподдержка / Продажи / Запись на встречи / Приём заказов.
  Тип задаёт основу правил и список «что агент может»; клиент дописывает свои
  правила словами, приветствие, прощание, голос, язык, часы работы, «кто
  отвечает» (сразу ИИ / сначала сотрудник).
- Текст правил для модели собирает CRM из основы сценария и правил клиента.

### 3. Общий «проводник инструментов» на АТС
- Ядро станции не знает про сценарии: какие инструменты есть в звонке, CRM
  отдаёт в ответе сессии; вызов уходит в одну ручку CRM
  (`/api/internal/voice-agent/tools`), которая проверяет звонок и выполняет
  инструмент от имени организации звонка. Одна установка ядра; дальше новые
  сценарии — только CRM.
- Инструменты Зейтуна переходят на этот проводник.

### 4. Сценарии и их инструменты
| Сценарий | Инструменты |
|---|---|
| Техподдержка | ответ из базы знаний; открыть заявку (номер, суть); статус заявки по номеру |
| Продажи | квалификация; лид/сделка; задача «перезвонить» на время |
| Запись на встречи | свободные окна (`computeSlots`); запись (`createBooking`) |
| Приём заказов | каталог, цена, сумма, заказ, аптека по номеру (как у Зейтуна) |
Запись делает агент; всё, что он создал, видит и правит сотрудник.

### 5. Лимиты и учёт
- Минуты в месяц и одновременные звонки на организацию; отказ при
  исчерпании — понятной фразой, не тишиной.
- Квота синтеза речи Google — общая на установку: при нескольких клиентах
  нужен Tier 2 (сейчас 100 запросов в сутки).
