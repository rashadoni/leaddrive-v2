# LeadDrive CRM v2 — заметки для Claude

## Гейт перед мержем — проверки самого GitHub (решение владельца 2026-09-11, подтверждено 2026-09-26)

В `main` обязательны пять контекстов, и все пять запускает сам GitHub на
каждом PR: `pr-scope`, `static-checks`, `typecheck`, `runner-policy`, `scan`.
Мерж — когда они зелёные. Настройку держит
`scripts/ci/configure-main-protection.sh`, а тесты
`scripts/ci/test-event-platform-assets.mjs` и
`scripts/ci/test-configure-main-protection.mjs` не дают ни удалить гейт, не
заменив, ни вернуть в него `agent-review`.

**Пути с данными клиентов закрыты по содержимому дерева, а не по корню ветки**
(2026-11-01). Репозиторий публичный; 2026-09-11 персональные данные клиентов
вычистили из истории, и защита была ручной — «ветка не должна быть потомком
старого корня `87ba5ae0`». Главный чекаут стоял на локальной
`feat/chat-voice-parity` с третьим корнем `7f9a57e8`: проверку по предку она
проходила, имея в дереве 74 файла по запрещённым путям (70 в
`migration_data/`, `scripts/v1-data/`, `cost_model_migration_data/` и четыре в
`public/data/`). Теперь смотрят дерево вершины и дерево каждого
коммита диапазона — `scripts/ci/check-forbidden-data-paths.sh`, список путей
один (`scripts/ci/forbidden-data-paths.txt`), гейт шагом в уже обязательной
джобе `scan`. Это не частный случай: на боксе 1 ноября из 1486 локальных
ветвей запрещённые пути несли 584 (539 — файлы трёх вычищенных каталогов),
и проверка по предку блокировала из них только 63, пропуская 521; проверка по
дереву краснеет на всех 584 и ни на одной из 902 чистых. На origin таких
ветвей 0. **Для них хук важнее гейта в CI:** PR они не проходят, их опасность —
прямой `git push origin <ветка>` из любого воркитри, которого проверки на
`pull_request` не видят вовсе. В новом чекауте поставь хуки:
`bash scripts/git-hooks/install.sh --force`; до этого перед пушем руками
`bash scripts/ci/check-forbidden-data-paths.sh HEAD --history origin/main..HEAD`.
Подробности — `docs/DELIVERY-ARCHITECTURE.md`, слой 2.

**Проверки `agent-review` нет, и возвращать её нельзя — ни в каком виде.**
Её завели, когда на старом аккаунте искали, как сэкономить; без секрета
`ANTHROPIC_API_KEY` она намеренно зеленела вхолостую, и была **единственной**
обязательной. 2026-09-26 её вернули как «независимое ревью точного SHA другим
агентом» (#439/#440) — и она встала на каждом PR, потому что публиковать её
было некому. Владелец в тот же день: «убери эту проверку с ИИ… удали её, чтоб
для других сессий также не выскакивала». Ни платный ИИ-ревьюер в CI, ни
статус, который должна публиковать другая сессия, в гейт `main` не входят.
Нашёл `agent-review` в обязательных — сними (постоянное разрешение владельца).

Что это значит для тебя:

- Мержи, когда пять обязательных проверок зелёные. Отдельный разбор другой
  сессией не требуется.
- Красное не мержить и через `--admin` не обходить — см. «Автономия» ниже.
- **Новый обязательный контекст обязан появляться на каждом PR.** GitHub
  засчитывает обязательную проверку, только когда по ней пришёл check run:
  path-фильтр на обязательном workflow вешает PR вне его путей на «Expected —
  waiting for status» навсегда. Экономить на документационных PR — джобой-
  детектором (`pr-scope`), от которой зависят тяжёлые джобы: пропущенная джоба
  засчитывается как пройденная.
- **Детектор тоже обязателен.** Если он упадёт, зависимые джобы пропустятся, а
  пропуск GitHub считает успехом — без обязательности сломанный детектор молча
  открыл бы `main` для любого кода.

Чего не ловят никакие проверки — урок остаётся в силе. 2026-09-09 в #14 была
необратимая потеря данных: `DEAL_TERMINAL_PATTERNS = ["won","lost"]` через
`contains` не отсекает стадии `Qazanıldı`, `Uduzdu`, `Отказ`, и обезличивание
уволенного переписало бы **все его закрытые сделки за все годы** на нажавшего
кнопку админа. Все проверки при этом были зелёными, включая свой же тест — он
проверял форму запроса, а не поведение. Отсюда: тест пишется на поведение на
реальных данных, а не на форму вызова.

И практическое правило оттуда же: названия стадий сделки никогда не хардкодить,
брать `orgStageVocabulary(orgId)` из `src/lib/deal-stage-vocabulary.ts`.
`Deal.stage` — свободная строка, в проде семь написаний на пять стадий.

## Порядок доставки — `docs/DELIVERY-ARCHITECTURE.md`

Этот документ главнее всего остального в том, что касается пути изменения до
клиентов, и действует одинаково для Claude, Codex и любых будущих сессий.
Коротко, четыре слоя:

1. В `main` только через PR, прямой пуш запрещён.
2. Каждый PR проходит обязательные проверки GitHub — `pr-scope`,
   `static-checks`, `typecheck`, `runner-policy`, `scan`. ИИ-ревьюера в гейте
   нет (снят 2026-09-11 и ещё раз 2026-09-26, см. начало файла).
3. Прод выкатывается только из `main`, с атомарной подменой, проверкой здоровья
   и откатом — это уже построено.
4. Перед мержем того, что увидит пользователь, показать владельцу короткий
   список человеческим языком и дождаться «давай». Единственное, чего не ловит
   ни один тест: 6 сентября 2026 корректно написанная фича на главной, которую
   никто не заказывал, доехала до `main` с зелёными проверками.

Владелец работает один и диффы не читает. Его участие — одна строка «давай».

## Рабочий режим (одобрено владельцем)

Одобренные планы реализовывать **автономно**, без запроса подтверждений на каждый шаг:
ветка → PR → ревью агентом → полный прогон тестов → «давай» от владельца → мерж → автодеплой.
Отчёт владельцу — после каждого PR. Останавливаться и спрашивать только при
разрушительных действиях (удаление данных, откаты) или продуктовых развилках,
меняющих смысл фичи.

## Схему встреч меняет только запись в родословной (2026-11-03)

У встреч свой контракт релиза: в артефакт кладётся отпечаток моделей `Booking*`
(`.booking-backend-contract.json`), и прод принимает артефакт, только если этот
отпечаток согласован с работающим. Пока режим встреч `workspace` (с
2026-10-24, обратно не выключается), правило было «ровно тот же отпечаток», то
есть **модели `Booking*` были заморожены навсегда**: 2026-11-03 релиз с четырьмя
необязательными колонками `booking_pages` встал на шаге «Admit booking backend
from current main before staging» (`booking_artifact_admission=BLOCKED`), не
дойдя до прода.

- **Поменял модель `Booking*` — добавь запись в
  `scripts/booking/schema-lineage.json`**: отпечаток (его считает
  `bookingSchemaHash`), имя своей миграции, `bookingAdditive`. Вершина
  родословной обязана совпадать со `schema.prisma`, иначе красный
  `static-checks` и несобравшийся релиз.
- **`bookingAdditive: true` проверяется по SQL миграции, а не на слово**
  (`additiveMigration`): только добавленные колонки, которые прежний артефакт
  может не заполнять. Переименование, удаление, смена типа, ограничение,
  `NOT NULL` без `DEFAULT` — это `false`, и тогда релиз снова требует
  совпадения отпечатков и ручного плана.
- **Этот же список — сеть автоматического отката**: по нему `admitRollback`
  пускает прежнюю сборку. Строгое равенство отказывало и ей, так что неудачный
  health-check оставил бы прод лежать до совместимого восстановления.
- Подробности и порядок — `docs/booking-release-cutover-plan.md`, раздел
  «Форвард-релиз».

## Тихое окно миграции: аренда жива, пока её продлевают (2026-11-02)

Деплой не мигрирует, пока что-то работает, и ждёт тишины до 5 минут. Аренду
задачи он считал живой по будущему `leaseUntil` — а **каждый деплой убивает
процесс задач (`pm2 delete leaddrive-v2-jobs`), не освобождая аренды**, и у
`finance-deadlines`, `social-poll-all`, `mtm-auto-checkout` сроки 10–15 минут.
Поэтому один деплой мог на четверть часа заблокировать миграцию следующему:
2026-11-02 прогон 41480027867 пять минут видел `system=1` при `tx=0` и упал,
релиз не доехал (прод при этом не тронут — это преднастроечная проверка).

- **Живая аренда — та, которую продлевают.** `withJobLease` продлевает раз в
  `ttl/3` и пишет `leaseUntil` и `updatedAt` из одного `CURRENT_TIMESTAMP`, так
  что аренда несёт свой срок как `leaseUntil - updatedAt`, а у живой он не
  старше трети. Граница — половина срока: пропущенное сердцебиение с запасом.
- **Брошенные не удаляются, а не учитываются** и называются в журнале вместе с
  живыми (`job leases: имя (renewed Ns ago, ttl Ms, live|abandoned)`). Раньше
  в логе был только счётчик, и час ушёл на выяснение, кто именно держал окно.
- **Поведение доказано на настоящем Postgres** —
  `src/__tests__/deploy-migration-window-postgres.test.ts` берёт SQL из самого
  `server-deploy.sh`, так что скрипт и тест не разойдутся; гейт в
  `static-checks` и в деплое. Строковый тест рядом
  (`server-deploy-migration-window.test.ts`) стережёт, что отказ от живых
  аренд остался на месте.

## Загруженные файлы — шифрование на диске (`src/lib/crypto/tenant-file-encryption.ts`)

Владелец 2026-10-22 утвердил: файлы клиентов (медиа чатов, вложения
договоров/задач/тикетов, фото и документы MTM) лежат на диске зашифрованными
ключом организации. Конверт: AES-256-GCM кусками по 64 КиБ, свой ключ на файл,
заголовок подписан каждым куском; чужая организация, обрезка, подмена куска —
отказ, а не другие байты.

- **Писать файл клиента только запечатанным**: `writeFile(путь,
  sealTenantFile(orgId, bytes))`. **Читать только через декодер**:
  `openTenantFileStream` (потоком, для раздачи) или `decodeTenantFileBytes`
  (в память), под организацией, для которой доступ уже проверен. Старые файлы
  без конверта проходят как есть, поэтому старое и новое живут рядом.
  Стережёт `tenant-file-readers-guard.test.ts`: модуль, который называет место
  загрузок и читает или пишет файл, обязан расшифровывать/запечатывать или
  стоять в списке «открыто намеренно» с причиной.
- Размер на диске у зашифрованного файла больше записанного в БД; сравнивать с
  записанным размером только расшифрованные байты.
- Открыто намеренно: публичные картинки писем и логотипы (их раздают без
  входа), временные вложения писем, кэш публичных соцсетей.
- Файлы, записанные до шифрования, запечатывает
  `cron-trigger.sh "/api/cron/tenant-file-encryption-backfill"`: без `apply=1`
  это только подсчёт, с `apply=1&limit=N` пишет пачкой, повторять, пока
  `hasMore`. Запускать после свежего бэкапа файлов. Файл без строки-владельца
  в БД не трогается. После прогона бэкап файлов без `TENANT_PII_MASTER_KEY`
  нечитаем — ключ уже лежит в бэкапе секретов (`snapshot-secrets.sh`).
  **На проде он закончен** (2026-11-03: 112 из 112, `wouldSeal=0`).
- **«Файл без конверта `LDFE`» и «незапечатанный файл клиента» — не одно и то
  же** (2026-11-03). В дереве `uploads` открытыми лежат ещё 25 публичных файлов
  (`logos`, `email-images`, `social-logos`, `social-media-previews` — их не
  шифрует сам код) и две пустые `.gitkeep`; 9 сирот снятой функции планограмм
  (`mtm-golden/`) удалены 2026-11-03 по слову владельца, и ожидаемое состояние
  теперь — `plain_unexpected=0`. Считать открытые файлы остатком бэкфилла —
  ошибка, она уже была сделана. Смотрит на диск одна вещь — копия файлов клиентов
  (`scripts/backup/uploads-offsite-mirror.sh`): она делит открытые файлы на
  `plain_public` / `plain_empty` / `plain_unexpected`, кладёт последнее в своё
  состояние и сторож предупреждает. Проверять по дереву, а не по очереди на
  отправку: счёт по очереди читается нулём на следующий день после прогона.
  Новый публичный каталог — в `PLAIN_BY_DESIGN` там же, с причиной, иначе
  сторож будет звать его утечкой. Код стережёт `tenant-file-readers-guard.test.ts`,
  но он читает код и о лежащем на диске не знает ничего.

## Ключ данных организации — `src/lib/crypto/tenant-data-keys.ts`

Владелец 2026-10-22 («вариант 3», без KMS и Vault): у каждой организации свой
СЛУЧАЙНЫЙ ключ данных в `tenant_data_keys` (FORCE RLS), завёрнутый главным
ключом, с версиями. Раньше ключ организации был HKDF(главный ключ, orgId) — его
нельзя уничтожить для одной организации.

- **API шифрования остаётся синхронным.** Ключ грузится при входе в контекст
  тенанта (`enterTenant` в `api-auth.ts`, `runWithTenant`) и лежит в памяти
  процесса (`tenant-data-key-cache.ts`, на `globalThis`, 10 мин). Есть ключ —
  запись `v2:<версия>:…` и конверт файла `d<версия>`; нет — запись v1 / `t1`,
  запись никогда не падает из-за ключа.
- **Чтение v2 без ключа в памяти бросает `TenantDataKeyUnavailableError`, в
  том числе soft-путь.** Отдать строку как «плейнтекст» нельзя: следующее
  сохранение зашифровало бы её как значение. Код, который читает PII или файл
  клиента вне запроса (крон, вебхук, скрипт), сначала зовёт
  `ensureTenantDataKeys(orgId)` / `preloadTenantDataKeys(orgId)`; файл читать
  через `openTenantFileBytes` / `openTenantFileStream` — они грузят ключ сами.
- Ключ создаётся при первом входе организации (гонка решена уникальным
  индексом). Активный ключ, завёрнутый другим главным ключом, — ошибка, а не
  повод создать новый.
- Старое переводит `cron-trigger.sh "/api/cron/tenant-data-key-reencrypt"`:
  без `apply=1` — только подсчёт остатка по организациям (ключей не создаёт);
  с `apply=1&limit=N` — переписывает колонки и файлы, повторять, пока
  `hasMore`. Запускать после свежего бэкапа БД и файлов и по «давай»
  владельца. `health_medical_records` и `workforce_attendance_evidence`
  переписать нельзя (триггеры) — их v1 считаются отдельно (`appendOnlyColumns`).
- Новая зашифрованная колонка → в `REENCRYPTABLE_COLUMNS`
  (`tenant-data-key-reencrypt.ts`); тест сверяет его с линтом колонок.
- Стережёт `tenant-data-keys-postgres.test.ts` (гейт в `static-checks` и в
  деплое). Не сделано и делается владельцем позже: смена главного ключа
  (перезавёртка строк) и уничтожение ключа организации.

## Проверяющий под NDA — `src/lib/reviewer-access.ts`

Владелец 2026-10-23 («Давай, делай доступ проверяющего по этому плану»):
временный доступ только на чтение для человека со стороны. Выдаёт админ в
«Настройки → Пользователи → Дать доступ проверяющему»: имя, e-mail, разделы,
дата окончания (не дальше 30 дней), причина. Пароль показывается один раз.

- **Роль `reviewer`** + строка `reviewer_access_grants`. Читает только
  отмеченные разделы (остальные — в `hiddenModules`); `checkPermission` не даёт
  ему ничего, кроме `read`, и никогда `settings`/`users`/`audit`/`social-legal`.
- **Прокси режет до маршрута** (`reviewerRequestDenial`): любые записи, любые
  выгрузки (`…/export…`), настройки, пользователи, журнал, админка, страницы
  `/settings` и `/admin`, файлы неотмеченных разделов. Новый путь с выгрузкой или
  администрированием, не подходящий под эти шаблоны, — дописать туда же.
- **Срок** проверяет `auth.ts` при входе и при каждом обновлении сессии
  (`reviewerAccessUntilFor`): нет строки, закрыта или истекла — сессии нет.
  «Закрыть доступ сейчас» — `isActive=false` + сдвиг `passwordChangedAt`.
- **Журнал**: каждое чтение через `getSession`/`requireAuth`/`requireSessionAuth`
  пишется в неизменяемый `compliance_audit_log` (`recordReviewerRead`). Новый
  способ аутентификации сессии обязан звать его же.
- Проверяющих нет в списке сотрудников и в выборе исполнителя; обычное
  редактирование пользователя их не трогает (409), только панель.
- Водяной знак с именем, e-mail и датой — на каждом экране проверяющего.

  вопрос владельцу;
- мержи в `main`, когда обязательные проверки зелёные;
- дай деплою после мержа пройти (см. «Deploy» в AGENTS.md — там разрешение на
  деплой уже стоит).

Докладывай результат, а не каждый шаг. «Смержил #1102, задеплоил,
/api/v1/ping ok» — это весь отчёт, который нужен.

Чего это разрешение НЕ покрывает — никакая автономия не делает это
безопасным:

- **Мерж красного.** Никогда не мержить с падающей обязательной проверкой, не
  обходить её через `--admin`, не ослаблять, не перевешивать и не удалять
  гейт ради мержа. Если гейт действительно неправильный — скажи об этом и
  оставь его на месте.
- **Разрушительные операции с продовыми данными** — дроп или восстановление
  базы, удаление тенанта, необратимый бэкфилл. Подготовь и спроси.
- **Всё, что требует лично владельца**: пароли, платёжные данные, создание
  аккаунтов, чужие панели. Спроси, не изобретай обходной путь.
- **Чужая ветка в работе.** Мержи то, что делал сам. PR другой сессии — только
  если владелец попросил.

Если твой мерж сломал прод — откатывай и передеплоивай сразу, это тоже твоя
работа и тоже без спроса.

## CI и деньги

CI живёт на **GitHub-hosted Linux в публичном репозитории
`rashadoni/leaddrive-v2`**. Для публичных репозиториев стандартные раннеры
бесплатны, поэтому PR-проверки больше не делят платный лимит минут. Счёт делал
`macos-*`: из $121.17 за сентябрь 2026 macOS — $84.41, Linux — $36.76. Поэтому
запрет macOS ниже абсолютный и проверяется скриптом.

Пул Contabo CI и заменявшие его пайплайны Azure DevOps выключены. Их метки
(`leaddrive-ci`, `leaddrive-typecheck`, `leaddrive-ci-light`) не должны
появиться в workflow снова.

- **Каждая GitHub-hosted джоба фиксирует `runs-on: ubuntu-24.04`.** Не
  `ubuntu-latest`: этот алиас переезжает на следующий LTS по расписанию GitHub и
  меняет базовый образ всех джоб в день, когда нет ни одного коммита для bisect.
- **Никогда не добавляй `runs-on: macos-*`.** Ни для нативной проверки, ни
  временно, ни под label-gate. Настоящая нативная macOS/iOS-работа идёт на
  физическом Mac владельца под
  `runs-on: [self-hosted, macOS, ARM64, leaddrive-mac-local]` с
  `timeout-minutes`. На 2026-09-09 в репозитории нет ни одной цели Swift/Xcode,
  поэтому Mac-раннер не зарегистрирован — если кажется, что он нужен, сначала спроси.
- `scripts/ci/check-github-runner-policy.mjs` проверяет всё перечисленное и стоит
  required-чеком. Запусти его локально, прежде чем трогать workflow.
- Единственный оставшийся self-hosted раннер — `[self-hosted, fanum-pbx-vpn]`,
  им пользуется только `set-voice-provider-registry-cutover.yml`, потому что ему
  нужен VPN до PBX. Больше туда ничего не направляй и не клади продовый секрет в
  workflow, которому только что поменял метки.

Деньги больше не главный ограничитель — **главное время и шум в ревью**.
Ограничители сохраняются:

- **Итерируй в драфте.** На draft-PR `static-checks` и `typecheck` не
  запускаются. Помечай PR ready for review, когда ветка готова: сработает
  `ready_for_review`, и гейт отработает один раз — перед мержем, который он и
  охраняет.
  Черновик PR или нет, решает `pr-scope` по живому состоянию PR
  (`scripts/ci/pr-draft-state.sh`), а не по `github.event.pull_request.draft`:
  событие — снимок. 2026-10-09 на #639 пуш и «ready» ушли подряд: прогон по
  новому коммиту получил в событии `draft: true`, а `ready_for_review` пришёл со
  старым коммитом и был отменён — обе тяжёлые джобы пропущены, готовый PR
  показал `CLEAN` без единого теста. Отсюда и правило на мерж: у PR с кодом
  `static-checks` и `typecheck` должны быть `success`. `skipped` там — это «не
  проверено», а не «прошло».
- Правки только в `**/*.md`, `docs/**`, `.agents/**` запускают из
  `pr-checks.yml` одну лёгкую джобу `pr-scope`; тяжёлые `static-checks` и
  `typecheck` пропускаются. Не подмешивай код в документационный PR ради
  прогона CI.
- Новый workflow на `pull_request` обязан иметь и `paths`-фильтр уже всего
  репозитория, **и** `concurrency` с `cancel-in-progress: true`, чтобы новый пуш
  отменял предыдущий прогон.
  **Исключение ровно одно:** workflow, чей чек *обязателен* в `main`, не должен
  иметь `paths`-фильтра. GitHub засчитывает required-контекст только когда по
  нему пришёл check run, поэтому path-фильтрованный required-чек намертво вешает
  каждый PR вне своих путей на «Expected — waiting for status». Поэтому
  `runner-policy.yml` запускается на каждом PR. Делаешь чек обязательным —
  снимай с него `paths` тем же изменением.
- Не снимай эти ограничители, чтобы проверка прошла быстрее. Скажи и спроси.

Так как репозиторий публичный:

- **Никогда не используй `pull_request_target`.** Он запускается с секретами
  базового репозитория поверх недоверенного кода head. Обычный `pull_request`
  секреты fork-PR не отдаёт — именно это защищает `NEXTAUTH_SECRET` в
  `pr-checks.yml`.
- Fork-PR должны оставаться за «Require approval for all external contributors»
  в Settings -> Actions.
- Считай любое значение в окружении `production` продовым. Кроме `deploy.yml` и
  операционных `workflow_dispatch`-джоб его никто не читает.

Раз в неделю смотри Billing -> Actions usage по SKU. **Появление любого macOS SKU
— инцидент**: найди workflow, который его произвёл, и сообщи.

Полный разбор с цифрами — `docs/ci-cost-policy.md`.

«тогда давай лишние серверы уберем. он по карману бьет», и на вопрос, сколько

## Финансовые API: роль и модуль проверяет каждая ручка

`/api/finance`, `/api/cost-model` и `/api/budgeting` живут вне `/api/v1`. До
2026-10-07 сорок из сорока пяти файлов там спрашивали только «вошёл ли человек в
организацию» (`getOrgId`): наблюдатель мог согласовать платёжное поручение, а
тенант без модуля «Финансы» — пользоваться всеми тремя.

- **Каждая ручка — `withRlsAuth(scope, action, …)`**, ничего другого. Scope по
  неймспейсу: `finance` / `profitability` / `budgeting` (все три ведут на модуль
  `finance`). Action — по методу; исключения перечислены в
  `READS_THROUGH_POST` теста. Новую ручку `finance-api-authorization.test.ts`
  найдёт сам и прогонит по всем ролям.
- **Кто что может** записано в `ROLE_PERMISSIONS` и продублировано таблицей `MAY`
  в том же тесте — намеренно: ожидание, выведенное из `checkPermission`,
  доказывает только, что матрица согласна сама с собой. Менеджер ведёт
  казначейство и не удаляет; модель затрат он читает; продажи и поддержка
  финансов не видят.
- **`finance` не входит в `MODULES`**, поэтому API-ключ такой scope получить не
  может: ключ действует как админ, а платёж согласует человек (`approvedBy`).
- **Своё поручение менеджер не согласует, админ — может** (владелец,
  2026-10-07; без исключения для админа организация с одним финансистом не
  провела бы ни одного платежа). Правило одно на сервер и на экран —
  `isOwnOrderToApprove` в `src/lib/finance/payment-order-approval.ts`; автору
  вместо кнопки показана подпись. Поручение без записанного автора — ничьё.
- Экраны финансов не показывают отказ сервера — упавшая мутация просто ничего не
  делает. Поэтому кнопку, которую сервер отклонит, не рисуют:
  `useFinanceAccess()` / `useCostModelAccess()`.
- Оплата счёта и исполнение поручения идут через `applyBillPayment`
  (`src/lib/finance/bill-payment.ts`): одна транзакция, атомарный инкремент,
  Decimal. Проверено на настоящем Postgres
  (`finance-bill-payment-postgres.test.ts`): на прежнем коде восемь
  одновременных оплат по 10 давали в счёте 20.
- **Запись реестра платежей не привязана к платежу внешним ключом**
  (`PaymentRegistryEntry.sourceType` + `sourceId`), поэтому база её сама не
  уберёт. Кто удаляет платёж — отдельно или вместе со счётом клиента либо
  входящим счётом, чьи платежи уходят каскадом, — в той же транзакции удаляет и
  запись реестра. До 2026-10-07 этого не делал никто: снятая оплата оставалась в
  реестре и в его итогах. Порядок важен: сначала документ, потом реестр —
  удаление документа ждёт платёж, который записывается прямо сейчас; в обратном
  порядке гонка оставляла до восьми записей из восьми. Запись исполненного
  поручения при удалении его счёта остаётся — поручение живо. Стережёт тот же
  `finance-bill-payment-postgres.test.ts`.

## Финансовые уведомления: адресат — настройка организации

До 2026-10-07 `telegram-notify.ts` и ночной `finance-deadline-job.ts` брали бота
и чат из окружения (`TELEGRAM_BOT_TOKEN` + `TELEGRAM_FINANCE_CHAT_ID`) — одна
пара на всю установку, а Telegram включён по умолчанию во всех четырёх
категориях. То есть контрагенты и суммы ЛЮБОГО тенанта с «Финансами» были
адресованы в один чат. На проде это не сработало по случайности: чат был задан,
а токен пуст, и он общий с соцмониторингом — утечку включила бы первая же
правка env не про финансы.

- **Бот и чат — свои у организации**, в `Organization.settings.financeNotifications`
  (`telegramBotToken`, `telegramChatId`, рядом с `recipientEmail`). Решение
  владельца 2026-10-07: общего бота нет, поэтому один тенант физически не может
  написать в чат другого. Не настроено — Telegram молчит; запасного чата из
  окружения нет и появиться не должно (`src/lib/finance/notification-settings.ts`).
- Отправляет только `sendFinanceTelegram(target, text)`: адресат — аргумент,
  окружение он не читает. Новому финансовому уведомлению адресата брать через
  `financeTelegramTarget(readFinanceNotifSettings(org.settings))`.
- Токен наружу не отдаётся никому (финансы читает и наблюдатель): GET возвращает
  маску. PUT с маской или вовсе без Telegram-полей сохраняет прежний токен — так
  форму шлёт вкладка, открытая до этих полей; пустая строка — «отключить».
- Стережёт `finance-telegram-recipient-postgres.test.ts` на настоящем Postgres,
  с заданной парой в окружении: мокается только `fetch` (и сессия), проверяется,
  куда реально ушёл каждый запрос к api.telegram.org. Гейт стоит в `static-checks`
  и в деплое.

## MTM: что может агент — `src/lib/mtm/agent-permissions.ts`

Таблица «Что может агент» на `/mtm/access` (владелец, 2026-10-04: «рол матрикс —
что может делать агент, а что не может, по всем функциям»). Она не должна стать
второй декоративной матрицей, как `/settings/roles`, которую не читает ни одна
проверка прав:

- **Строка с переключателем — это настройка MTM**, которую API уже читает там,
  где отказывает агенту (`agentPermissionEnabled(settings, id)` →
  403 `MTM_AGENT_PERMISSION_DISABLED`). Своего хранилища у таблицы нет.
- **Строка без переключателя** («может всегда» / «не может никогда») обязана
  иметь запись в `FACTS` теста `lib-mtm-agent-permissions.test.ts` — функцию
  прав, вызванную от имени агента, или строку-страж в роуте. Без неё тест красный.
- Новая функция для агента → новая строка здесь. Новый переключатель → ключ в
  `MTM_SETTING_DEFAULTS` (по умолчанию как было до него), проверка в роуте, тест
  на отказ и на то, что ничего не создано. Приложение получает переключатели в
  bootstrap как `policies.agentPermissions` и прячет вход; сервер отказывает сам.
- Агент не меняет клиентов и организации напрямую — только заявкой. Это правило
  владельца (2026-10-02), а не переключатель; не превращать его в переключатель.

  агент при «Я приехал — начать визит» сам отвечает «вместе с руководителем».

  визита (`MtmVisitParticipant`, `role: OBSERVER`, `jointSessionId`). Ответ
  без сессии визит не меняет и чек-ин не ломает.
- **Оценка** (`MtmVisitEvaluation`) — только на таком визите, от того самого
  руководителя, до конца следующего дня после чек-ина; пункты 1..5,

- **Вопросы оценки — свои у компании** (владелец 2026-10-21: «Да, в параметрах
  MTM»): настройка `visitEvaluationQuestions`, вкладка «Визит» в настройках MTM —

  вопрос, которого в нём нет, — 409 `MTM_VISIT_EVALUATION_QUESTIONS_CHANGED`

- **Агент оценку не видит — нигде.** Ни в приложении, ни в вебе (вкладка

  повторить это правило; стережёт `mtm-joint-visit-postgres.test.ts` (гейт в

## MTM: «агент едет к вам» — `src/lib/mtm/customer-eta-link.ts`

Как в такси (владелец 2026-10-12 и 2026-11-02, по макету): когда агент выехал
к следующему клиенту маршрута дня, бот шлёт этому клиенту ссылку — где агент
сейчас и примерно когда приедет. По умолчанию выключено; включает компания в
«Настройки MTM → Карта агентов», канал — SMS (провайдер компании) или WhatsApp
(номер компании и её одобренный шаблон `mtm_agent_on_the_way`, четыре
переменные: компания, агент, время, ссылка).

- **«Выехал» решает минутная задача** (`/api/cron/mtm-customer-eta`,
  `customer-eta-link-job.ts`), а не чек-аут: агент на смене, не на перерыве,
  без открытого визита, телефон только что прислал место (то же правило, что у
  публичной страницы), следующая точка — первая PENDING после последней
  посещённой, не раньше чем за 90 мин до `plannedTime`, не ближе 150 м.

  'CUSTOMER_ETA'`, уникальный `routePointId`) пишется ДО отправки; не ушло —
  `FAILED`, ссылка отозвана, повтора нет.
- **Кому из агентов — выбирает компания** (владелец 2026-11-07: «пока не хочу
  всем включать»): под той же галочкой «Всем агентам» / «Только выбранным» и
  имена (`customerEtaAgentScope`, `customerEtaAgentIds`, правило одно —
  `customerEtaForAgent`). «Всем» — как было до выбора; «выбранным» без имён —
  никому. Задача проверяет выбор и в чтении, и под `FOR SHARE` перед записью
  ссылки; сохранение принимает только агентов этой компании.
- Ссылка бота — та же `mtm_location_share_links` и тот же публичный ответ, но
  свой выключатель (`customerEtaLinksEnabled`; выключение отзывает все ссылки
  бота) и не входит в пять ссылок руководителя. Отметился у клиента — ответ
  `ARRIVED` без координат; в визите у другого — без координат.

- Местный номер «050…» становится «+994…» только у компании на времени Баку;

## MTM: координаты за перерыв не пишутся

Перерыв сотрудника — его личное время (правило владельца): где он его провёл,
не записывается и никому не показывается. Точку, снятую в перерыв, не пишет ни
один вход:

- `POST /api/v1/mtm/mobile/location` — отказ `MTM_LOCATION_WORKDAY_PAUSED`
  (с задачи A7);
- `POST /api/v2/mtm/mobile/location/batch` — с 2026-10-11 отбрасывает такую
  точку и называет её в `pausedClientLocationIds`, остальные точки пакета
  пишет. До этого проверял только окно рабочего дня;
- `POST /api/v1/mtm/locations` (веб-сессия и API-ключ, пишут за сотрудника) —
  с 2026-10-12 тот же отказ (владелец: «да»). До этого на рабочий день не
  смотрел вообще. Проверяется только перерыв: точка за того, у кого смены в
  этот момент нет, пишется как раньше.

Публичная ссылка на местоположение защищена отдельно
(`src/lib/mtm/location-share-link-position.ts`).

- **Что такое перерыв, решает один читатель** — `src/lib/mtm/workday-pauses.ts`
  (`MTM_WORKDAY_PAUSE_EVENT_TYPES`, `mtmWorkdayPauses`,
  `isDuringMtmWorkdayPause`): журнал рабочего дня, включая REOPEN руководителя.
  Секунда начала и секунда конца перерыва — работа. Решает момент, когда точка
  снята, а не статус смены в момент загрузки. Второй разбор журнала не писать.
- **Новый путь записи в `mtm_agent_locations`** обязан спросить этого читателя
  до записи и получить случай в
  `src/__tests__/mtm-mobile-location-break-postgres.test.ts`: тест читает
  таблицу на настоящем Postgres и стоит гейтом в `static-checks` и в деплое.
- Не проверяет перерыв одна вещь, и сознательно: кнопка руководителя
  «поделиться своим местоположением» (`mode: "SELF_SHARE"`, одна точка на
  нажатие, полевому агенту недоступна) — человек сам нажал её про себя. Это
  предложение сессии от 2026-10-11, владелец не возразил; отдельным решением
  он это не утверждал.
- Сервер отказывает только по перерыву, который уже записан в журнале.
  Устройство, приславшее координаты раньше своего PAUSE, их запишет; приложение
  на паузе координаты не снимает.

## Аптеки Зейтуна — компании из 1С (`src/lib/pharmacy-orders/pharmacy-companies.ts`)

Владелец 2026-10-26 («Макет аптек подходит, делай»): каждая аптека из списка
1С (ListClients) — карточка компании Зейтуна, `externalSource = "zeytun_1c"`,
`externalId` = GUID контрагента в 1С. Главная база — 1С.

- **Что принадлежит 1С, в CRM не правится**: название, адрес, город, телефон
  (`PHARMACY_SOURCE_FIELDS`). PUT компании с другим значением — 409
  `SOURCE_MANAGED`, форма эти поля блокирует; удалить такую компанию нельзя
  (ни по одной, ни пачкой) — следующая загрузка вернула бы её. CRM добавляет
  своё сверху: менеджер (`managerId`), категория, заметка.
- **Загрузка** — крон `zeytun-catalog-refresh` (тик каждые полчаса; сам тик
  в 1С не ходит), из снимка, который он же держит (`loadZeytunPharmacyCompanies`): организация и снимок —
  из разрешения линии (`orderOrganizationId`, `pharmacySource`). Уже
  загруженный список ничего не меняет. Пропавшая из 1С аптека — `status:
  inactive` + `externalRemovedAt`, не удаляется; если из списка разом пропало
  больше 20 аптек и больше пятой части, удаления не принимаются
  (`removalsHeld`) — так выглядит обрезанный ответ 1С, а не закрытие.
- **Заказ ссылается на аптеку** `companyId`: звонок — по GUID из 1С, старый
  заказ — при загрузке, менеджер — кнопкой на карточке заказа
  (`set_pharmacy`, `manager_selected`, только аптеку из 1С).
- **Заказ пишется по ходу звонка** (владелец 2026-10-27: длинный заказ не
  должен пропадать). Звонок линии длится до 15 минут (`CALL_MAX_SECONDS`;
  станция сама отвергает больше — `MAX_CALL_SECONDS` в
  `scripts/pbx/fanum-zeytun-inbound.py`, менять оба), ИИ сохраняет список после
  каждой позиции. Поэтому WhatsApp менеджерам уходит по окончании звонка
  (`announceCallOrder` из call-lifecycle), а не при первом сохранении,
  и карточка заказа не принимает правок, пока звонок идёт (`call_in_progress`):
  следующее сохранение ИИ их бы затёрло.
- **Станция досылает заказ, если CRM не ответила** (владелец 2026-10-28).
  Каждое сохранение станция сначала пишет к себе на диск
  (`ZeytunOrderSpool`, `/var/spool/zeytun-phone-orders`, файл на звонок), потом
  шлёт с номером `seq`; не ответила CRM (сеть, таймаут, 5xx, 429) — ИИ слышит
  `queued` и говорит «принят» без номера, а поток ядра досылает раз в 10–60 с,
  в том числе после звонка, сутки. CRM принимает такой заказ и после конца
  звонка — только с `seq`, только по звонку, который линия сама взяла (claim),
  не дольше `LATE_ORDER_WINDOW_MS`; более старый `seq` ничего не меняет
  (`stationSeq`), а заказ, который менеджер уже правил после звонка, не
  трогает (`stationRevision`). Досланный после звонка заказ рассылает
  WhatsApp заново, по составу на сейчас. Новое поле в теле `order` — сначала
  CRM, потом станция: схема строгая, станция с новым полем до деплоя CRM
  получала бы 400.
  Когда у звонка уже есть номер заказа (первое сохранение прошло), следующее
  сохранение станция пишет на диск и сразу отвечает ИИ `saved` с этим номером,
  а в CRM шлёт за ответом (владелец 2026-10-30: «долго принимает заказ») —
  ИИ не молчит 1–4 с после каждой позиции. Первое сохранение и сохранение без
  диска ждут CRM, как раньше.
  Служба голоса на станции запущена с `ProtectSystem=strict`: писать ядро может
  только в разрешённые каталоги. Очередь разрешена добавкой
  `/etc/systemd/system/fanum-voice.service.d/zeytun-order-spool.conf`
  (`ReadWritePaths=-/var/spool/zeytun-phone-orders`, 2026-10-29); новый путь
  записи ядра — туда же, иначе в журнале `zeytun_order_spool status=unavailable`.
- **Звонок без итогового сохранения — строки из расшифровки** (очередь владельца 2026-11-06, задача 1b;
  стенд: модель в половине звонков сохраняет список только в конце). Когда приходит расшифровка звонка
  линии (`call-result`), а заказ звонка не закончен (`finishedOnCallAt` пуст) или его нет, CRM один раз
  читает заказ из расшифровки (`gemini-3.8-flash`, JSON по схеме, `zeytun-transcript-recovery.ts`) и
  дописывает строки, которых в заказе нет (по товару 1С или по слову марки): без товара 1С,
  `not_found`, с пометкой «(transkriptdən)» — товар выбирает менеджер. Строки заказа не меняются; заказ,

## Перевод звонка от ИИ на менеджера в браузере (`src/lib/voip/inbound-handoff.ts`)

- **На станции ИИ говорит на отдельной ветке** (`Dial(Local/s@fanum-inbound-ai-leg/n,,g)`
  в `scripts/pbx/fanum-inbound-browser.conf`): в Asterisk 20.6 закончившийся
  AudioSocket кладёт трубку своего канала, поэтому после ИИ на том же канале
  нельзя было ничего сделать. После ветки станция спрашивает
  `/api/internal/asterisk/inbound-handoff` (`start` / `return`).
- **Состояние — `CallLog.handoffState`**: `requested` (ИИ попросил,
  инструмент `transfer_to_manager`) → `ringing` (обычный звонящий человеческий
  входящий: всплывающее окно, захват браузером, проверка готовности — без
  нового кода) → `connected` | `returned`. Один раз на звонок.
- Перевод предлагается, только если менеджер может ответить
  (`managerCanAnswer` в `zeytun-line-host.ts`; владелец 2026-10-27: «только в
  рабочее время или когда менеджер в сети»): у кого-то с правом отвечать на
  звонки (`voip` write, `browserSoftphoneAllowed` для него) сейчас открыта
  CRM — живой поток `/api/v1/shell/events` с `calls`
  (`src/lib/shell-events/presence.ts`, память веб-процесса). Иначе инструмент
  отвечает `unavailable`, и ИИ сразу принимает заказ сам — ночью аптека не
  слушает 30 с гудков. Вкладка, у которой поток не поднялся, не считается.
- Что не забыть: звонящий переведённый звонок не должен уходить к ИИ по
  настройке ответа (готовность это проверяет), поздний «answered» ветки ИИ не
  должен снимать «ringing» (lifecycle), стенограмма ИИ пишется и после того,
  как строка стала human (call-result), а вторая часть после возврата
  дописывается к первой.
- **Вопрос «перевёл ли ИИ звонок» аптека слушает тишиной** (звонок 0127e38f,
  2026-11-04: «он прощается, я прощаюсь, а отбой не даёт, линия открыта»).
  AGI `handoff` идёт после ветки ИИ и до `Hangup()`: канал аптеки закрылся
  через 12,1 с после последнего слова ИИ (3,0 и 4,2 с на двух звонках до
  него), а до CRM вопрос со станции не дошёл ни разу. Теперь он один, весь —
  с поиском адреса — не дольше `HANDOFF_START_SECONDS` (1,5 с), положившей
  трубку аптеке не задаётся, а причину отказа AGI пишет в stderr
  (`handoff_dns` / `connect` / `tls` / `timeout` / `http_NNN`). Пока вопрос
  не доходит до CRM, перевод на менеджера не работает: AGI отвечает «нет», и
  звонок кладётся. AGI ставится без пароля:
  `sudo -n /usr/local/sbin/zeytun-agi-install <пакет> <новый sha> <живой sha>`
  (`scripts/pbx/zeytun-agi-install`, правило — `zeytun-agi-install.sudoers`).

## Голосовое управление (Gemini Live)

- **Провайдер — Google Gemini Live**, `@google/genai`, модель в
  `src/lib/ai/voice/gemini-live.ts`. ElevenLabs в проде не используется: это
  прежний провайдер, от которого остались имена — раздел когда-то назывался
  «ElevenAgents», а колонка сессии до сих пор `elevenlabsConversationId`
  (значения в ней при этом вида `gemini:issued:*`). Читай эти имена как
  исторические; владелец поправлял сессию 2026-09-23, которая по ним решила,
  что голос — ElevenLabs. Текстовый Da Vinci — это Claude, другой слой.
- **Модель — не строка, а строка плюс её настройка** (`geminiLiveModel()` там
  же). По умолчанию `gemini-3.8-live` (с 2026-10-08); прежнюю
  `gemini-3.1-flash-live-preview` Google отключает не раньше 2026-11-17, и
  отключённая модель не «хуже работает» — не открывается ни одна сессия. Модели
  различаются двумя полями, и чужая настройка — это отказ в сессии: 3.8 не
  принимает `thinkingLevel` и вызывает инструменты асинхронно, если каждому не
  указано `BLOCKING` (тогда ассистент говорит, не дождавшись данных CRM).
  Сменить модель без релиза — `VOICE_GEMINI_LIVE_MODEL` в окружении процесса;
  `…-extended-thinking` сюда не годится (инструменты только асинхронно,
  `turnComplete` перестаёт значить «договорил», а на нём стоит голосовое «да»).
- **Модель сначала проверяют на настоящем провайдере, потом включают.** Моки
  докажут только, что мы отправили то, что собирались. Ключ Gemini живёт только
  на проде, поэтому проверка тоже живёт там:
  `cron-trigger.sh "/api/cron/voice-provider-check?model=<id>&turn=1"` открывает
  настоящую сессию ключом самого сервера (ключ никуда не уходит) и отвечает
  `"ok":true|false` с причиной словами Google. `turn=1` задаёт вопрос о данных
  и придерживает ответ инструмента: модель обязана дождаться. Без параметров
  проверяется модель, на которой сейчас сидят сессии, — это делает каждый
  деплой (шаг «Verify Gemini Live accepts the voice assistant setup»), так что
  отключённая Google модель — красный шаг, а не жалоба пользователя. Тот же
  код — `gemini-live-provider-probe.test.ts`, если ключ есть под рукой.
- **Сокет с сервера через SDK работает только с `WS_NO_BUFFER_UTIL`**
  (`src/instrumentation.ts`). webpack подсовывает `ws` пустой модуль вместо
  отсутствующего `bufferutil`, и любой кадр от 48 байт падал с
  `b.mask is not a function` — так выглядел первый запуск проверки на проде.
  Локально и в vitest этого нет: там `ws` не собран в бандл.
- **Ассистент вправе промолчать.** В 3.8 proactive audio включён всегда: на
  речь, обращённую не к нему, модель может не прислать вообще ничего — ни
  звука, ни `turnComplete`. Это не зависание. Когда человек замолчал, говорит
  `voiceActivity` (`ACTIVITY_END`; `inputTranscription.finished` не приходит
  никогда), и если ассистент после этого десять секунд бездействует, консоль
  возвращается в «слушаю» и ничего модели не шлёт. Сторож, который ждёт ответа
  на каждую реплику, на этой модели закрывает живые разговоры.
- **Граница доверия.** Разговор ведёт провайдер, но данные CRM через него НЕ идут.
  Каждый вызов инструмента — это same-origin fetch из вкладки пользователя с его
  сессионной кукой (`src/components/ai/voice-console.tsx` → `/api/v1/ai/voice/read`).
  Агент решает ЧТО спросить, браузер — КТО спрашивает. Поэтому украденный токен
  разговора даёт чат-бота, а не данные. **Не заменять client tools на webhook tools:**
  провайдер не подписывает вызовы webhook-инструментов, и наш эндпоинт не смог бы
  отличить настоящий вызов от поддельного.
- **Только чтение.** Ничего из `src/lib/ai/tools.ts` голосу не доступно. Агент
  зачитывает вслух данные, которые пишет внешний мир (входящие сообщения, имена
  лидов), и модель, чьи аргументы можно увести таким текстом, не должна быть в
  одном шаге от `send_email`.
- **Кому голос — решает переключатель «Голос» в «Настройки → Пользователи»**
