# LeadDrive CRM v2 — заметки для Claude

## Порядок доставки — `docs/DELIVERY-ARCHITECTURE.md`

Этот документ главнее всего остального в том, что касается пути изменения до
клиентов, и действует одинаково для Claude, Codex и любых будущих сессий.
Коротко, четыре слоя:

1. В `main` только через PR, прямой пуш запрещён.
2. Каждый PR разбирает агент, который его не писал (`agent-review` —
   единственная обязательная проверка). Своё же ревью не считается.
3. Прод выкатывается только из `main`, с атомарной подменой, проверкой здоровья
   и откатом — это уже построено.
4. Перед мержем того, что увидит пользователь, показать владельцу короткий
   список человеческим языком и дождаться «давай». Единственное, чего не ловит
   ни один тест: 6 сентября 2026 корректно написанная фича на главной, которую
   никто не заказывал, доехала до `main` с зелёными проверками.

Владелец работает один и диффы не читает. Его участие — одна строка «давай».

## Рабочий режим (одобрено владельцем)

Одобренные планы реализовывать **автономно**, без запроса подтверждений на каждый шаг:
ветка → PR → ревью агентом → полный прогон тестов → «давай» от владельца → мерж → автодеплой.
Отчёт владельцу — после каждого PR. Останавливаться и спрашивать только при
разрушительных действиях (удаление данных, откаты) или продуктовых развилках,
меняющих смысл фичи.

## Прод и деплой

- Пуш в `main` **автоматически деплоит на прод** (`.github/workflows/deploy.yml`):
  security-гейты → сборка → tarball → scp → `scripts/server-deploy.sh`
  (атомарный swap, `prisma migrate deploy` fail-fast, health-check `/api/v1/ping`,
  авто-откат). Ручной `scripts/deploy.sh` отключён: он намеренно завершается с
  ошибкой, потому что обходил backup/migration/cutover gates.
- Прод: `root@13.140.132.245`, `/opt/leaddrive-v2`, PM2 `leaddrive-v2`, порт 3001,
  https://app.leaddrivecrm.org. Production получает готовый immutable artifact
  от ephemeral GitHub-hosted Linux runner и не собирает приложение из checkout.
  `scripts/server-build-deploy.sh` также отключён и намеренно завершается с
  ошибкой.
- Приложение — PWA: после деплоя пользователи могут видеть старый UI из кэша
  service worker'а — это не баг деплоя (лечится жёстким обновлением).
- Шаги «Verify … scheduler» дёргают на проде `cron-trigger.sh`. У него локальный
  flock, и раньше совпадение с минутным кроном печатало `SKIPPED` (exit 0,
  эндпоинт при этом НЕ вызван) — ассерт падал на здоровом проде, а вместе с ним
  молча пропускались все шаги ниже (run 33415973322, 2026-08-31: одна гонка за
  лок съела шесть чужих проверок). `SKIPPED` — это «не проверено», а не
  «прошло»: не заменять ожидание на «считать успехом». Теперь верификаторы
  ждут лок (`CRON_TRIGGER_LOCK_WAIT_SECONDS=120`, при исчерпании — красный шаг),
  а каждая пост-деплойная проверка помечена
  `if: !cancelled() && steps.deploy_atomic.outcome == 'success'` и отчитывается
  сама за себя. Лок именуется по ВСЕЙ строке таргета, поэтому с расписанием
  конкурируют только `voice-call-queues` и `mtm-cleanup`, а `…?smoke=1` — нет.

## Postgres RLS (критично)

- Почти все тенантные таблицы под `FORCE ROW LEVEL SECURITY`
  (политика `tenant_isolation` по `organizationId`). RLS **fail-closed**:
  запрос без контекста тихо возвращает 0 строк.
- Каждый путь к БД обязан идти через `withRls` / `withRlsAuth` (роуты) или
  `runWithTenant` / `runWithRlsBypass` (`src/lib/rls-context.ts`). Не возвращать
  голый PrismaPromise из `.run`-скоупа. Fire-and-forget промисы наследуют
  ALS-контекст, только если созданы внутри скоупа.
- Миграции выполняются без `app.org_id`: backfill по RLS-таблицам — только через
  DO-блок snapshot/disable/restore (образец:
  `prisma/migrations/20260705152500_monitoring_external_sources_rls_backfill`).
- Проверки: `python3 scripts/rls/find-context-gaps.py` (0 gaps — гейт),
  рантайм-страж `[RLS-GUARD]` в `src/lib/prisma.ts`.
- Standalone-скрипты `scripts/*.ts|mjs` НЕ обёрнуты — на проде запускать только
  через `scripts/_rls.mjs → makeScriptPrisma` или BYPASSRLS-роль.
- `contacts`, `deals`, `invoices` — RLS включён и FORCE (проверено на проде
  2026-08-06). Всего на проде 447 из 461 тенантной таблицы под RLS; список
  оставшихся 14 — в `docs/rls-rollout-runbook.md`.

## Тесты и проверки

- `npm test` (vitest, node env, `src/__tests__/*.test.ts`). Базлайн теперь
  **зафиксирован в `test-baseline.json`** (список красных на main файлов) и
  проверяется блокирующим `node scripts/check-test-baseline.mjs` — в pr-checks
  и в deploy. Гейт двусторонний: падает и когда зелёный файл покраснел, и когда
  перечисленный позеленел. Второе — не придирка: базлайн, называющий проходящие
  файлы, это место, где спрячется следующая настоящая поломка. Устаревший базлайн
  опаснее его отсутствия — настоящую поломку списывают на «известное», — поэтому
  список правится коммитом с объяснением, а не регенерацией «чтобы позеленело».
  Оговорка из `ca51fc153`: `--update` гоняй по CI-логу, не по dev-боксу
  (`lib-rls-context` таймингозависим и локально красный, а на раннерах зелёный).
- `npx tsc --noEmit` **локально не измеряется — не пытайся.** Графу типов нужно
  ~12 ГБ (CI ставит `NODE_OPTIONS=--max-old-space-size=12288`), dev-бокс уходит
  в OOM и печатает пустой лог. `grep -c 'error TS'` по такому логу даёт 0,
  неотличимый от чистого прогона: **локальный ноль — это краш, а не «ошибок
  нет».** На этом уже обожглись: PR #1056 опубликовал «tsc --noEmit: 0 errors»
  и в тот же день сам себя опроверг — прогон упал с exit 134, не напечатав ни
  строки. Ровно от этой ловушки и написан `scripts/ci/check-typecheck-gate.sh`.
  Авторитетное чтение одно — CI-лог. Шаг «Defect-shaped type errors vs baseline»
  печатает его строкой `check-typecheck-baseline: N gated pair(s) now,
  M in baseline (T errors total)`. Порядок величины T — сотни (август 2026:
  ~845). **Точное T сюда не переписывать: оно зависит не только от твоей ветки.**
  2026-08-31 два коммита PR #1058 с побайтово одинаковым кодом (менялся только
  текст `CLAUDE.md`) дали 845 и 846 за час: `actions/checkout` без `ref:` на
  событии `pull_request` берёт `refs/pull/N/merge`, то есть твою ветку, влитую
  в main НА МОМЕНТ ПРОГОНА, — а между прогонами в main въехал чужой PR #1057.
  Стабильная и осмысленная величина — N/M (гейтящиеся пары, сейчас 68): именно
  её сторожит `typecheck-baseline.json`. Отсюда же практический вывод: рост T
  между твоими прогонами не обязательно твой.
- Шаг `npx tsc --noEmit` в pr-checks действительно `continue-on-error` — но это
  единственный такой шаг, и его выхлоп кормит два **блокирующих** гейта, так что
  «тайпчек ничего не блокирует» уже неправда:
  - `scripts/ci/check-typecheck-gate.sh` — семейства, которые никогда не «просто
    тип»: TS1xxx (синтаксис), TS2307 (импорт в никуда), TS2304/TS2552
    (несуществующее имя — `next.config` глушит ошибки сборки, поэтому такое
    доезжает до браузера как ReferenceError). Плюс фейлит сам факт непрошедшего
    тайпчека: exit вне {0,1,2} — это не диагностика, а смерть компилятора.
  - `scripts/ci/check-typecheck-baseline.mjs` — новые ошибки дефектных семейств
    (TS2339/2345/2353/2322/2554/2551) против `typecheck-baseline.json`,
    гранулярность «файл + код». TS7006 (implicit any) намеренно НЕ гейтится:
    это половина кучи и вопрос строгости, а не баг.
  Итого блокируют сборку четыре шага: `lint:pii-columns`, оба гейта выше и
  `check-test-baseline.mjs`. Почему advisory было мало — `#1056`: TS2353 неделями
  печатался на трёх вызовах, где `channelConfigId` терялся, и ответы Chatwoot
  уходили через первый попавшийся конфиг.
- Про `lead-qualification.ts` / `ai-autoreply.ts`: прежняя формулировка «известные
  implicit-any, воспроизводятся на чистом main» **снята**, и заменять её на
  «уже починили» тоже нечем — сказать, живы ли там именно TS7006, по коммитнутым
  артефактам нельзя: TS7006 в базлайн не пишется вовсе, так что отсутствие файла
  в `typecheck-baseline.json` не доказывает ничего. Что известно точно: на main
  этот файл всё ещё числится там как `src/lib/inbox/lead-qualification.ts TS2345`.
  Вывод простой — списывать ошибку в этих двух файлах на «пре-существующую»
  нельзя ни в одну сторону, сверяйся с CI-логом конкретного PR.
- i18n: `node scripts/check-translations.js` — en.json источник истины,
  ru/az обязаны иметь все ключи (рус. плюралы: one/few/many/other).
- Конвенции тестов роутов: моки `@/lib/prisma` + `@/lib/api-auth`, реальные
  RLS-обёртки; Next 15 params — `Promise.resolve({id})`; образцы:
  `src/__tests__/s3-sequences.test.ts`, `s3-cadence.test.ts`.

## Автономия

Владелец держит несколько агентских сессий сразу (Codex, Claude desktop,
помощники в CI) и не хочет быть передаточным звеном между ними. Постоянное
разрешение, выдано 2026-09-06: **доводи изменение до продакшена сам.** То
есть без подтверждений на каждом шаге:

- пушь ветку и открывай PR;
- следи за проверками, красную — чини сам: красная проверка это работа, а не
  вопрос владельцу;
- мержи в `main`, когда обязательные проверки зелёные;
- дай деплою после мержа пройти (см. «Deploy» в AGENTS.md — там разрешение на
  деплой уже стоит).

Докладывай результат, а не каждый шаг. «Смержил #1102, задеплоил,
/api/v1/ping ok» — это весь отчёт, который нужен.

Чего это разрешение НЕ покрывает — никакая автономия не делает это
безопасным:

- **Мерж красного.** Никогда не мержить с падающей обязательной проверкой, не
  обходить её через `--admin`, не ослаблять, не перевешивать и не удалять
  гейт ради мержа. Если гейт действительно неправильный — скажи об этом и
  оставь его на месте.
- **Разрушительные операции с продовыми данными** — дроп или восстановление
  базы, удаление тенанта, необратимый бэкфилл. Подготовь и спроси.
- **Всё, что требует лично владельца**: пароли, платёжные данные, создание
  аккаунтов, чужие панели. Спроси, не изобретай обходной путь.
- **Чужая ветка в работе.** Мержи то, что делал сам. PR другой сессии — только
  если владелец попросил.

Если твой мерж сломал прод — откатывай и передеплоивай сразу, это тоже твоя
работа и тоже без спроса.

## CI и деньги

GitHub Actions платный. Проверка кабинета 2026-09-08: за сентябрь начислено
$121.17, из них Linux $36.76 и macOS $84.41. Это текущий счёт аккаунта, а не
прогноз. У бюджета $100 стоит `Stop usage = No`: предупреждение не
останавливает задания и дальнейшие расходы.

Раньше `typecheck` в `pr-checks.yml` шёл на `macos-15-intel`, сейчас — на
выделенном self-hosted Linux-раннере. Графу типов нужно ~12 ГБ; на прежнем
Ubuntu-раннере памяти не хватало, и джоба
умирала с `exit 143`, пропуская блокирующие гейты. Убирать её нельзя — пустой лог
от рухнувшего компилятора неотличим от чистого прогона, см. выше про PR #1056.

`synchronize` прилетает на каждый пуш, и раньше ветка с
дюжиной чекпойнт-коммитов оплачивала дюжину macOS-прогонов.

- **Итерируй в драфте.** На draft-PR `static-checks` и `typecheck` не запускаются. Помечай PR
  ready for review, когда ветка готова: сработает `ready_for_review`, и гейт
  отработает один раз — перед мержем, который он и охраняет.
- Правки только в `**/*.md`, `docs/**`, `.agents/**` больше не запускают
  `pr-checks.yml` вовсе. Не подмешивай код в документационный PR ради прогона CI.
- Не добавляй `runs-on: macos-*` в новые джобы. Нужно больше 8 ГБ — спроси
  владельца.
- Новый workflow на `pull_request` обязан иметь и `paths`-фильтр уже всего
  репозитория, **и** `concurrency` с `cancel-in-progress: true`.
- Не снимай эти ограничители, чтобы проверка прошла быстрее. Скажи и спроси.

- Дорогой `typecheck` теперь идёт на выделенном self-hosted боксе
  (`runs-on: [self-hosted, linux, x64, leaddrive-typecheck]`, ровно один раннер —
  чтобы две 12-гигабайтные компиляции не делили 24 ГБ). Не возвращать на
  `macos-*`, не перевешивать метки, не класть на этот хост и в workflow с этими
  метками ни одного продового секрета.
- **Все остальные джобы на `pull_request` тоже идут туда**, под
  `runs-on: [self-hosted, linux, x64, leaddrive-ci]`, кроме коротких
  `agent-review` и скана секретов: они идут на существующий runner 4 с меткой
  `leaddrive-ci-light`. Установки зависимостей, Prisma, тесты и сборки на эту
  метку не направлять. Включённые минуты
  кончаются в первые дни месяца, после этого `ubuntu-latest` на PR-джобе —
  платное время. Не ставь `ubuntu-*` в новую `pull_request`-джобу. Осознанные
  исключения: label-gated `production-build` и весь `deploy.yml` (продовый
  SSH-ключ) остаются на GitHub-hosted.
- Раннеры делят один хост. Джоба не имеет права занимать фиксированный порт или
  фиксированный путь в `/tmp`: порты сервисов публикуй как `- 5432` и читай
  выданный порт из `job.services.<id>.ports['5432']` в шаге (job-level `env`
  его не видит), приложение под тестом поднимай на свободном порту, временные
  файлы — в `$RUNNER_TEMP`. Всё, что требует `sudo`/`apt` (например
  `playwright install --with-deps`), там не работает — проси поставить
  зависимость на хост. Образец — `static-checks` в `pr-checks.yml` и
  `social-monitoring-queue-e2e.yml`.

Полный разбор с цифрами — `docs/ci-cost-policy.md`.

## Голосовое управление (ElevenAgents)

- **Граница доверия.** Разговор ведёт ElevenLabs, но данные CRM через них НЕ идут.
  Каждый вызов инструмента — это same-origin fetch из вкладки пользователя с его
  сессионной кукой (`src/components/ai/voice-console.tsx` → `/api/v1/ai/voice/read`).
  Агент решает ЧТО спросить, браузер — КТО спрашивает. Поэтому украденный токен
  разговора даёт чат-бота, а не данные. **Не заменять client tools на webhook tools:**
  ElevenLabs не подписывает вызовы webhook-инструментов, и наш эндпоинт не смог бы
  отличить настоящий вызов от поддельного.
- **Только чтение.** Ничего из `src/lib/ai/tools.ts` голосу не доступно. Агент
  зачитывает вслух данные, которые пишет внешний мир (входящие сообщения, имена
  лидов), и модель, чьи аргументы можно увести таким текстом, не должна быть в
  одном шаге от `send_email`.
- **Гейт фейлит закрыто.** `src/lib/ai/voice/gate.ts` проверяет env-allowlist ПЕРВЫМ
  и безусловно: `orgHasModule` возвращает true при ошибке БД, `getOrgModuleContext`
  кэширует пустой результат на 30с, а модульный гейт `requireAuth` для superadmin
  вообще не выполняется. Гейт стоит на организации, а не только на пользователе.
- **Бюджет минут — резерв вперёд, зачёт по факту** (`src/lib/ai/voice/budget.ts`).
  Остановить разговор со стороны сервера НЕЛЬЗЯ, поэтому «считать израсходованное»
  не работает: закрыл вкладку — бесплатно. Брошенную сессию добивает крон
  `/api/cron/voice-session-reaper` и списывает резерв целиком.
- Микрофон открыт ТОЛЬКО на `/ai/voice` (`src/proxy.ts`); матчер зовётся через
  guard `!!pathname &&` — большинство вызовов `withCspHeaders` pathname не передают.
- Список пилота — в env (`VOICE_PILOT_ORG_ID`, `VOICE_PILOT_USER_IDS`), не в БД:
  роут флагов организации и `UserPreference` пишутся их же владельцем.
- Метрики отбирались проходом на «правда, но вводит в заблуждение»; что выброшено
  и почему — в комментариях `src/lib/ai/voice/summaries.ts`. Не возвращать оттуда
  возраст очереди по `lastMessageAt` и «открытые визиты» как дневную величину.
