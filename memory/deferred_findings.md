- **[FIXED 2026-08-26 — Facebook webhook: contested `pageId` routed by unordered scan (cross-tenant)].** `src/app/api/v1/webhooks/facebook/route.ts` resolved the inbound channel with `findFirst({ where: { ...orgScope, pageId, ... } })` and **no `orderBy`**. On the shared-LeadDrive-app path (no `?t=`) `orgScope` is `{}` by design, so when two orgs both held an ACTIVE ChannelConfig for the same `pageId` the winner was whatever row the planner reached first — it could flip on a VACUUM/plan change with nothing in the logs. The comment already named the risk ("pageId is NOT unique across tenants…") but the guard had only been applied to the `?t=` path. **Live on prod 2026-08-26:** IG business account `17841410801241198` has an active row in BOTH `leaddrive` (channelType=instagram, "Мыслители прошлого / @kishiklubu.az") and `brandprotection` (channelType=instagram, `settings.igLogin=true`, connected 2026-07-21). **Fix:** `findMany` + `orderBy [createdAt asc, id asc]`, then a TOTAL JS order — (1) non-igLogin first (an Instagram-Login row belongs to the tenant's separate IG-Login app, served by `/api/v1/webhooks/instagram`, which mirrors this by *preferring* igLogin rows; de-preferred, not excluded, so a pageId claimed only by an igLogin row still ingests), (2) `channelType` matching the payload surface, (3) **oldest `createdAt`** — deliberately not newest: pageId is typed by hand into the channel form with no OAuth proof of ownership, so "newest claim wins" would let a tenant capture another's DMs by pasting their public Page ID, and a latecomer cannot back-date a row, (4) `id`. Resolution stays under `runWithRlsBypass` (it IS the org resolution); everything downstream stays inside `runWithTenant`.
