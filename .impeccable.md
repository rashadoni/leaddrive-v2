## Design Context

### Users

Brand-protection operators, communications teams, lawyers, and assistants working for companies, public figures, and brands. They use the screen during focused review of potentially harmful social content and need to understand what was actually checked, what matched, and what remains unavailable.

### Brand Personality

Careful, operational, and evidence-led. The interface should create confidence through explicit provenance and honest capability states, not through decorative claims or artificial certainty.

### Aesthetic Direction

Keep LeadDrive's light, professional CRM shell and restrained orange accent. The media workflow should feel like a compact evidence workbench: one dominant URL action, a readable processing trail, and results that distinguish detected facts from unavailable stages. Support the existing dark theme without introducing a separate visual language.

### Design Principles

1. Lead with the next useful action: paste one link, choose the monitored subject, start the check.
2. Make every stage auditable: resolved metadata, cover OCR, frame OCR, transcript/ASR, match decision.
3. Never present a configured capability as a completed check; use explicit ready, blocked, queued, and completed states.
4. Keep advanced budgets, visual references, and provider settings available but secondary to the primary check flow.
5. Preserve responsive operation and keyboard accessibility for analysts working from laptops and tablets.

## Confirmed Feature Brief: Check a social video by URL

### Feature Summary

An operator submits a TikTok, Instagram, Facebook, YouTube, direct video, image, or audio URL and associates it with a monitored subject. LeadDrive resolves the assets it can legally access, processes cover/frame/audio text according to tenant policy, and shows exact matches and blockers in one queue.

### Primary User Action

Paste a URL and start a check without manually hunting for a cover or audio URL.

### Design Direction

An evidence workbench consistent with the context above: fast, calm, and explicit about limitations.

### Layout Strategy

The URL check occupies the first and strongest section. Provider readiness and stage progress sit next to it. The processing queue follows immediately. Visual references and budget/policy controls remain available in a secondary settings area.

### Key States

- Empty: explains which links can be checked and which stages depend on provider access.
- Resolving: URL and metadata are being inspected.
- Queued/processing: shows the current stage without implying a match.
- Match: shows matched terms, subject, confidence, signal type, and source.
- No match: confirms processing completed but did not find a configured subject.
- Partial/blocked: names the unavailable asset or missing provider credential and the manual fallback.
- Error: preserves the submitted URL and gives an actionable reason.

### Interaction Model

Submit from the URL field, receive an immediate resolution summary, then poll the existing dashboard while work is queued. Operators can retry a blocked observation after configuration changes and open the original source in a new tab.

### Content Requirements

All user-facing copy is localized in Russian, English, and Azerbaijani. Capability labels describe actual evidence: cover found, audio unavailable, transcript supplied, provider missing, or extraction unsupported.

## Confirmed Feature Brief: Truthful monitoring coverage

### Feature Summary

Every monitoring card and the creation wizard must state what is actually
scanned: a bounded keyword/hashtag query, comments under posts discovered by
that query when enabled, or no configured search terms. Facebook and Instagram

- A paid provider improves collection reach but never implies 100% of a social network.
- `Complete` means complete only for the requested input or query window, with no known provider/schema error and without hitting the configured record cap.
- Facebook and Instagram scenarios use bounded global provider queries; this
  improves reach but must never be presented as exhaustive coverage of either
  network.

- Configured: a working collection route exists; completeness may still be unknown.
- Limited: a source or route is degraded, sampled, or only partially covered.
- Needs setup: no runnable route or comment capability exists.
- Input complete: the latest requested source/window completed below its cap.
- Partial/pending/blocked/unknown: explicit alternatives that must never be rendered as success.

## Confirmed Feature Brief: Guided monitoring workflow and automatic review

### Feature Summary

Brand-protection operators need one compact workflow for a selected monitoring
instead of several oversized cards with unrelated actions scattered through
them. The workflow must guide the operator from collection, through automatic
and manual review, to a clean result while keeping provider limits, evidence,
duplicates, and rollback behavior explicit.

### Primary User Action

Select one monitoring and move through three clear stages: collect current
evidence, resolve the review queue, then open the clean accepted result.

### Design Direction

Use LeadDrive's careful, operational, evidence-led personality. The screen
should feel like a compact analyst workbench: one obvious next action, dense but
readable evidence, restrained orange for the active step, and honest language
for incomplete or blocked coverage.

### Layout Strategy

- Replace the expanded two-column card wall with a compact monitoring selector.
- Render one selected monitoring in a single full-width workbench.
- Keep a persistent three-step navigator: **Collection**, **Review**, and
  **Results**.
- Show only the active step's detailed controls; retain the other steps as
  compact summaries so operators always understand what comes next.
- Keep source diagnostics and rollback details available through progressive
  disclosure rather than nested cards.
- On narrow screens, the selector scrolls horizontally and the step navigator
  becomes a compact vertical sequence without hiding any action.

### Key States

- No monitoring selected: select the first available active monitoring and
  explain the three-stage flow.
- Collection ready: one primary run action for the selected monitoring.
- Collection running/stopping/completed/limited: live source progress and an
  explicit next step.
- Review loading: calculate the current queue without changing it.
- Review ready: group exact normalized-link repetitions, preserve different
  sites/pages/profiles/posts as separate evidence, and show deterministic
  positive, negative, protected, and unresolved counts.
- Review applying: atomically apply only frozen decisions; do not call a
  provider or start a new search.
- Review success: show affected links/rows, remaining review count, and a
  time-bounded rollback action.
- Review stale/conflict/error: preserve the queue and explain the exact safe
  recovery action.
- Results: accepted posts and comments only, with source links and filters.
- Empty results: explain whether collection has not run, produced no relevant
  evidence, or remains blocked.

### Interaction Model

1. Choose a monitoring from the compact selector.
2. In **Collection**, run only that monitoring and observe live progress.
3. Continue to **Review**, inspect the frozen automatic plan, and explicitly
   confirm its safe decisions.
4. The positive path may advance a candidate only when the existing
   deterministic relevance evaluator can prove the monitored subject from
   independent evidence. A provider snippet alone never qualifies.
5. Exact normalized-link repetitions move together; different URLs remain
   separate even when their stories are similar.
6. Continue to **Results** to view the clean accepted feed.
7. Keyboard focus follows the completed action to the next stage; every stage
   remains directly selectable for inspection.

### Content Requirements

- Localize every label and status in Azerbaijani, Russian, and English.
- Use outcome-based action labels: run this monitoring, review automatic
  decisions, apply safe decisions, open clean results.
- Keep counts explicit and separate: accepted results, queue rows, distinct
  links, exact-link repetitions, rejected, advanced, protected, and unresolved.
- State clearly that automatic review reuses the existing queue and does not
  launch paid providers.
- Avoid internal error codes in primary copy; expose them only in secondary
  diagnostics when they help an administrator resolve a blocker.

### Safety Contract

- Tenant and monitoring scope are mandatory for every read and mutation.
- Automatic positive decisions require deterministic evidence and the existing
  relevance contract; uncertain candidates stay in review.
- Applying a plan is atomic, idempotent, fingerprinted, audited, and reversible
  during the displayed rollback window.
- No automatic monitoring run, provider call, external reply, or paid action is
  introduced by this workflow.

- responsive-design.md
- ux-writing.md

None blocking. The owner's confirmed priorities are compact cards, a

- Occasional phone users work from a contact-first queue. They choose or undo a
  working date without loading a compressed spreadsheet.
- Keyboard and low-vision users need visible focus, arrow navigation between
  matrix cells, text state in addition to color, and usable 200% zoom.

### Design Direction

Preserve the business density and spreadsheet-like efficiency of the supplied
SwissMed reference while modernizing its interaction model. The result should
feel calm, precise, and operational inside LeadDrive's light professional shell;
it is functional parity, not a pixel copy of the legacy QuadraSoft screen.

### Trust and Interaction Contract

- Contact identity remains sticky while dates move horizontally and rows are
  virtualized vertically.
- Cell, row, date, and all-visible actions stage changes first. A review step
  names every affected contact and date before version-checked persistence.
- Draft, published/in-progress, conflict, unavailable, add, and remove states
  use localized text and icons in addition to color.
- Last-visit and monthly-count facts retain their source meaning; source
  drill-down remains available for the monthly count.
- Phone selections stay reversible until save and use touch-sized controls.
- The current governed coverage snapshot may be displayed, but live
  capacity/coverage simulation remains explicitly unavailable until SwissMed
  supplies signed transition and capacity rules.

### Responsive Layout Strategy

- Desktop and landscape tablet: dense virtualized grid with sticky contact
  identity, bounded date windows, and a persistent staged-change summary.
- Compact tablet: the same grid with compound identity cells and horizontal
  date paging.
- Phone: contact cards with horizontally scrollable working-date actions and a
  detailed staged-change review; never scale the full matrix into the viewport.

### Content Requirements

All new labels, state descriptions, dates, errors, and recovery actions are
localized in Russian, Azerbaijani, and English. Internal enum values are never
shown directly.

### Open Questions

The two small legacy header controls and the exact live capacity/coverage
transition rules are not proven by the reference image. They remain blocked on
signed product clarification and must not be invented in the UI.

## Confirmed Feature Brief: Step-by-step MTM route building

### Users and Primary Action

Field agents and managers who are not technical users create a day's route.
They need to select an employee, choose a date, and add the right doctor,
pharmacy, or organization without having to understand ownership terminology,
open a second catalogue, or reconstruct the route after returning. The primary
action is always the next unfinished step in that one flow.

### Design Direction

Use LeadDrive's existing light CRM shell and orange primary action, but make
the route builder a real three-screen wizard rather than a dense administration
form with three simultaneous panels. It should be calm, literal, and
reassuring: only the current step is visible, there is one clear next action,
instructions are Azerbaijani-first, and touch targets work on a tablet. The
audience benchmark is a capable seventh-grade student.

### Interaction Contract

- The empty route may never show an "Add customer" action before an employee
  and date are selected. It must instead point directly to the missing choice.
- Once the employee and date are set, doctors, pharmacies, and organizations
  are chosen inside the same builder; route creation does not redirect to a
  separate catalogue.
- If a manager needs an existing unassigned or transferable record, the
  builder exposes a compact, scoped in-place picker. A transfer is named
  plainly before it takes effect and remains audited server-side.
- Agents without assignment rights see one concise explanation and a useful
  manager-request path, never an inert or misleading primary button.
- Optional route name, participants, notes, filters, and detailed planning
  tools remain progressively disclosed until the basic route is complete.
- Step one contains only employee, date, and optional settings. Step two is a
  focused doctor/pharmacy/organization picker. Step three reviews order and
  time before save or publication.
- A compact progress indicator is shown once. Large duplicate step cards,
  blocked future panels, and competing orange actions are not shown.

### Responsive Layout Strategy

- Desktop and landscape tablet: one centered step at a time with bounded line
  length; the customer picker may use a balanced two-column result grid.
- Compact tablet: the same wizard with full-width fields and touch-sized
  controls, never a compressed desktop split view.
- Phone and APK: a single column with a solid safe-area-aware bottom action;
  Back remains secondary and the one next action spans the available width.

### Content Requirements

All visible instructions, confirmation states, errors, and recovery actions
are localized in Azerbaijani, English, and Russian. Use the same plain term
for each object throughout a path. No UI copy may imply that a page transition
will occur when the action remains in place.

## Confirmed Feature Brief: Plain-language MTM visit journal

### Users and Primary Action

Field agents need to see and finish the visit that is happening now. Managers
need to understand who is currently at a customer, what was completed today,
and which visit evidence needs attention. Both groups include people with
little software experience, so the primary action and current state must be
understandable without knowing internal MTM status codes.

### Design Direction

Turn the legacy data table into a calm operational journal. Lead with active
work and today's facts, then place searchable history below it. Preserve the
light LeadDrive shell and restrained orange action, but remove the repeated
metric-card wall, raw enums, browser-locale dates, and permanently exposed
destructive icons. The comprehension benchmark is a seventh-grade student.

### Interaction Contract

- An active visit is always the first actionable section and keeps its existing
  offline-safe workspace.
- History opens on today's activity, with explicit 7-day, 30-day, and all-time
  choices. Search, status, and sort remain available without competing with the
  primary action.
- Every row answers who, where, when, duration, state, and GPS evidence in plain
  language. Internal enum values are never rendered directly.
- GPS is described as confirmed, outside the expected area, or unavailable;
  color is supportive and never the only signal.
- Edit remains discoverable for authorized users. Delete is secondary, named,
  and protected by the existing confirmation instead of occupying every row in
  red.
- The journal states when only the latest bounded result set is available and
  never presents a truncated count as a complete total.
- Phone and tablet layouts become stacked touch-sized journal entries rather
  than a horizontally compressed desktop table.

### Content Requirements

All labels, statuses, date ranges, empty states, errors, GPS explanations, and
recovery actions are localized in Azerbaijani, Russian, and English. Errors use
actionable product language and never expose generic English fetch messages to
an Azerbaijani or Russian user.
